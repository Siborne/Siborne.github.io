MVC から DDD へ：パッケージ名が変わっただけではなく、「オブジェクト」が生きた

はじめに

DDD（ドメイン駆動設計）を学ぶ際、多くの人が複雑な概念に挫折します。しかし本質に立ち返れば、DDD は MVC の「超進化拡張版」 と理解できます。MVC の基盤の上に、より明確な責務分割とロジックの分離を通じて、システムがビジネスの複雑化に伴って「肥大化」する痛点を解決します。

一、核心的な考え方：「説明書を探す」から「当事者に聞く」へ

従来の MVC（貧血モデル） では、エンティティクラス（Entity/PO）は単なるデータの入れ物であり、白紙のようなものでした。すべてのビジネスロジックは Service 層に蓄積されます。

  • 痛点： Service が肥大化し、ロジックが散乱し、メンテナンスは絡まった糸の中から糸口を探すようなものです。

DDD（充血モデル） では、データとビジネスロジックが一緒に記述されます。

  • 転換： エンティティクラスが、生命と原則を持つ「ビジネスエキスパート」になります。

  • 例： 「注文キャンセル」のロジック。

    • MVC： OrderService が Order データを取得し、状態を判断し、状態を変更し、保存します。
    • DDD： Order エンティティ内部に cancel() メソッドがあり、自身でキャンセル可能か判断します。

ポイント： DDD の利点はロジックの高度な凝集性です。ビジネスロジックに変更があった場合、数千行の Service を探し回るのではなく、対応するドメインモデルオブジェクトだけを修正すればよいのです。

二、アーキテクチャの対応関係：DDD と MVC のマッピング

DDD のフローは次のようにシンプルに理解できます：

Controller $\rightarrow$ Application Service $\rightarrow$ Domain Model $\rightarrow$ Repository (Impl $\rightarrow$ Mapper)

理解を助けるために、この対比表を見てみましょう：

層 DDD の名称 MVC の対応 責務の強化点
インターフェース層 Interfaces Controller プロトコル変換（REST/JSON）のみを担当し、ビジネスロジックは一切行わない。
アプリケーション層 Application Service (軽量) 指揮官： if-else を書かず、ドメインオブジェクトの作業を編成するだけ。
ドメイン層 Domain Entity (重量) 核心： ビジネスルールを含み、データとロジックが共存。
インフラ層 Infrastructure DAO / Mapper プラグイン化： データベースの詳細を隠蔽。Repository はインターフェース、Mapper は実装。

三、DDD のパッケージが増える理由（分離の真実）

DDD が ApplicationService、Domain Model、Repository などを導入することに気づくでしょう。一見煩雑に見えますが、実際には二段階の核心的分離を実現するためです：

1. ビジネスロジックとフロー編成の分離 (Application vs Domain)

  • Application 層は「最初に何をし、次に何をするか」だけを気にします。
  • Domain 層は「このビジネスルールは何か」だけを気にします。
  • 成果： ビジネスロジックは環境から切り離して単体テストが可能で、データベースを起動する必要がなく、非常に高速です。

2. ビジネスロジックとストレージ技術の分離 (Domain vs Infrastructure)

  • ドメインモデルは Repository インターフェースだけを認識し、基盤が MyBatis、JPA、Redis のいずれであるかを気にしません。
  • 成果： データベースを MySQL から MongoDB に変更しても、コアビジネスロジック（Domain 層）は一字も変更する必要がありません。

四、モデルの3つのメンバー（戦術的モデリング）

DDD のドメイン層では、すべてのクラスが同じというわけではありません。ビジネスロジックをより科学的に整理するために、通常モデルを以下の3種類に分類します：

1. エンティティ (Entity) —— 一意の識別子を持つ

エンティティの最も核心的な特徴は**アイデンティティ（Identity）**です。たとえすべての属性が変わっても、それは依然として同じオブジェクトです。

  • 定義： 一意の識別子（ID）を持つオブジェクト。2つの注文の商品と価格が全く同じでも、ID が異なれば別のもの。
  • 特徴： ライフサイクルを持つ（作成、変更、状態遷移、アーカイブ）。
  • 例： Order（注文）、User（ユーザー）。

シナリオ： 注文作成時、状態は「支払い待ち」、配送先住所は「上海」；支払い後、状態は「支払い済み」に、住所は「北京」に変更。

核心： 状態と住所は変わったが、OrderNo（または ID） が変わっていないため、依然として同じ注文とみなします。

コードの特徴： 内部に必ず private Long id; または private String orderNo; があり、ロジック判断時にこの ID を使用して equals() を行います。

2. 値オブジェクト (Value Object) —— 属性のみを持ち、ID を持たない

値オブジェクトは「説明的なテキスト」のようなものです。2つの値オブジェクトのすべての属性が同じであれば、それらは同じものです。

  • 定義： ID を持たず、属性によって定義されます。2つのオブジェクトの属性値が完全に同じであれば、相互に置換可能です。
  • 特徴： 不変性（Immutable）。住所を変更する場合、元の住所オブジェクトの属性を変更するのではなく、新しい住所オブジェクトに直接置き換えます。
  • 例： Address（都道府県市区町村の組み合わせ）、Money（通貨+金額）。

シナリオ： 注文に配送先住所がある：{都道府県: "広東", 市区町村: "深圳", 町域: "南山区"}。

核心： この住所オブジェクトの「身分証明書」は気にせず、どの住所が記入されているかだけを気にします。2つの注文が同じ場所に配送される場合、これら2つの住所オブジェクトは論理的に等価です。

コードの特徴：

  1. ID を持たない。
  2. 不変性（Immutable）：住所を変更したい場合、address.setStreet("福田区") を呼び出すのではなく、Order に新しい Address オブジェクトを直接与えます：order.changeAddress(new Address("広東", "深圳", "福田区"))。
  • コードの小技：

3. 集約ルート (Aggregate Root) —— 組織の管理者

  • 定義： 関連オブジェクトのグループの「大ボス」。外部は集約ルートを通じてのみ内部メンバーにアクセスできます。
  • 責務： ビジネスの整合性（不変条件）を維持する。
  • 例： 注文業務では、Order が集約ルートで、OrderItem（注文明細）はその内部メンバー。

シナリオ： 1つの注文に3つの商品（注文明細）がある。

核心：

  1. 外部の Service は Order をバイパスして直接 OrderItem の価格を変更できない。
  2. order.adjustItemPrice(itemId, newPrice) を呼び出す必要がある。Order という「大ボス」がこの操作の合法性を判断する（例：注文が既に出荷済みの場合、ボスは価格変更を拒否する）。

ライフサイクル： 集約ルートはその内部メンバーの生死に責任を持つ。Order がデータベースから削除された場合、その内部の OrderItem も一緒に消滅しなければならない。

禁止事項： Controller で直接 OrderItemMapper を呼び出してある商品の価格を変更することは絶対にできず、必ず Order.updateItemPrice() を通す必要がある。

4. まとめ対比

モデルタイプ 一意の ID あり 属性が完全に同じ場合 変更方法 例
エンティティ (Entity) はい 依然として2つの独立したオブジェクト メソッドで属性を変更 ユーザー(User)、商品(Product)
値オブジェクト (VO) いいえ 同じオブジェクトとみなす 全体置換（不変） 通貨(Money)、住所(Address)
集約ルート (AR) はい （エンティティに同じ） 内部の全メンバーを調整 注文(Order)、フォーラムトピック(Topic)

五、モデル変換：各層に独自の「顔」がある

「分離」を実現するために、各層で使用されるモデルは実際には異なります。記述は面倒ですが、データベースロジックがビジネスロジックを汚染するのを効果的に防げます：

  1. DTO（Data Transfer Object）： インターフェース層で使用。フォームのような形で、フィールドが少ない場合もある。
  2. Domain Entity： ドメイン層で使用。あなたが書いた「生きたオブジェクト」で、ビジネスロジックを持つ。
  3. PO（Persistent Object）： インフラ層で使用。データベーステーブルと全く同じ形。

// エンティティクラス：Order.java
public class Order { // <--- これは【集約ルート】
    private Long orderId; // <--- 集約ルートもエンティティであり、一意の ID を持つ
    private List<OrderItem> items; // <--- 注文明細は【エンティティ】だが、集約ルートの管理下
    private OrderStatus status; // CREATED, PAID, CANCELLED, SHIPPED
    private Address address; // <--- 配送先住所は【値オブジェクト】、ID なし、全体置換
    private BigDecimal totalPrice;

    // 集約ルートのメソッド：ビジネスの整合性を保証
    public void changeAddress(Address newAddress) {
        if (this.status == OrderStatus.SHIPPED) {
            throw new BusinessException("出荷後は住所を変更できません");
        }
        this.address = newAddress; 
    }

    // --- ビジネスロジック：新規注文の構築制約 ---
    public Order(List<OrderItem> items) {
        if (items == null || items.isEmpty()) {
            throw new BusinessException("注文には少なくとも1つの商品が必要です");
        }
        this.items = items;
        this.status = OrderStatus.CREATED;
        this.totalPrice = calculateTotal(); // 内部ロジック、自動で合計金額を計算
    }

    // --- ビジネスロジック：注文のキャンセル ---
    public void cancel() {
        if (this.status == OrderStatus.SHIPPED) {
            throw new BusinessException("出荷済みの注文はキャンセルできません");
        }
        this.status = OrderStatus.CANCELLED;
    }

    private BigDecimal calculateTotal() {
        return items.stream().map(OrderItem::getPrice).reduce(BigDecimal.ZERO, BigDecimal::add);
    }
  
    // Getter 省略...
}

// リポジトリインターフェース：OrderRepository.java（ビジネス動作のみ定義）
public interface OrderRepository {
    void save(Order order);
    Order findById(Long id);
}

@Service
public class OrderApplicationService {
    @Autowired
    private OrderRepository orderRepository;

    // 新規注文フロー
    @Transactional
    public void createOrder(OrderCreateDTO dto) {
        // ドメインモデルを呼び出して作成
        Order order = new Order(dto.getItems());
        // リポジトリを呼び出して永続化
        orderRepository.save(order);
    }

    // 注文キャンセルフロー
    @Transactional
    public void cancelOrder(Long id) {
        // 1. リポジトリを通じて「生きた」オブジェクトを見つける
        Order order = orderRepository.findById(id);
        // 2. オブジェクトに指示を送る：自分でキャンセルして
        order.cancel(); 
        // 3. 変更後の状態を保存
        orderRepository.save(order);
    }
}

@Repository
public class OrderRepositoryImpl implements OrderRepository {
    @Autowired
    private OrderMapper orderMapper; // MyBatis の Mapper

    @Override
    public void save(Order order) {
        // 1. 変換：ドメインオブジェクト Order を DB テーブルオブジェクト OrderPO に変換
        OrderPO po = convertToPO(order);
        // 2. 永続化：Mapper を呼び出して SQL を実行
        if (po.getId() == null) {
            orderMapper.insert(po);
        } else {
            orderMapper.updateStatus(po);
        }
    }

    @Override
    public Order findById(Long id) {
        OrderPO po = orderMapper.selectById(id);
        // 3. 復元：DB レコードをビジネス能力を持つドメインオブジェクトに戻す
        return convertToEntity(po);
    }
}

@RestController
@RequestMapping("/api/orders")
public class OrderController {
    @Autowired
    private OrderApplicationService orderAppService;

    @PostMapping("/create")
    public Response create(@RequestBody OrderCreateDTO dto) {
        orderAppService.createOrder(dto);
        return Response.ok();
    }

    @PostMapping("/{id}/cancel")
    public Response cancel(@PathVariable Long id) {
        orderAppService.cancelOrder(id);
        return Response.ok();
    }
}
  1. ロジックはどこに？
  • 「キャンセルできるか」の判断ロジックは Order クラス内（ドメイン層）。
  • 「まず取得し、次に変更し、最後に保存」 の手順は OrderApplicationService 内（アプリケーション層）。
  1. 分離はどこに？
  • ApplicationService はデータベースが MySQL かテキストファイルかを全く知らない。なぜなら orderRepository.save() しか呼び出さないから。
  • 実際の SQL 文はすべて Infrastructure 層の Mapper に物理的に隔離されている。
  1. なぜこのように書くのか？
  • 将来「注文キャンセル」のルールが変わった場合（例：支払いから30分以上経過するとキャンセル不可）、Order エンティティクラスの1箇所だけを変更すればよく、他の3層のコードは一切触らなくてよい。これが複雑なビジネスに対応する DDD の威力。

七、まとめ：DDD は何を強化したのか？

  1. 高凝集： 誰のデータは誰が責任を持つ。ビジネスロジックが各 Service に「流出」しなくなる。
  2. 保守性向上： コード構造がそのままビジネスの設計図。ドメインオブジェクトを見ればビジネスルールが分かる。
  3. プラグイン化： データベースと外部サービスがすべて「プラグイン」になり、システムがより堅牢に。

八、結び

DDD は MVC を覆そうとするものではなく、ビジネスがある程度複雑になったときに、開発者に与えられる「メス」であり、絡み合ったロジックを優雅に分解できるようにするものです。

一言でまとめると： MVC はコードを正しい位置に置くことを可能にし、DDD はオブジェクトを「生きた」ものにする。
