Java
简体中文 English 繁體中文

ThreadLocal とは

Java 公式ドキュメントの説明によると：ThreadLocal クラスはスレッド内部のローカル変数を提供するために使用されます。この変数はマルチスレッド環境でアクセス（get および set メソッドでアクセス）される際に、各スレッドの変数が他のスレッド内の変数から相対的に独立していることを保証します。ThreadLocal インスタンスは通常 private static 型であり、スレッドとスレッドコンテキストの関連付けに使用されます。

ThreadLocal の役割は次のとおりです：スレッド内のローカル変数を提供し、異なるスレッド間で相互に干渉せず、この変数はスレッドのライフサイクル内で機能し、同じスレッド内の複数の関数やコンポーネント間での共通変数の受け渡しの複雑さを軽減します。

  • スレッド並行性：マルチスレッド並行のシナリオで
  • データの受け渡し：ThreadLocal を通じて同じスレッド、異なるコンポーネント間で共通変数を受け渡し（Session に少し似ている？）
  • スレッド分離：各スレッドの変数は独立しており、相互に影響しない

基本的な使い方

Thread の使用を紹介する前に、まず ThreadLocal のよく使うメソッドをいくつか理解しましょう。

ThreadLocal と synchronized の違い

ThreadLocal パターンと synchronized キーワードはどちらもマルチスレッドの並行アクセス変数の問題を処理するために使用されますが、両者の問題へのアプローチと考え方は異なります。

synchronized ThreadLocal
原理 同期メカニズムは時間と空間のトレードオフ方式を採用し、1つの変数のみを提供し、異なるスレッドが順番にアクセス ThreadLocal は空間と時間のトレードオフの概念を採用し、各スレッドに変数のコピーを提供し、同時アクセスで相互干渉しない
重点 複数スレッド間のリソースアクセスの同期 マルチスレッドにおいて各スレッド間のデータを相互に隔離

まとめ：先ほどの例では、ThreadLocal と synchronized の両方で問題を解決できますが、ThreadLocal を使用する方が適切です。なぜなら、プログラムの並行性をより高く保てるからです。

利用シーン

上記の紹介を通じて、ThreadLocal の特徴について基本的に理解できました。では具体的にどのようなシーンで使われるのでしょうか？次に事例を見てみましょう：トランザクション操作

振込事例

ここでは簡単な振込シナリオを構築します：account というデータテーブルがあり、その中に jack と Rose という2人のユーザーがいます。ユーザー Jack がユーザー Rose に送金します。事例の実装は主に MySQL データベース、JDBC、C3P0 フレームワークを使用します。

トランザクション開始の注意点：

すべての操作を1つのトランザクション内で行うために、事例で使用する接続は同一でなければなりません。service 層でトランザクションを開始する connection は、dao 層でデータベースにアクセスする connection と一致している必要があります。

スレッド並行の状況では、各スレッドはそれぞれの connection のみを操作できます。つまりスレッド分離です。

従来の解決方法の問題点

  • コードの結合度が高まる（service 層から connection パラメータを渡す必要があるため）
  • プログラムのパフォーマンスが低下する（同期コードブロックを追加すると、並行性が失われる）

このとき ThreadLocal を使って現在のスレッドとバインドすることで、コード間の結合を低減できます。

ThreadLocal 実装の利点

上記の事例から、特定のシナリオでは ThreadLocal ソリューションに2つの顕著な利点があることがわかります：

  • データの受け渡し：各スレッドにバインドされたデータを保存し、必要な場所で直接取得でき、パラメータの直接受け渡しによるコード結合の問題を回避
  • スレッド分離：各スレッド間のデータは相互に隔離されながらも並行性を持ち、同期方式によるパフォーマンス損失を回避

ThreadLocal の内部構造

よくある誤解

ソースコードを見なければ、ThreadLocal は次のように設計されていると推測するかもしれません：各 ThreadLocal が Map を作成し、スレッドを Map の key、保存するローカル変数を Map の value とすることで、各スレッドのローカル変数分離の効果を達成する。これは最もシンプルな設計方法で、JDK の初期の ThreadLocal は確かにこのように設計されていましたが、現在はもう違います。

現在の設計

JDK は後に設計を最適化し、JDK8 での ThreadLocal の設計は：各 Thread が ThreadLocalMap を保持し、この Map の key は ThreadLocal インスタンス自体、value が実際に保存する値 Object です。具体的なプロセスは以下の通りです：

  • 各 Thread スレッドの内部には Map（ThreadLocalMap）がある
  • Map には ThreadLocal オブジェクト（key）とスレッドの変数コピー（value）が格納される
  • Thread 内部の Map は ThreadLocal によって管理され、ThreadLocal が map への値の取得と設定を担当
  • 異なるスレッドでは、コピー値を取得する際に、他のスレッドは現在のスレッドのコピー値を取得できず、コピーの分離が形成され、相互に干渉しない

比較

JDK8 の設計に変わったことの利点：

  • 各 Map に格納される Entry の数が減少。なぜなら、以前の Entry 数は Thread の数で決まっていたが、今は ThreadLocal の数で決まる
    • 実際の開発では、Thread の数は ThreadLocal の数をはるかに上回る
  • Thread が破棄されるとき、ThreadLocalMap もそれに伴って破棄される。ThreadLocal は Thread 内に格納されているため、Thread の破棄とともに消え、オーバーヘッドを低減できる

ThreadLocal コアメソッドのソースコード

内部構造に基づいて、コアメソッドのソースコードを分析します。コンストラクタを除き、ThreadLocal が外部に公開するメソッドは以下の4つです：

メソッド宣言 説明
protected T initialValue() 現在のスレッドローカル変数の初期値を返す
public void set(T value) 現在のスレッドにバインドされたローカル変数を設定
public T get() 現在のスレッドにバインドされたローカル変数を取得
public void remove() 現在のスレッドにバインドされたローカル変数を削除

set メソッド

コードフロー：

  • まず現在のスレッドを取得し、現在のスレッドに基づいて Map を取得
  • 取得した Map が空でなければ、パラメータを Map に設定（現在の ThreadLocal の参照を key として）
  • Map が空であれば、そのスレッドに Map を作成し、初期値を設定

get メソッド

コード実行フロー：

  • まず現在のスレッドを取得し、現在のスレッドに基づいて Map を取得
  • 取得した Map が空でなければ、Map 内で ThreadLocal の参照を key として対応する Entry を取得、そうでなければ4番目のステップへ
  • e が null でなければ e.value を返し、そうでなければ4番目のステップへ
  • Map が空または e が空の場合、initialValue 関数で初期値 value を取得し、ThreadLocal の参照と value で新しい Map を作成

まとめ：まず現在のスレッドの ThreadLocal 変数を取得し、存在すれば値を返し、存在しなければ作成して初期値を返す。

remove メソッド

コード実行フロー：

  • まず現在のスレッドを取得し、現在のスレッドに基づいて Map を取得
  • 取得した Map が空でなければ、現在の ThreadLocal オブジェクトに対応する Entry を削除

initialValue メソッド

このメソッドの役割は、そのスレッドローカル変数の初期値を返すことです。

  • このメソッドは遅延呼び出しメソッドで、上記のコードから、set メソッドがまだ呼ばれておらず先に get メソッドが呼ばれた場合にのみ実行され、1回のみ実行されます。
  • このメソッドのデフォルト実装は直接 null を返します。
  • null 以外の初期値が必要な場合は、このメソッドをオーバーライドできます。（備考：このメソッドは protected メソッドであり、明らかにサブクラスでオーバーライドするために設計されています）

ThreadLocalMap ソースコード分析

ThreadLocal の操作は実際には ThreadLocalMap を中心に展開されています。ThreadLocalMap のソースコードは比較的複雑で、以下の3つの側面から議論します。

基本構造

ThreadLocalMap は ThreadLocal の内部クラスで、Map インターフェースを実装せず、独立した方法で Map の機能を実装しており、その内部の Entry も独立して実装されています。

ThreadLocalMap でも、K-V 構造のデータを保存するために Entry を使用します。ただし Entry の key は ThreadLocal オブジェクトのみ可能で、これはコンストラクタで制限されています。

また、Entry は WeakReference を継承しており、つまり key（ThreadLocal）は弱参照です。その目的は ThreadLocal オブジェクトのライフサイクルとスレッドのライフサイクルを切り離すことです。

弱参照とメモリリーク

ThreadLocal の使用中にメモリリークが発生することがあり、このメモリリークが Entry に弱参照の key を使用していることに関係していると推測する人もいます。この理解は実は正しくありません。

メモリリーク関連の概念

  • Memory overflow（メモリオーバーフロー）：申請者が使用するのに十分なメモリがない状態。
  • Memory leak（メモリリーク）：プログラム内で動的に割り当てられたヒープメモリが、何らかの理由でプログラムによって解放されないか解放できず、システムメモリの浪費を引き起こし、プログラムの実行速度低下やシステムクラッシュなどの深刻な結果をもたらすこと。メモリリークの蓄積は最終的にメモリオーバーフローにつながります。

弱参照関連の概念

Java の参照には4種類あります：強参照、軟参照、弱参照、虚参照。現在の問題は主に強参照と弱参照に関係します：

  • 強参照（“Strong” Reference）：最も一般的な通常のオブジェクト参照で、強参照がオブジェクトを指している限り、そのオブジェクトはまだ「生きている」ことを示し、ガベージコレクタはそのようなオブジェクトを回収しません。
  • 弱参照（WeakReference）：ガベージコレクタは弱参照のみを持つオブジェクトを発見すると、現在のメモリ空間が十分かどうかに関わらず、そのメモリを回収します。

key に強参照を使用するとメモリリークが発生するか？

  • ビジネスコードで ThreadLocal を使い終わり、threadLocal Ref が回収されたと仮定します。
  • しかし threadLocalMap の Entry が threadLocal を強参照しているため、threadLocal は回収できません。
  • この Entry を手動で削除せず、CurrentThread がまだ実行中である限り、強参照チェーン threadRef->currentThread->threadLocalMap->entry が常に存在し、Entry は回収されず（Entry には ThreadLocal インスタンスと value が含まれる）、Entry のメモリリークが発生します。

つまり、ThreadLocalMap の key に強参照を使用しても、メモリリークを完全に回避することはできません。

key に弱参照を使用するとメモリリークが発生するか？

  • 同様にビジネスコードで ThreadLocal を使い終わったと仮定します。
  • ThreadLocalMap は ThreadLocal の弱参照のみを保持しているため、threadlocal インスタンスを指す強参照がなく、threadlocal は正常に gc 回収され、このとき Entry の key=null となります。
  • しかし Entry を手動で削除せず CurrentThread がまだ実行中である限り、強参照チェーン threadRef->currentThread->threadLocalMap->entry->value が存在し、value は回収されず、この value には永遠にアクセスできなくなり、value のメモリリークが発生します。

つまり、ThreadLocalMap の key に弱参照を使用しても、メモリリークの可能性があります。

メモリリークの本当の原因

上記2つの状況を比較すると、メモリリークの発生は ThreadLocalMap の key に弱参照を使用するかどうかとは関係がないことがわかります。メモリリークの本当の原因は何でしょうか？

注意深い人は、上記2つのメモリリークの状況に共通する2つの前提条件に気づくでしょう：

  • この Entry を手動で削除していない
  • CurrentThread がまだ実行中である

1点目はよく理解できます。ThreadLocal を使い終わったら、その remove メソッドを呼び出して対応する Entry を削除すれば、メモリリークを回避できます。

2点目はやや複雑です。ThreadLocalMap は Thread のプロパティであり、現在のスレッドに参照されているため、そのライフサイクルは Thread と同じ長さです。ThreadLocal を使い終わったとき、もし現在の Thread もそれに伴って実行終了すれば、ThreadLocalMap も当然 gc 回収され、根本的にメモリリークを回避できます。

まとめると、ThreadLocal のメモリリークの根源は：ThreadLocalMap のライフサイクルが Thread と同じ長さであり、対応する key を手動で削除しないとメモリリークが発生するということです。

なぜ弱参照を使うのか？

上記の分析から、ThreadLocalMap の key にどの種類の参照を使用してもメモリリークを完全に回避することはできず、弱参照の使用とは関係がないことがわかりました。

メモリリークを回避するには2つの方法があります：

  • ThreadLocal を使い終わったら、その remove メソッドを呼び出して対応する Entry を削除する
  • ThreadLocal を使い終わったら、現在の Thread もそれに伴って実行終了する

2番目の方法は1番目に比べて明らかに制御が難しく、特にスレッドプールを使用する場合、スレッドの終了時に破棄されず、そのままスレッドプールに戻されます。

つまり、ThreadLocal を使い終わったらすぐに remove を呼び出すことを忘れなければ、key が強参照でも弱参照でも問題はありません。ではなぜ key に弱参照を使うのでしょうか？

実際、ThreadLocalMap の set / getEntry メソッドでは、key が null（つまり ThreadLocal が null）かどうかを判断し、null の場合は value も null に設定します。

これは、ThreadLocal を使い終わり CurrentThread がまだ実行中の場合、remove メソッドを呼び忘れても、弱参照は強参照よりも1層多くの保証を提供することを意味します：弱参照の ThreadLocal は回収され、対応する value は次回 ThreadLocalMap が set、get、remove のいずれかのメソッドを呼び出すときにクリアされ、メモリリークを回避します。

ハッシュ衝突の解決

線形探査法による Hash 衝突の解決

この方法は次のアドレスを順に探査し、空きアドレスが見つかるまで挿入します。全空間で空きアドレスが見つからない場合はオーバーフローが発生します。

例：現在の table の長さが16の場合、key の hash 値が14と計算され、table[14] に既に値があり、その key が現在の key と一致しない場合、hash 衝突が発生します。このとき 14+1 で15を得て、table[15] を判断します。このときまだ衝突する場合は0に戻り、table[0] を取得し、挿入できるまで同様に繰り返します。

上記の説明に従えば、Entry table を環状配列と見なすことができます。

ThreadLocal の使用シーン

ソースコードでの使用シーン

ThreadLocal の主な役割はデータ分離です。埋め込まれたデータは現在のスレッドにのみ属し、変数のデータは他のスレッドに対して相対的に隔離されています。マルチスレッド環境で、自分の変数が他のスレッドによって改ざんされるのを防ぎます。

例えば、Spring がトランザクション分離レベルを実装するためのソースコードでは：

Spring は ThreadLocal 方式を採用して、単一スレッド内のデータベース操作が同じデータベース接続を使用することを保証します。同時に、この方式によりビジネス層でトランザクションを使用する際に connection オブジェクトを意識して管理する必要がなく、伝播レベルを通じて複数のトランザクション設定間の切り替え、一時停止、再開を巧みに管理します。

Spring フレームワークでは ThreadLocal を使ってこの分離を実現しており、主に TransactionSynchronizationManager クラスで使用されています。

ユーザー使用シーン1

以前、リリース後に一部のユーザーの日付がおかしくなっていることが判明し、調査の結果 SimpleDateFormat が原因でした。当時 SimpleDateFormat の parse() メソッドを使用しており、内部に Calendar オブジェクトがあります。SimpleDateFormat の parse() メソッドを呼び出すと、まず Calendar.clear() が呼ばれ、次に Calendar.add() が呼ばれます。あるスレッドが先に add() を呼び出し、別のスレッドが clear() を呼び出すと、parse() メソッドが解析する時刻がおかしくなります。

解決策として、スレッドプールに ThreadLocal でラップした SimpleDateFormat を使用し、initialValue を呼び出して各スレッドに SimpleDateFormat のコピーを持たせることで、スレッドセーフの問題を解決し、パフォーマンスも向上させました。

ユーザー使用シーン2

プロジェクト内で、あるスレッドが複数のメソッド呼び出しにまたがって渡す必要があるオブジェクト、つまりコンテキスト（Context）がよくあります。これは状態であり、多くの場合ユーザー ID、タスク情報などです。これには過剰なパラメータ受け渡しの問題が存在します。

各メソッドに context パラメータを追加するのは非常に面倒で、呼び出しチェーンに修正できないサードパーティライブラリがある場合、オブジェクトパラメータを渡せなくなります。そこで ThreadLocal を使って改造し、呼び出し前に ThreadLocal にパラメータを設定し、他の場所では get するだけで済むようにしました。

多くのシーンで cookie、session などのデータ分離は ThreadLocal を通じて実装されています。Android では、Looper クラスが ThreadLocal の特性を利用して、各スレッドに1つの Looper オブジェクトのみが存在することを保証しています。
