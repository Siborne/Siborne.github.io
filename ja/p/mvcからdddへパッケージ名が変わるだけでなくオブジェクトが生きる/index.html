MVCからDDDへ：パッケージ名が変わるだけでなく、「オブジェクト」が生きる

はじめに

DDD（ドメイン駆動設計）を学ぶ際、多くの人は複雑な概念に挫折します。しかし本質に立ち返れば、DDDを**MVCの「進化した強化版」**と理解できます。MVCの上に、より明確な責任分担と論理の疎通化を実現し、業務複雑化後の「ボトルネック」を解決します。

1. 核心哲学：「説明書を探す」から「当事者に聞く」へ

従来の**MVC（アネミックモデル）**では、エンティティクラス（Entity/PO）はしばしばデータのキャリアに過ぎず、白紙のようです。すべてのビジネスロジックがService層に蓄積されます。

  • 課題： Serviceが大きくなり、ロジックが散在し、メンテナンスが糸の束の中から末端を見つけるようなものになります。

**DDD（リッチモデル）**では、データとビジネスロジックが一緒に記述されます。

  • 変化： エンティティクラスが生命を持ち、原則を持つ「ビジネスエキスパート」になります。

  • 例： 「注文キャンセル」ロジック为例。

    • MVC： OrderServiceがOrderデータを取得し、ステータスを判断し、ステータスを変更し、保存。
    • DDD： Orderエンティティ内部にcancel()メソッドがあり、自身でキャンセル可能かどうかを判断。

ポイント： DDDの利点はロジックが高度に凝集することです。ビジネスロジックが変更された場合、対応するドメインモデルオブジェクトを変更するだけで、何千行ものServiceを探す必要はありません。

2. アーキテクチャマッピング：DDDとMVCの対応関係

DDDのフローを簡単に理解すると：

Controller $\rightarrow$ Application Service $\rightarrow$ Domain Model $\rightarrow$ Repository (Impl $\rightarrow$ Mapper)

理解しやすくするために、この比較表を見てみましょう：

レイヤー DDD命名 MVC対応 強化された責任
インターフェース Interfaces Controller プロトコル変換（REST/JSON）のみ担当し、ビジネスロジックはなし。
アプリケーション Application Service（軽量） 指揮官： if-elseロジックはなく、ドメインオブジェクトの動作を調整するのみ。
ドメイン Domain Entity（重厚） コア： ビジネスルールを含み、データとロジックが共存。
インフラストラクチャ Infrastructure DAO / Mapper プラグイン型： データベース詳細を隠蔽。Repositoryはインターフェース、Mapperは実装。

3. なぜDDDのパッケージが増えるのか？（疎通化の真実）

DDDがApplicationService、Domain Model、Repositoryなどを導入していることに気づくでしょう。これは一見煩雑に見えますが、実は2レベルのコア疎通化を実現しています：

1. ビジネスロジックとプロセス調整の疎通化（Application vs Domain）

  • Application層は「最初に何をし、次に何をするか」のみ関心を持つ。
  • Domain層は「このビジネスルールが何か」のみ関心を持つ。
  • 利点： ビジネスロジックが環境から切り離されてユニットテスト可能。データベース起動不要、極めて高速。

2. ビジネスロジックとストレージ技術の疎通化（Domain vs Infrastructure）

  • ドメインモデルはRepositoryインターフェースのみ認識し、底層がMyBatis、JPA、Redisかは関心を持たない。
  • 利点： データベースがMySQLからMongoDBに変更されても、コアビジネスロジック（Domain層）は1文字も変更不要。

4. モデルの3つのメンバー（戦術モデリング）

DDDのドメイン層では、すべてのクラスが同じではありません。ビジネスロジックをより科学的に組織するために、モデルを以下の3カテゴリに分類します：

1. エンティティ（Entity） — ユニーク識別子を持つ

エンティティの最も重要な特徴はアイデンティティです。すべての属性が変更されても、同じオブジェクトです。

  • 定義： ユニーク識別子（ID）を持つオブジェクト。2つの注文が同じ商品と価格を持っていても、IDが異なれば、それらは異なるもの。
  • 特徴： ライフサイクルを持つ（作成、変更、ステータス遷移、アーカイブ）。
  • 例： Order（注文）、User（ユーザー）。

シナリオ： 注文作成時、ステータスは「支払い待ち」、配送先住所は「上海」；支払い後、ステータスは「支払い済み」に変更、住所は「北京」に変更。

コア： ステータスと住所が変更されても、**OrderNo（またはID）**が変更されないため、同じ注文と見なされます。

コード特徴： 内部に必ずprivate Long id;またはprivate String orderNo;があり、ロジック判断時にこのIDでequals()を使用。

2. 値オブジェクト（Value Object） — 属性のみ、IDなし

値オブジェクトは「記述的なテキスト」のようです。2つの値オブジェクトのすべての属性が同じ場合、同じものです。

  • 定義： IDなし、属性で定義。2つのオブジェクトの属性値が完全に同じ場合、相互に置き換え可能。
  • 特徴： イミュータビリティ。住所を変更する場合、元の住所オブジェクトの属性を変更するのではなく、新しい住所オブジェクトに直接置き換え。
  • 例： Address（県市区町村の組み合わせ）、Money（通貨+金額）。

シナリオ： 注文に配送先住所がある：{県: "広東", 市: "深圳", 街道: "南山区"}。

コア： この住所オブジェクトの「身分証」は関心外で、どこに記入されたかのみ関心。2つの注文が同じ場所に配送される場合、2つの住所オブジェクトは論理的に等価。

コード特徴：

  1. IDなし。
  2. イミュータビリティ：住所を変更する場合、address.setStreet("福田区")を呼び出すのではなく、Orderに新しいAddressオブジェクトを直接渡す：order.changeAddress(new Address("広東", "深圳", "福田区"))。
  • コードのコツ：

3. アグリゲートルート（Aggregate Root） — 組織管理者

  • 定義： 関連オブジェクトグループの「ボス」。外部はアグリゲートルートを通じて内部メンバーにアクセス可能。
  • 責任： ビジネスの完全性を維持（不変条件）。
  • 例： 注文ビジネスでは、Orderがアグリゲートルート、OrderItem（注文項目）が内部メンバー。

シナリオ： 1つの注文に3つの商品（注文項目）がある。

コア：

  1. 外部のServiceがOrderを迂回して特定のOrderItemの価格を変更することは不可。
  2. order.adjustItemPrice(itemId, newPrice)を呼び出す必要。Orderとして「ボス」がこの操作が合法かどうかを判断（例：注文がすでに発送された場合、ボスは価格変更を拒否）。

ライフサイクル： アグリゲートルートは内部メンバーの生死に責任。Orderがデータベースから削除されると、内部のOrderItemも一緒に消える必要。

禁止事項： ControllerでOrderItemMapperを直接呼び出して特定の商品の価格を変更することは絶対に不可。Order.updateItemPrice()を通じる必要。

4. まとめ比較

モデルタイプ ユニークIDあり 属性が同じ場合 変更方法 例
エンティティ はい 依然として2つの独立したオブジェクト メソッドで属性を変更 User, Product
値オブジェクト いいえ 同じオブジェクトと見なされる 完全な置き換え（イミュータブル） Money, Address
アグリゲートルート はい （エンティティと同じ） 内部メンバーすべてを調整 Order, Forum Topic

5. モデル変換：各レイヤー独自の「顔」

「疎通化」を実現するために、各レイヤーが使用するモデルは異なります。書き方が面倒でも、データベースロジックがビジネスロジックを汚染するのを効果的に防ぎます：

  1. DTO（Data Transfer Object）： インターフェース層が使用。フォームのように見え、フィールドは少ない場合がある。
  2. Domain Entity： ドメイン層が使用。これは「生きているオブジェクト」で、ビジネスロジックを持つ。
  3. PO（Persistent Object）： インフラストラクチャ層が使用。データベーステーブルと全く同じ見た目。

// エンティティクラス：Order.java
public class Order {// <--- これは【アグリゲートルート】
    private Long orderId;// <--- アグリゲートルートもエンティティで、ユニークIDを持つ
    private List<OrderItem> items;// <--- 注文項目は【エンティティ】だが、アグリゲートルートに管理される
    private OrderStatus status; // CREATED, PAID, CANCELLED, SHIPPED
    private Address address; // <--- 配送先住所は【値オブジェクト】で、IDなし、完全な置き換え
    private BigDecimal totalPrice;

	// アグリゲートルートのメソッド：ビジネスの完全性を確保
    public void changeAddress(Address newAddress) {
        if (this.status == OrderStatus.SHIPPED) {
            throw new BusinessException("発送後は住所を変更できません");
        }
        this.address = newAddress; 
    }

    // --- ビジネスロジック：新規注文の作成制約 ---
    public Order(List<OrderItem> items) {
        if (items == null || items.isEmpty()) {
            throw new BusinessException("注文には少なくとも1つの商品が必要");
        }
        this.items = items;
        this.status = OrderStatus.CREATED;
        this.totalPrice = calculateTotal(); // 内部ロジック、合計金額を自動計算
    }

    // --- ビジネスロジック：注文キャンセル ---
    public void cancel() {
        if (this.status == OrderStatus.SHIPPED) {
            throw new BusinessException("発送済みの注文はキャンセルできません");
        }
        this.status = OrderStatus.CANCELLED;
    }

    private BigDecimal calculateTotal() {
        return items.stream().map(OrderItem::getPrice).reduce(BigDecimal.ZERO, BigDecimal::add);
    }
  
    // Getter省略...
}

// リポジトリインターフェース：OrderRepository.java（ビジネス行動のみ定義）
public interface OrderRepository {
    void save(Order order);
    Order findById(Long id);
}

@Service
public class OrderApplicationService {
    @Autowired
    private OrderRepository orderRepository;

    // 注文作成プロセス
    @Transactional
    public void createOrder(OrderCreateDTO dto) {
        // ドメインモデルを呼び出して作成
        Order order = new Order(dto.getItems());
        // リポジトリを呼び出して永続化
        orderRepository.save(order);
    }

    // 注文キャンセルプロセス
    @Transactional
    public void cancelOrder(Long id) {
        // 1. リポジトリを通じて「生きている」オブジェクトを取得
        Order order = orderRepository.findById(id);
        // 2. オブジェクトにコマンドを送信：自分でキャンセルしてください
        order.cancel(); 
        // 3. 変更されたステータスを保存
        orderRepository.save(order);
    }
}

@Repository
public class OrderRepositoryImpl implements OrderRepository {
    @Autowired
    private OrderMapper orderMapper; // MyBatis Mapper

    @Override
    public void save(Order order) {
        // 1. 変換：ドメインオブジェクトOrderをデータベーステーブルオブジェクトOrderPOに変換
        OrderPO po = convertToPO(order);
        // 2. 永続化：Mapperを呼び出してSQLを実行
        if (po.getId() == null) {
            orderMapper.insert(po);
        } else {
            orderMapper.updateStatus(po);
        }
    }

    @Override
    public Order findById(Long id) {
        OrderPO po = orderMapper.selectById(id);
        // 3. 復元：データベースレコードをビジネス能力を持つドメインオブジェクトに復元
        return convertToEntity(po);
    }
}

@RestController
@RequestMapping("/api/orders")
public class OrderController {
    @Autowired
    private OrderApplicationService orderAppService;

    @PostMapping("/create")
    public Response create(@RequestBody OrderCreateDTO dto) {
        orderAppService.createOrder(dto);
        return Response.ok();
    }

    @PostMapping("/{id}/cancel")
    public Response cancel(@PathVariable Long id) {
        orderAppService.cancelOrder(id);
        return Response.ok();
    }
}
  1. ロジックはどこにある？
  • **「キャンセル可能か」**のロジックはOrderクラス内（ドメイン層）。
  • **「まず検索、次に変更、最後に保存」**のステップはOrderApplicationService内（アプリケーション層）。
  1. 疎通化はどこにある？
  • ApplicationServiceはデータベースがMySQLかテキストファイルかを知らず、orderRepository.save()のみ呼び出す。
  • 実際のSQL文はすべてInfrastructure層のMapperに物理的に分離。
  1. なぜこのように書くのか？
  • 将来「注文キャンセル」のルールが変更された場合（例：支払い後30分以降はキャンセル不可）、Orderエンティティクラスの1箇所のみ変更し、他の3層のコードは変更不要。これがDDDの複雑なビジネスへの対応力。

7. まとめ：DDDは一体何を強化したのか？

  1. 高凝集： 誰のデータ誰が責任を持ち、ビジネスロジックが various Services で「流産」しなくなる。
  2. メンテナンス性： コード構造がビジネスブループリントで、ドメインオブジェクトを見ればビジネスルールがわかる。
  3. プラグイン型： データベースと外部サービスが「プラグイン」となり、システムがより堅牢に。

8. おわりに

DDDはMVCを覆すものではなく、ビジネスが一定の複雑さに達した時、開発者に「メス」を提供し、絡み合ったロジックを優雅に分解できるようにするものです。

一言でまとめると： MVCはコードを正しい場所に置くことを可能にし、DDDはオブジェクトを「生きさせる」ものです。
