Beyond LLM：プロンプトエンジニアリングからマルチエージェントまでの AI Builder 全景ロードマップ

Stanford の Beyond LLM 講座を出発点に、Prompt Engineering、RAG、Fine-Tuning、Agentic Workflow、Multi-Agent の完整技術スタックを体系的に整理し、AI エンジニアリングの全景認知フレームワークを構築します。

コア要点

  • 横軸 vs 縦軸：基盤モデルのアップグレードは OpenAI と Anthropic の仕事；一般開発者は縦軸に注力すべき——エンジニアリング技術で既存 LLM の能力を増強する、いわゆる Augmenting LLM。
  • 単一モデル強化の三本柱：Prompt Engineering（コストゼロ、優先使用）→ RAG（知識補完）→ Fine-Tuning（やむを得ない場合のみ）。
  • モデルからシステムへ：Agentic Workflow は LLM を「質問に答えるモデル」から「実際に動作し、価値を生み出すシステム」へと昇格させる。
  • マインドセットの転換：確定性エンジニアリング思考からファジーエンジニアリング思考へ——あなたは管理者、AI は実行者。
  • 評価は生命線：完成された Evaluation システムなしでは、Agent の本番稼働リスクは制御不能。
  • Multi-Agent の本質：Agent を Tool として呼び出す、API を呼び出すのと同じように。

はじめに：AI Builder のジレンマと縦軸思考

AI 分野をフォローしているなら、この2年間で最もホットな役職は間違いなく AI Engineer と AI Builder でしょう。大規模言語モデルが強力になるほど、这些人の価値は高まります——企業の内部ツール構築や業務プロセス最適化を支援し、多くの人はアイデアを製品化して起業さえしています。

しかし、AI を学びたい人は多いものの、大多数はどこから手をつけるべきか分かりません。市中のリソースは断片すぎるか難解すぎるかで、読んでも何を学んだか、次にどこへ進むべきかが分からないままです。

Stanford には Beyond LLM という講座があり、これが現時点で最も答えに近いものだと考えています。大規模言語モデルの本質から始め、Prompt Engineering、RAG、Fine-Tuning、Agentic Workflow、そして Multi-Agent フレームワークまで一貫して解説します。本記事ではその核心を一記事のボリュームで整理します——読み終えれば、AI のビジネス応用に関する包括的な認知フレームワークが構築されているでしょう。

LLMとは何か？ その限界は？

LLM（Large Language Model、大規模言語モデル） は Transformer アーキテクチャに基づく大規模ニューラルネットワークで、大量のテキストデータによるトレーニングを通じて、次のトークンの確率分布を予測することを学習しました。本質的には、極めて複雑な自己回帰確率予測機です。

LLM が強くなるには2つの道があります：

  • 横軸：より強力な Base Model（基盤モデル） への切り替え、例えば GPT-4 から GPT-5 へのアップグレード。しかし、この道は OpenAI と Anthropic が歩むもので、一般の人々には大規模モデルをトレーニングする能力も資金もありません。
  • 縦軸：既存 LLM に各種エンジニアリング技術を重ねること、すなわち Augmenting LLM（増強型言語モデル）——既存の基盤モデルの上で能力を向上させる方法を考えるのです。

この縦軸こそ、本記事全体の焦点です。

学習のヒント：初心者なら、まずエネルギーの100%を縦軸に投入すべきです。横軸の話——今日 GPT-5 がリリース、明日 Claude 4 が登場——ニュースとして流してください。本当に職場で差別化できる競争力は、他の人が ChatGPT で話すだけなのに、あなたが RAG + Agentic Workflow でカスタマーサービスのチケット処理システムを構築できることです。

Base Model だけしか使えなければ、ビジネスシーンでは必ず壁に当たります。ChatGPT が登場したばかりの頃、ネットワーク機能はなく、ツールを呼び出すこともできず、せいぜい賢いQ&Aボットに過ぎず、実際に何かを成し遂げることはできませんでした。

Stanford の教授は、Base Model の一般的な限界を整理しました：

限界 説明
ドメイン知識の欠如 あなたの会社のデータ、内部ドキュメント、製品仕様を Base Model は一切知らない
情報の遅れ モデルを数ヶ月ごとに再トレーニングすることは不可能；新しい用語、出来事、企業を認識しない
出力の非制御性 LLM の出力は確率的；同じプロンプトを2回実行すると結果が異なる可能性がある。チャットでは問題ないが、本番環境では深刻な后果を引き起こす可能性がある
長コンテキストの劣化 コンテキストが長すぎるとモデルの性能が著しく低下し、「Lost in the Middle」現象が発生する——情報がコンテキスト内にあっても、モデルが見つけられないことがある

キーインサイト：これら4つの限界は独立して存在するのではなく、相互に増幅し合います。例えば「情報の遅れ」が「出力の非制御性」と組み合わさると、モデルが自信満々で古い誤った情報を述べ、あなたには一見して見破れないということです。これらの4つの限界を理解することは、後で学ぶ RAG や Agentic Workflow の根本的な動機となります——各技術は本質的にこれらのうち1つ以上を解決するものです。

AI 製品を作るには、より強力な Base Model に切り替えるだけでは不十分です——縦軸に注力する必要があります。

以下の記事では、前半に単一 LLM を強化する3つのツール：Prompt Engineering、Fine-Tuning、RAG を紹介し、後半はシステム設計に入り、Agentic Workflow、Evaluation 評価方法、そして Multi-Agent を解説します。

二、単一 LLM を強化する3つのツール

Prompt Engineering：すべてのエンジニアの基本スキル

Prompt Engineering（プロンプトエンジニアリング） は、LLM に入力するテキスト指示を設計・最適化し、モデルにより高品質で期待に沿った出力を導く実践です。

Stanford の教授は断言します：「Prompt Engineer」が独立した職業になるとは考えていない——なぜなら、これはすべてのエンジニアが習得すべき基本スキルであり、九九のようなものだからです。

ギザギザのフロンティア、居眠り、そしてケンタウロスの隠喩

トップコンサルティングファーム BCG が行った古典的な実験：コンサルタントを3グループに分け——AI なしグループ、ChatGPT グループ、ChatGPT + プロンプトトレーニンググループ。研究から3つの重要な現象が見出されました：

  1. The Jagged Frontier（ギザギザのフロンティア）：AI はすべてのタスクで優秀なわけではありません。AI によって劇的に効果が上がるタスクもありますが、逆に足を引っ張るタスクもあります。この境界がどこにあるかを明確に知る必要があります。

  2. Falling Asleep at the Wheel（ハンドルで居眠り）：あるタスクが AI の不得手な領域だと気づかず、過度に信頼して出力をそのまま提出すると——AI を使わない場合よりも悪い結果になります。

  3. Centaurs vs Cyborgs（ケンタウロス vs サイボーグ）：

    • Centaur（ケンタウロス）モード：委任型——長いプロンプトを AI に投げてブリーフィング全体を完成させ、自分は他のことをする。反復性が高く、明確なプロセスを持つタスクに最適。
    • Cyborg（サイボーグ）モード：高頻度の往復協働型——モデルと一文ずつ対話する。判断力、創造力、往復の修正が必要なタスクに最適。

重要なのはどちらが優れているかではなく、意識的に切り替えることです。企業の自動化ワークフローでは Centaur モードが、個人の深い協働では Cyborg モードが一般的です。

概念の連結：Centaur モードは本質的に、後述する Agentic Workflow の原形です——タスク全体をシステムに投げると、システム内部で自動的に分解・実行されます。Cyborg モードは日常的に ChatGPT/Claude を使う方法に近いです。Agent システムを構築する際、あなたの役割は Cyborg（自ら往復対話する）から Centaur（プロセスを設計し、システムに自動実行させる）へと移行します。

Prompt Chaining：最も重要で最も過小評価されている技術

多くの人は Prompt Engineering とはフォーマットを整えることだと思っています——誰向けか、どのフォーマットか、重点はどこか。これらはもちろん重要ですが、教授は指摘します：最も一般的で最も重要な技術は Prompt Chaining（プロンプトチェーン呼び出し） であると。

区別に注意：Chain of Thought（CoT、思考の連鎖） はモデルに「step by step」で考えさせる；Chaining は複雑なプロンプトを複数の独立したプロンプトに分割し、前の出力を次の入力として渡すことです。

例——顧客からの苦情に対する返信を書く：

方式 方法 問題
単一プロンプト 「この苦情を読み、専門的な返信を書いて」 ブラックボックス；出力に問題があってもどこを修正すべきか分からない
Chaining（3ステップ） ① 顧客の不満点を抽出 → ② 抽出した問題で草案を作成 → ③ 草案を使って完全な返信を作成 各ステップを独立してテスト・デバッグ可能

Chaining はモデルのパフォーマンスを向上させるだけでなく、Observability（可観測性） も与えてくれます——LLM が何をしているか、どのステップで問題が発生したかを把握できます。

実践的なアドバイス：実際のプロジェクトでは、単一プロンプトではなく Chaining から始めることをお勧めします。最もシンプルな要件でも、まず2-3ステップに分割してみてください——デバッグ効率が少なくとも3倍向上するでしょう。ツールとしては LangChain の LCEL や直接 Python で連鎖させる方法があり、コアロジックは50行以内で書けます。

Fine-Tuning：やむを得ない場合のみ

Fine-Tuning（ファインチューニング） とは、事前学習済みモデルをベースに、特定ドメインのアノテーションデータでモデルパラメータをさらに学習させ、特定タスクでの性能を向上させることです。

Stanford の教授の立場は明確です：やむを得ない場合のみ。理由は4つ：

  1. 大量の高品質アノテーションデータが必要：一般の人にはコストが高すぎる。
  2. オーバーフィットしやすい：特定タスクでは非常に強くなるが、一般的な質問には答えられなくなり、Base Model の持つ汎用性を失う。
  3. 時効性が低い：2ヶ月かけて Fine-Tune してリリースしても、来月には新しい世代の Base Model があなたのバージョンを塗り替える。
  4. Prompt Engineering で通常同じ効果が得られる：コストははるかに低く、プロンプトは Portable（移植可能）——新しい Base Model に切り替えてもプロンプトの大半は使えるが、Fine-Tuning したモデルは使えない。

もちろん、法律、科学など高精度の反復出力が必要なドメイン、あるいは Base Model が特定ドメインで本当に苦戦している少数のシナリオでは Fine-Tuning が有効です。

よくある誤解：「私の業界は専門的だから Fine-Tune が必要」と考える人が多いです。しかし実際には、医療、金融、法律などのほとんどのユースケースでは、RAG + 念入りに設計されたプロンプトで本番グレードの効果が得られます。判断基準はシンプルです：タスクが「新しい能力」（単なる「新しい知識」ではなく）をモデルに学習させる必要がある場合のみ、Fine-Tune が真に必要です。

では、Prompt Engineering では特定ドメインの知識を収められず、Fine-Tuning ではコストパフォーマンスが合わない場合——どうするか？ 答えは RAG です。

RAG：LLM とプライベート知識を接続する標準ソリューション

RAG（Retrieval-Augmented Generation、検索増強生成） は、AI エンジニアの面接で最もよく出題されるテーマの1つです。その核心的なアイデアは：知識をモデルパラメータに詰め込むのではなく、推論時に動的に関連コンテンツを検索し、プロンプトに含めてモデルに参照させることです。

RAG が解決する痛点：

  • Context Window が小さすぎる / 長いコンテキストでの検索精度が低い
  • 情報に時効性がある
  • モデルがハルシネーション（LLM が存在しない事実をでっち上げる現象） を起こしやすい

キーインサイト：ハルシネーションは RAG が解決すべき核心的な問題ですが、注意すべき点があります——RAG はハルシネーションの確率を「下げる」ものであり、「排除」するものではありません。資料をプロンプトに固定しても、モデルは要約や推論時に偏差を生む可能性があります。だからこそ、後述する Evaluation システムが極めて重要なのです：ハルシネーション率を継続的に監視する必要があり、リリース後にすべてがうまくいったと思わないでください。

RAG ワークフロー

高精度が求められる医療シナリオ——薬の副作用の照会を想定します：

  1. ベクトル化と格納：Embedding モデル（埋め込みモデル） を使ってすべてのデータをベクトルに変換し、Vector Database（ベクトルデータベース） に格納します。意味的に類似したテキストは数学的な空間でも距離が近くなります。

  2. クエリのベクトル化：ユーザーの質問「薬Aの副作用」も同じ Embedding モデルでベクトルに変換します。

  3. 意味検索：距離尺度を使ってベクトルデータベースから最も関連性の高いドキュメントチャンクを検索します。注意：これはキーワードマッチングではありません——ドキュメントに「副作用」ではなく「有害反応」と書かれていても、見つけることができます。

  4. プロンプトの組み立て：検索されたドキュメント + System Prompt + ユーザーの質問を最終的なプロンプトに組み立てます。テンプレートはおおよそ以下の通り：

以下の Documents に基づいてユーザーの質問に回答してください。Documents に答えがない場合は「分かりません」と答えてください。

この設計はモデルを提供したデータの範囲内に閉じ込め、自由に發揮させないためです。モデルに回答の出典（何ページ、何章）を付記させ、ユーザーが検証できるようにもできます。

Chunking と多階層検索

薬の説明書は50ページに及ぶ可能性があり、全体をベクトルに変換すると細かい情報が失われます。そのため通常 Chunking（ドキュメント分割） が必要です——ドキュメントを一定サイズのチャンクに分割し、それぞれを個別にベクトル化します。

より高度なアプローチは多階層ストレージです：ドキュメント全体、各章、各段落のベクトルを同時に保持します。検索時にはまず関連する章を見つけ、そこから正確な段落に絞り込みます。

実践的なアドバイス：Chunking は RAG システムで最も過小評価されがちなコンポーネントです。経験則として——Chunk Size は256〜1024トークンに制御し、隣接するチャンク間に10%〜20%のオーバーラップ（Overlap）を設けること。小さすぎると意味が不完全になり、大きすぎると検索精度が低下します。多階層検索（まず章を検索し、次に段落を検索）は50ページ以上のドキュメントで顕著な効果がありますが、複雑さも相应に増します——まず単一レイヤーの Chunking でフルパイプラインを動かしてから、最適化することをお勧めします。

RAG は超長コンテキストウィンドウに淘汰されるのか？

モデルが超長コンテキストウィンドウをサポートし、計算コストが十分安くなれば、Base Model がデータベース全体を直接読み、RAG は不要になると言う人がいます。Stanford 教授の答え：

理論的には正しいが、実際には間違い。

理由は非常に現実的——レイテンシ（遅延） です。質問のたびにモデルが Google Drive 全体を再読するのでは、誰も待ちきれません。検索エンジンが事前に構築したインデックスを使って高速に定位するように、クエリのたびにウェブ全体を再クロールすることは不可能です。

RAG は精度だけでなく、検索効率やリアルタイム更新などの優位性もあり、予見可能な将来においても価値を持ち続けるでしょう。

三、Agentic Workflow：モデルからシステムへ

単一モデルを強化する3つのツールを解説した後、次の大きなセクション——モデルからシステムへ——に入ります。単一の LLM がどれほど強力でも、できることには限界があります。Agentic Workflow は AI を「質問に答えるモデル」から「実際に動作し、価値を生み出すシステム」へと変貌させます。

Agentic Workflow とは何か？

Agentic Workflow（エージェントワークフロー） という用語は Andrew Ng（アンディ・ング） によるものです——Coursera 共同創設者、Google Brain 創設責任者、元百度主席科学者。彼は乱用されがちな「AI Agent」という言葉を意図的に避け、Agentic Workflow で正確に表現します：

一連のプロンプト、外部ツール（Tools）、メモリ（Memory）、および各種コンポーネントを構造化されたワークフローに組み合わせ、システムとして形成する。

RAG は基本的に一つのことを行います：LLM に外部データを参考として提供する。一方、Agent は RAG を多数のツールの1つとして扱い、外部 API の呼び出し、メモリの維持、多段階の意思決定も実行できます。

注文返品の例：

シナリオ RAG ができること Agent ができること
「この注文を返品したい」 返品ポリシードキュメントを渡す RAG でポリシーを検索 → 注文番号を積極的に確認 → ツールで注文を照会 → 返品を確認 → 3〜5営業日で入金と通知

RAG はツールであり、Agent は RAG をツールとして使うシステムです。

学習のヒント：この一文は講座全体で最も重要なメンタルモデルの1つです。この思考習慣を身につけましょう：新しい技術（新しいベクトルデータベース、新しい Agent フレームワークなど）を見るたびに、まず自問する——これは「ツール」か「システム」か？ ツールはパズルの1ピースであり、システムはパズルを組み立てる方法です。大多数の人が行き詰まるのは、ツールを使えないからではなく、それらをどう組み立てるか分からないからです。

エンジニアリングマインドセットの4つの転換

Agentic Workflow を構築するには、エンジニアリングマインドセットが4つのディメンションで転換する必要があります：

ディメンション 従来のソフトウェア Agentic AI ソフトウェア
データ 構造化データ（JSON、データベース、フォーム） 自由テキスト、画像、音声——固定フォーマットなし
ロジック Deterministic（確定的）：同じ入力は常に同じ出力を返す Fuzzy（曖昧）：同じ入力でも異なる出力が生じうる
アーキテクチャマインドセット 各実行パスを正確に制御、マイクロサービスを書くように Think like a manager：AI にゴールと制約を与え、実行方法を任せる
テスト 確定的テスト、100回実行しても結果は同じ 反復探索的テスト、モデルはコンテキストに敏感で全ケースを網羅できない

最初の実装原則が導かれます：

Deterministic で解決できる問題は Deterministic で解決し、残りの Fuzzy な部分にはガードレール（Guardrails）を設ける。

キーインサイト：この原則はより具体的な言葉に翻訳できます——コード内では常に if-else が LLM 呼び出しを包むべきであり、LLM 呼び出しが if-else を包むべきではない。 LLM をシステム内の「曖昧な推論モジュール」として扱い、外側を確定的ロジック（バリデーション、リトライ、フォールバック）で保護します。こうすれば LLM が間違いを犯しても、システムはクラッシュしません。

教授は自身の例を挙げました：スキル評価システムで、選択問題とマッチング問題は確定的に採点します（標準解答がある）；しかし音声+プログラミング混合問題には標準解答がなく、LLM の曖昧な採点に頼るしかありません。そして Fuzzy な採点には必ず誤判定が生じる——そのため、システム内に Appeal Feature（異議申し立て機能） を設計し、受験者が異議を申し立てた場合に人間が介入して審査できるようにしました。

これがガードレールの具体的な形です：AI をゼロエラーにしようとするのではなく、エラー発生時に誰かがキャッチできる体制を作ることです。

実践的なアドバイス：ガードレール設計には3つのレベルがあります——① 入力ガードレール：ユーザー入力が有法かどうかをバリデート；② プロセスガードレール：Agent の各ステップの出力が期待フォーマットに合っているかを監視；③ 出力ガードレール：最終結果が安全な範囲内にあるかどうか。少なくとも①と③を実装し、②は上級最適化です。また、常に Human-in-the-loop（人間の介入） のエスケープハッチを用意してください。

Agent を構築する3つのコア要素

「パリ行きの飛行機を予約して」を例に：

① Prompts（プロンプト）

AI にその役割、できること、できないことをどう伝えるか。

② Context Management（コンテキスト管理）

本質は一つのこと：正しい情報を正しいタイミングで Agent に提供する。以下を含む：

  • Working Memory（ワーキングメモリ）：高頻度、高速アクセスが必要な情報、例えばユーザー名、今回の目的地。
  • Archival Memory（アーカイブメモリ）：低頻度、遅くても良い情報、例えば過去5年の予約記録、必要時に照会。

③ Tools（ツール）

Agent が呼び出せる外部能力、通常は2種類：

  • 実行系：Flight Search、Hotel Booking、Payment
  • 照会系：CRM で顧客データを照会、注文記録を照会

Agent 自律性の3レベル分類

レベル 説明 特徴
Level 1: Hardcoded Steps ステップがすべて固定、順番に実行 安全で予測可能だが、堅い
Level 2: Hardcoded Tools + 自律ステップ Agent にツールセットを与え、実行順序を自主決定させる 現在最も一般的な Production Setup、教授推奨の出発点
Level 3: Fully Autonomous ステップを自ら決定、ツールを自ら作成することさえある 最も能力が高いが、リスクも最大——誤判断が深刻な損失を引き起こす可能性

学習のヒント：初めて Agent を構築するなら、必ず Level 2 から始めてください。Level 1 は堅すぎて、予期しない状況で詰まります；Level 3 は危険すぎて、本番環境では制御不能です。Level 2 のスイートスポットは——あなたが「ツールの範囲」を制御し、Agent が「実行順序」を制御することです。Level 2 に完全に習熟し、Eval システムも構築してから、Level 3 の探索を検討しましょう。

MCP：産業グレードのツール統合標準

MCP（Model Context Protocol、モデルコンテキストプロトコル） は、AI ツールエコシステムの断片化問題を解決するために Anthropic が策定した標準化クライアント-サーバーアーキテクチャです。

従来のアプローチ：各 API に対して個別に統合ロジックを書き、LLM に各 API の使い方とパラメータを手動で教える必要がありました。

MCP のアプローチ：間にプロトコル層を置く——Agent は各 API を知る必要がなく、MCP Server と通信するだけで、MCP Server がバックエンドサービスとの仲介を担います。

MCP をユニバーサル USB-C コネクタとして想像できます：以前は各国のコンセント規格が異なり、アダプターを山ほど持ち歩く必要がありました；MCP があれば、1つ刺すだけで全部つながります。

キーインサイト：2024年末のリリース後、MCP は急速に業界標準となりました。2026年半ばの現在、主要な AI ツール（Claude Desktop、Cursor、Continue など）がすべて MCP をネイティブサポートしています。这意味着、MCP Server を1つ書けば（例えば会社の Jira に接続するサーバー）、MCP 対応のすべての AI アプリケーションから直接呼び出すことができます。さらに、MCP は Agent-to-Agent Communication も自然にサポートします——詳細は Multi-Agent セクションで展開します。

四、Evaluation：本番システムの生命線

単一 Agent でも Multi-Agent でも、デプロイ前に同じ質問に答えなければなりません：本当に機能しているとどうやって分かるのか？

答えは Evaluation（評価システム）——Production グレードの Agentic システムの生命線です。

3次元評価フレームワーク

Stanford 教授は、3つのディメンションを交差使用する完全な評価フレームワークを提示しました：

ディメンション1：End-to-End（エンドツーエンド）vs Component-based（コンポーネントレベル）

  • End-to-End は全体を見る：ユーザーは使用後に何点を付けたか？ 満足しているか？
  • Component-based は分解して見る：このツールはメール更新を忘れなかったか？ 送信ステップのフォーマットは正しかったか？
  • 全体だけ見るとどこが壊れているかは分かるがなぜ壊れているかは分からない；コンポーネントだけ見ると細部は修正できるが全体的な体験は依然として悪いかもしれません。実務上は両方ともやるべきです。

ディメンション2：Objective（客観的）vs Subjective（主観的）

  • Objective は自動検証可能：ユーザーが Order ID は X と言うが、LLM がデータベースに Y を書き込んだ——Python スクリプトで自動比較できます。
  • Subjective には標準解答がありません：トーンは良いか？ 回答に共感はあるか？ これは人間の採点か、別の LLM を審査員として使う必要があります。

ディメンション3：Quantitative（定量的）vs Qualitative（定性的）

  • Quantitative は数値：住所変更の成功率は何%か？ 各ステップのレイテンシは？
  • Qualitative は感覚：どこでハルシネーションが発生したか？ トーンはどこがおかしかったか？ ユーザーはどのステップで詰まったか？ これは人間が1件ずつ確認するしかなく、近道はありません。

実践的なアドバイス：Eval システムの初期構築時、最も犯しやすいミスは、いきなり8つの交差セルすべてをカバーしようとすることです。推奨される優先順位：① Component × Objective（各ステップの正確さを自動検証）→ ② End-to-End × Quantitative（コア指標を追跡）→ ③ End-to-End × Subjective（定期的な人間サンプリング）。最初の2つは CI/CD で自動実行でき、3つ目は毎週20件を確認します。LLM-as-Judge などのより高度な手法は、システムに十分な自信が出てから導入しましょう。

LLM-as-Judge：AI で AI を評価する

Subjective Evaluation に対する一般的なアプローチは LLM-as-Judge（LLM を審査員として使う）——追加の LLM を使って採点する方法です。4つの主流設計：

  1. Pairwise Comparison（ペアワイズ比較）：Judge に2つの回答を与え、どちらが良いかを問う
  2. Single-answer Grading（単一回答採点）：直接1-5点を付ける
  3. Reference-guided Pairwise（参考ガイド付きペアワイズ比較）：標準解答を参照として追加
  4. Rubric-based（ルーブリックベース）：独自の採点基準を定義、例えば「5点=100字以内、3つのポイント含む、最初の文は要約；0点=的外れ、冗長で焦点がぼやけている」

これら4つは混在させることができます。例えば Rubric-based + Few-shot Examples で、審査員に何を求めるかをより明確にします。

よくある誤解：LLM-as-Judge の最大の罠は「同じモデルで自分自身を評価する」ことです——例えば GPT-4 で GPT-4 の出力を評価すると、Self-bias（自己偏好）が生じ、スコアが水膨れしやすいです。ベストプラクティスは異なるファミリーのモデルを Judge として使うこと（例えば Claude で GPT の出力を評価する）、あるいは少なくとも同じファミリーの異なるバージョンを使うことです。また、Judge のルーブリックは非常に具体的に書く必要があります；曖昧なルーブリックが生み出すスコアには参照価値がありません。

実践：Travel Agent の「礼儀正しさ」を例に

教授は Travel Agent の礼儀正しさ評価で、完全な4ステッププロセスをデモンストレーションしました：

ステップ 内容 省略できない理由
Step 1: Error Analysis 1000件のユーザー会話から20件を抽出し、人間が1件ずつ読む 問題がどんな見た目かをまず知らなければ、正しい評価を設計できない
Step 2: Design Eval LLM-as-Judge + 礼儀正しさルーブリックを使用 Step 1 で発見した問題を採点基準に翻訳する
Step 3: A/B Test (モデル) プロンプトを固定し、基盤モデルを差し替え、同じ会話を実行、Judge が採点 どのモデルの礼儀正しさが高いかを見る
Step 4: A/B Test (プロンプト) モデルを固定し、プロンプトの表現を変更、1語の差がどれほど影響するかを見る 些細なプロンプトの変更が顕著な差をもたらす可能性がある

核心原則：まず人間が問題を洗い出し、次に自動化評価を設計する；モデルとプロンプトという2つの変数は1回に1つだけ変更する。

学習のヒント：この「A/B Test では1回に1つの変数だけ変える」という原則はシンプルに聞こえますが、実際の実行では簡単に違反してしまいます。よくあるミスは：「Claude モデルに切り替え + 同時にプロンプトも最適化」——結果は改善したが、モデルの功績なのかプロンプトの功績なのか分からない。習慣をつけましょう：各実験で1つだけ変更し、実験ログに記録する。

五、ケーススタディ：カスタマーサービス AI Agent の構築

教授は完全なハンズオンケースを提供しました——「注文住所変更」リクエストを処理するカスタマーサービス Agent の構築。ユースケース：

ユーザーが言う：「注文 A127 の住所を変更したい。建国南路に引っ越したので。」

Step 1: Task Decomposition（タスク分解）

Agentic Workflow を構築する最初のステップはコーディングではなく、まずカスタマーサービスの担当者の横に1-2日座り、実際に这类リクエストをどう処理しているかを観察することです。人間のワークフローを理解した後、Task Decomposition——大きなタスクを小さなタスクに分解します。

観察の結果、カスタマーサービスは実際には5つのステップを踏んでいました：

① キー情報を抽出（Intent、Order ID、新しい住所）
  → ② データベースで顧客記録を照会

Step 2: 各ステップにツールを選択

ステップ ツール選択 理由
① 情報抽出 LLM 単一 API 呼び出し 純粋なテキスト理解、外部ツール不要
② DB照会/変更 Custom Tool または MCP Server 外部システムとのインタラクションが必要
③ ポリシーチェック RAG ポリシードキュメントは更新される、効率的な検索が必要
④ 返信起草 LLM 前のステップの情報を統合して自然言語を生成
⑤ メール送信 Email Tool 外部メールサービスを呼び出す

判断方法はシンプルです：まず各ステップが Fuzzy か Deterministic かを自問し、どのツールを使うかを決定する。

これが AI Builder が実際にやっている仕事です——各ツールと技術の限界を知り、必要なソリューションを組み立てること。

概念の連結：前述の3レベル分類を振り返ると——ここで構築したカスタマーサービス Agent は典型的な Level 2 です：ツールの範囲は固定（5つのステップにそれぞれ明確なツールがある）ですが、実行順序は入力に基づいて Agent が動的に決定します。

Step 3: Build Evals

前述の3次元フレームワークすべてを適用：

  • End-to-End：最終回答の正確さ、トーン、ユーザー満足度
  • Component-based：情報抽出精度、API エラー率、ポリシー遵守率
  • Objective：Order ID の正確さ、返品ポリシー違反を自動検証
  • Subjective：人間 + LLM-as-Judge で返信の礼儀正しさ、共感を評価
  • Quantitative：住所変更成功率、レイテンシ、返品正確率
  • Qualitative：どこでハルシネーションが発生？ トーンの一貫性は？ ユーザーはどのステップで混乱？

学習のヒント：初めて AI プロジェクトに取り組むなら、超シンプルなバージョンから始めましょう——3-5ステップの小さなタスクを選び、RAG も Multi-Agent も使わず、Prompt Chaining だけで Level 1 Agent を構築し、Objective Eval だけの評価システムを追加します。動かしてから反復的に RAG、ツールを追加し、Level 2 にアップグレードします。まず動かしてから最適化、シンプルさから複雑さへ——これが AI Builder の最も重要なエンジニアリング規律です。

六、Multi-Agent：Agent をツールとして扱う

なぜ Multi-Agent が必要なのか？

単一の Agent はすでにステップ分解、ツール呼び出し、RAG、メール作成ができます——一見十分です。Multi-Agent が存在する主な理由は2つ：

理由 説明
並列処理（Parallel Processing） 飛行機を予約する際、フライト検索、ホテル検索、天気確認——3つのことは完全可以に同時に行えます。単一 Agent は直列にしか動作できませんが、Multi-Agent なら3つの Specialized Agent が同時に実行可能
再利用性（Reusability） 会社の Design Agent はマーケティングチームにもプロダクトチームにも使える

しかし設計原則は：単一 Agent で解決できる問題に無理に Multi-Agent を使うと、複雑さが増すだけです。シンプルにできればシンプルに、過度な設計をしないこと。

よくある誤解：多くのチームが最初から「Multi-Agent システムを作りたい」と言い、単一 Agent では「高度じゃない」と考えます。しかし実際には、Multi-Agent は3つの追加コストをもたらします——① Agent 間の通信オーバーヘッドとレイテンシ、② 複数の System Prompt のメンテナンス負担、③ デバッグ時に複数の Agent ログを遡る必要がある。ビジネスが以下の2つの条件のうち1つを満たす場合にのみ、Multi-Agent が価値があります：a) タスクが2つ以上の独立した並列サブタスクに明確に分割できる；b) 異なるサブタスクが要求するコア能力が大きく異なり、単一 Agent のプロンプトが膨張しすぎる。

スマートホーム Multi-Agent の例

教授はスマートホームをブラインストーミングの例として使用しました。完全なスマートホーム Multi-Agent システムには以下が含まれる可能性があります：

  • 温度制御 Agent
  • 照明 Agent
  • セキュリティ Agent
  • エンターテインメント Agent
  • 通知 Agent
  • エネルギー管理 Agent
  • そして統括する Orchestrator（オーケストレーター）

2つのインタラクションパターン：

パターン 動作方式 適用シーン
Hierarchical（階層型） ユーザーは Orchestrator だけと話し、下位 Agent にタスクを委任 ユーザーサイド——「出かけるよ」、Orchestrator が照明、セキュリティ、温度制御を自動調整
Flat（フラット型） Agent 間で直接通信、中間者なし バックエンド——温度制御 Agent とエネルギー管理 Agent が直接通信し、毎回 Orchestrator を通るコストを省略

Agent 間が相互に通信する際——本質的には MCP Protocol です。Agent をツールとして扱う、API をツールとして扱うのと同じです。 各 Agent は Tool-like なインターフェースを外部に公開し、他の Agent はツールを呼び出すようにそれを呼び出します。

このマインドセットを一度理解すれば、Multi-Agent はもう神秘的ではありません——あなたがすでに理解しているものの上に、もう1層を重ねるだけです。

七、まとめ：あなたの AI 学習全景ロードマップ

本記事は基盤モデルの限界から出発し、LLM の能力を増強するための完整な技術スタックを層ごとに展開しました：

レベル 技術 コア要点
L1 Prompt Engineering 最も低コスト、優先使用。Chaining と Testing に重点を置き、すべてのエンジニアの基本スキル
L2 Fine-Tuning 法律、科学などの高精度ドメインを扱わない限り、または興味がなければ、安易に手を出さないこと。コストが高い、時効性が低い、Prompt Engineering で通常十分
L3 RAG モデルの知識を補完する標準ソリューション。AI 製品を作るならほぼ必ず遭遇する——Embedding → Vector DB → Retrieval → Generation
L4 Agentic Workflow 単一モデルの強化からシステム設計へ。核心はマインドセットの転換：Deterministic Engineering から Fuzzy Engineering へ、Task Decomposition、Evaluation システムの構築
L5 Multi-Agent Agent をツールとして扱い、相互協働。速度（並列化）と再利用性を向上。ただし覚えておこう：シンプルにできるなら複雑にしない

この認知フレームワークがあれば、盲目的に流行を追うことはなくなります——他の人が Multi-Agent を作るからといって真似をし、他の人が Fine-Tuning を語るからといってかっこいいと思うのではなく、実装から出発しましょう：日常生活や仕事の痛点を確認し、その痛点からソリューションを考えます。このプロセスの中で、自然にどの技術を学ぶ必要があるかが見えてきて、学習ルートを効率的に計画できるでしょう。

次のアクション：今日から始めたいなら、ここに「最小実行可能パス」があります——① 仕事での反復的なテキストタスクを見つける（週報作成、FAQ 返信など）；② Prompt Chaining で2-3ステップに分割し、チェーンとして動かす；③ 出力フォーマットを自動検証する Objective Test Case を数個書く；④ 1週間実行して効果を確認し、良い点と悪い点を記録する。この4ステップを完了すれば、あなたはすでに実践の中で成長する AI Builder です。
