从 MVC 到 DDD：不仅仅是包名变了，而是“对象”活了

引言

在学习 DDD（领域驱动设计）时，很多人会被复杂的概念劝退。但回归本质，我们可以将 DDD 理解为 MVC 的“超进化增强版”。它在 MVC 的基础上，通过更清晰的职责划分和逻辑解耦，解决了系统在业务复杂后的“臃肿”痛点。

一、 核心心法：从“找说明书”到“问当事人”

在传统的 MVC（贫血模型） 中，实体类（Entity/PO）往往只是数据的载体，像是一张白纸。所有的业务逻辑都堆积在 Service 层。

  • 痛点： Service 越来越大，逻辑散乱，维护起来像是在一坨乱麻中找线头。

在 DDD（充血模型） 中，数据和业务逻辑是写在一起的。

  • 转变： 实体类变成了有生命、有原则的“业务专家”。

  • 例子： 比如“订单取消”逻辑。

    • MVC： OrderService 获取 Order 数据，判断状态，修改状态，存盘。
    • DDD： Order 实体内部有一个 cancel() 方法，它自己判断能不能取消。

要点： DDD 的好处是逻辑高度内聚。一旦业务逻辑有变化，你只需要修改对应的领域模型对象，而不是去翻几千行的 Service。

二、 架构连连看：DDD 与 MVC 的映射关系

我们可以把 DDD 的流程简单理解为：

Controller $\rightarrow$ Application Service $\rightarrow$ Domain Model $\rightarrow$ Repository (Impl $\rightarrow$ Mapper)

为了方便理解，我们可以看这张对比表：

层次 DDD 命名 MVC 对应 职责增强点
接口层 Interfaces Controller 仅负责协议转换（REST/JSON），不做任何业务。
应用层 Application Service (轻) 指挥官： 不写 if-else，只负责编排领域对象干活。
领域层 Domain Entity (重) 核心： 包含业务规则，数据与逻辑共存。
基础层 Infrastructure DAO / Mapper 插件化： 屏蔽数据库细节。Repository 是接口，Mapper 是实现。

三、 为什么 DDD 的包变多了？（关于解耦的真相）

你会发现 DDD 引入了 ApplicationService、Domain Model、Repository 等。这看似繁琐，实则是为了实现两级核心解耦：

1. 业务逻辑与流程编排解耦 (Application vs Domain)

  • Application 层只关心“第一步做什么，第二步做什么”。
  • Domain 层只关心“这个业务规则是什么”。
  • 收益： 业务逻辑可以脱离环境进行单元测试，不需要启动数据库，速度极快。

2. 业务逻辑与存储技术解耦 (Domain vs Infrastructure)

  • 领域模型只认 Repository 接口，不关心底层是 MyBatis、JPA 还是 Redis。
  • 收益： 就算数据库从 MySQL 换成 MongoDB，你的核心业务逻辑（Domain 层）一个字都不用改。

四、 模型的三大成员（战术建模）

在 DDD 的领域层中，并不是所有的类都是一样的。为了让业务逻辑组织得更科学，我们通常将模型分为以下三类：

1. 实体 (Entity) —— 有唯一标识

实体最核心的特征是身份（Identity）。即使它的所有属性都变了，它依然是那个对象。

  • 定义： 具有唯一标识（ID）的对象。即使两个订单的商品、价格完全一样，只要 ID 不同，它们就是两个不同的东西。
  • 特点： 有生命周期（创建、修改、状态流转、存档）。
  • 例子： Order（订单）、User（用户）。

情景： 订单创建时，状态是“待支付”，收货地址是“上海”；支付后，状态变成了“已支付”，地址改成了“北京”。

核心： 虽然状态和地址都变了，但由于它的 OrderNo (或 ID) 没变，我们依然认为它是同一个订单。

代码特征： 内部一定有一个 private Long id; 或 private String orderNo;，且逻辑判断时使用这个 ID 进行 equals()。

2. 值对象 (Value Object) —— 只有属性，没有 ID

值对象就像是“描述性的文字”。如果两个值对象的所有属性都一样，那它们就是同一个东西。

  • 定义： 没有 ID，通过属性来定义。如果两个对象的属性值完全相同，它们就可以互相替换。
  • 特点： 不可变性 (Immutable)。如果你要改一个地址，不是改原地址对象的属性，而是直接换一个新的地址对象。
  • 例子： Address（省市区街道组合）、Money（币种+金额）。

情景： 订单里有一个收货地址：{省: "广东", 市: "深圳", 街道: "南山区"}。

核心： 我们并不关心这个地址对象的“身份证”，我们只关心它填的是哪。如果两个订单都发往这个地方，那这两个地址对象在逻辑上是等价的。

代码特征：

  1. 没有 ID。
  2. 不可变性 (Immutable)：如果你想改地址，不是调用 address.setStreet("福田区")，而是直接给 Order 换一个新的 Address 对象：order.changeAddress(new Address("广东", "深圳", "福田区"))。
  • 代码小技巧：

3. 聚合根 (Aggregate Root) —— 组织管理者

  • 定义： 一组关联对象的“大老板”。外部只能通过聚合根来访问它内部的成员。
  • 职责： 维护业务完整性（不变量）。
  • 例子： 在订单业务中，Order 是聚合根，OrderItem（订单项）是它内部的成员。

情景： 一个订单里有 3 个商品（订单项）。

核心：

  1. 外面的 Service 不能直接绕过 Order 去修改某个 OrderItem 的价格。
  2. 必须调用 order.adjustItemPrice(itemId, newPrice)。由 Order 这个“大老板”来决定这个操作合不合法（比如：订单如果已发货，老板就会拒绝修改价格）。

生命周期： 聚合根负责其内部成员的生死。如果 Order 从数据库里被删除了，它内部的 OrderItem 必须跟着一起消失。

禁令： 你绝对不能在 Controller 里直接调用 OrderItemMapper 去改某一行商品的价格，必须通过 Order.updateItemPrice()。

4. 总结对比

模型类型 是否有唯一 ID 属性完全相同时 修改方式 举例
实体 (Entity) 是 依然是两个独立的对象 通过方法修改属性 用户(User)、商品(Product)
值对象 (VO) 否 视为同一个对象 整体替换（不可变） 货币(Money)、地址(Address)
聚合根 (AR) 是 (同实体) 负责协调内部所有成员 订单(Order)、论坛主题(Topic)

五、 模型转换：每一层都有自己的“脸”

为了实现“解耦”，每一层使用的模型其实是不一样的。虽然写起来麻烦，但能有效防止数据库逻辑污染业务逻辑：

  1. DTO (Data Transfer Object): 接口层使用。长得像表单，字段可能很少。
  2. Domain Entity: 领域层使用。这是你写的那个“活的对象”，带业务逻辑。
  3. PO (Persistent Object): 基础设施层使用。长得和数据库表一模一样。

// 实体类：Order.java
public class Order {// <--- 这是一个【聚合根】
    private Long orderId;// <--- 聚合根也是实体，有唯一 ID
    private List<OrderItem> items;// <--- 订单项是【实体】，但受聚合根管理
    private OrderStatus status; // CREATED, PAID, CANCELLED, SHIPPED
    private Address address; // <--- 收货地址是【值对象】，没有 ID，整体替换
    private BigDecimal totalPrice;

	// 聚合根的方法：确保业务完整性
    public void changeAddress(Address newAddress) {
        if (this.status == OrderStatus.SHIPPED) {
            throw new BusinessException("发货后不能改地址");
        }
        this.address = newAddress; 
    }

    // --- 业务逻辑：新增订单的构造约束 ---
    public Order(List<OrderItem> items) {
        if (items == null || items.isEmpty()) {
            throw new BusinessException("订单至少需要一个商品");
        }
        this.items = items;
        this.status = OrderStatus.CREATED;
        this.totalPrice = calculateTotal(); // 内部逻辑，自动计算总价
    }

    // --- 业务逻辑：取消订单 ---
    public void cancel() {
        if (this.status == OrderStatus.SHIPPED) {
            throw new BusinessException("已发货订单无法取消");
        }
        this.status = OrderStatus.CANCELLED;
    }

    private BigDecimal calculateTotal() {
        return items.stream().map(OrderItem::getPrice).reduce(BigDecimal.ZERO, BigDecimal::add);
    }
  
    // 省略 Getter...
}

// 仓库接口：OrderRepository.java (只定义业务行为)
public interface OrderRepository {
    void save(Order order);
    Order findById(Long id);
}

@Service
public class OrderApplicationService {
    @Autowired
    private OrderRepository orderRepository;

    // 新增订单流程
    @Transactional
    public void createOrder(OrderCreateDTO dto) {
        // 调用领域模型进行创建
        Order order = new Order(dto.getItems());
        // 调用仓库进行持久化
        orderRepository.save(order);
    }

    // 取消订单流程
    @Transactional
    public void cancelOrder(Long id) {
        // 1. 通过仓库找到那个“活的”对象
        Order order = orderRepository.findById(id);
        // 2. 发送指令给对象：你自己取消吧
        order.cancel(); 
        // 3. 保存修改后的状态
        orderRepository.save(order);
    }
}

@Repository
public class OrderRepositoryImpl implements OrderRepository {
    @Autowired
    private OrderMapper orderMapper; // MyBatis 的 Mapper

    @Override
    public void save(Order order) {
        // 1. 转换：把领域对象 Order 转成 数据库表对象 OrderPO
        OrderPO po = convertToPO(order);
        // 2. 落地：调用 Mapper 执行 SQL
        if (po.getId() == null) {
            orderMapper.insert(po);
        } else {
            orderMapper.updateStatus(po);
        }
    }

    @Override
    public Order findById(Long id) {
        OrderPO po = orderMapper.selectById(id);
        // 3. 还原：把数据库记录转回成带有业务能力的领域对象
        return convertToEntity(po);
    }
}

@RestController
@RequestMapping("/api/orders")
public class OrderController {
    @Autowired
    private OrderApplicationService orderAppService;

    @PostMapping("/create")
    public Response create(@RequestBody OrderCreateDTO dto) {
        orderAppService.createOrder(dto);
        return Response.ok();
    }

    @PostMapping("/{id}/cancel")
    public Response cancel(@PathVariable Long id) {
        orderAppService.cancelOrder(id);
        return Response.ok();
    }
}
  1. 逻辑在哪里？
  • 判断“能否取消” 的逻辑在 Order 类里（领域层）。
  • “先查出来、再改、再存” 的步骤在 OrderApplicationService 里（应用层）。
  1. 解耦在哪里？
  • ApplicationService 根本不知道数据库是 MySQL 还是文本文件，因为它只调用了 orderRepository.save()。
  • 真正的 SQL 语句全被物理隔离在 Infrastructure 层的 Mapper 中。
  1. 为什么这么写？
  • 如果未来“取消订单”的规则变了（比如支付超过30分钟不能取消），你只需要改 Order 实体类一个地方，其他三层代码动都不用动。这就是 DDD 应对复杂业务的威力。

七、总结：DDD 到底增强了什么？

  1. 高内聚： 谁的数据谁负责，业务逻辑不再“流产”在各个 Service 里。
  2. 易维护： 代码结构即业务蓝图，看一眼领域对象就知道业务规则。
  3. 插件化： 数据库和外部服务都变成了“插件”，系统更健壮。

八、结语

DDD 并不是要推翻 MVC，而是在业务复杂到一定程度时，给开发者的一把“手术刀”，让我们能把纠缠在一起的逻辑优雅地拆解开。

一句话总结： MVC 让我们把代码放对位置，而 DDD 让我们让对象“活”了过来。
