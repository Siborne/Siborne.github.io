克隆大型仓库时遭遇 HTTP/2 流中断、SSL 连接重置？本文从排查过程到原理剖析，最终通过 SSH 协议替代 HTTPS 一劳永逸解决 Git 大仓库克隆的网络传输问题。

Computer Tools
English 繁體中文 日本語

1. 问题背景

在尝试克隆大型开源项目 taichi-project/anyagent 时，终端频繁出现由于网络层断开导致克隆失败的报错。

初始报错迹象：执行基础 git clone 时，数据拉取到一半突然中断：

error: RPC failed; curl 92 HTTP/2 stream 7 was not closed cleanly: CANCEL (err 8) fatal: early EOF

问题实质：这是典型的 Git 网络传输中断现象。目标仓库体积较大（或包含较多历史记录），通过当前网络代理环境（v2rayN）拉取时，HTTP/2 数据流被意外强行掐断。

2. 尝试过的解决方案

2.1 浅克隆（浅克隆（失败）

执行 git clone --depth 1 https://... 试图减少下载体积。

结果：对象数确实减少了，但依然在中途断开，报错演变为：

curl 56 OpenSSL SSL_read: SSL_ERROR_SYSCALL, errno 0

分析：这说明不仅仅是文件大小问题，底层 HTTPS 连接在数据传输中途被防火墙或代理软件的 SSL 机制物理切断了。

2.2 配置本地代理环境（部分有效）

查阅本地 v2rayN 代理配置，发现混合端口为 10808。尝试在 PowerShell 中注入临时环境变量 $env:HTTP_PROXY，或考虑开启 Tun 模式接管全局流量。

此方案虽然触及了网络连通性的根本，但 HTTP 代理在面对极大数据流的持续传输时依然不稳定，且代理规则容易与系统级网络配置发生冲突。

3. 原理剖析：HTTP(S) 与 SSH 的差异

HTTP/HTTPS 协议

  • 运作机制：依赖标准 Web 端口（80/443），数据传输受制于本机网络代理规则（PAC、系统代理或命令行环境变量）。
  • 优点：门槛极低，任何人拿到 URL 就能直接下载公开仓库。
  • 缺点：对网络环境极为敏感。经过复杂代理节点时，极易受到中间人证书替换（引发 SSL 解析错误）或大流量缓存溢出的影响，导致连接重置。

SSH 协议

  • 运作机制：运行在独立的 TCP 22 端口，采用非对称加密（公钥+私钥）机制。本机私钥与 GitHub 服务器上的公钥配对成功后，建立端到端加密隧道。
  • 优点：极其稳定且安全，直接穿透或绕过绝大多数针对 HTTP 的应用层代理和审查机制，免疫 curl 相关的网络阻断。
  • 缺点：配置门槛较高，需事先生成密钥对并在平台完成身份绑定，且与物理设备强绑定。

4. 为什么 HTTP 失败，而 SSH 成功？

结合本次排错过程，根本原因在于代理软件对不同协议数据流的处理机制差异：

  1. HTTPS 被代理"夹断"：使用 HTTPS 克隆时，流量被强制引导至代理软件的 10808 端口。代理节点在处理持续不断的大型 Git 对象流时，可能触发了超时丢弃机制，或本地 OpenSSL 与代理服务器之间的证书验证出现瞬间断层，导致系统强制 SYSCALL 中断。
  2. SSH 的"免检通行"：切换到 SSH 协议后，终端不再使用系统 HTTP 代理路由，而是直接通过 22 端口向远端发起握手。密钥的硬性背书使这条加密隧道足够底层且坚固，不再受上层 Web 代理规则干扰，从而保障大数据量的完整传输。

5. 最终方案：SSH 完整配置步骤

适用于 Windows PowerShell。

5.1 生成本机 SSH 密钥 

1

ssh-keygen -t ed25519 -C "你的邮箱@example.com"
  • 按回车接受默认保存路径（~/.ssh/id_ed25519）
  • 提示输入密码时，直接按两次回车留空，后续拉取代码无需额外输密码。

5.2 复制公钥内容 

1

Get-Content ~/.ssh/id_ed25519.pub | Set-Clipboard

如果使用默认 RSA 加密而非 ed25519，则文件是 ~/.ssh/id_rsa.pub。

5.3 绑定公钥到 GitHub

  1. 浏览器登录 GitHub，点击右上角头像 → Settings
  2. 左侧菜单选择 SSH and GPG keys
  3. 点击 New SSH key
  4. Title：随便填写，例如 “My Windows PC”
  5. Key type：保持默认 “Authentication Key”
  6. Key：粘贴刚才复制的公钥内容（以 ssh-ed25519 或 ssh-rsa 开头）
  7. 点击 Add SSH key 保存

5.4 测试连接 

1

ssh -T git@github.com

第一次连接时，会提示 Are you sure you want to continue connecting?，务必手动输入 yes。成功后显示类似 Hi your_username! You've successfully authenticated...。

5.5 重新克隆 

1

git clone git@github.com:taichi-project/anyagent.git

5.6 优缺点与最佳实践

优点：一劳永逸的安全与稳定。配置完成后，你和 GitHub 之间建立了一条完全加密且免密的直连通道，彻底免疫 HTTP/HTTPS 协议下的代理端口冲突、SSL 证书劫持、以及大文件传输时频繁出现的连接重置错误。

缺点：前置门槛较高。对于新手而言，理解公私钥非对称加密并在命令行中完成生成、复制、绑定这套流程容易出错（例如少复制字符、忘记输入 yes）。并且与设备强绑定，换电脑或重装系统后需要重新配置。

最佳实践：在日常开发中，强烈建议将 SSH 作为 Git 交互的默认协议。对自己长期维护或频繁 push/pull 的仓库，一律使用 SSH 直连；仅在需要临时下载一次性代码、对稳定性要求不高时，才使用 HTTPS 配合浏览器或终端代理。
