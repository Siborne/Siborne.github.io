From MVC to DDD: It’s Not Just Package Names That Change — The “Objects” Come Alive

Introduction

When learning DDD (Domain-Driven Design), many people are put off by complex concepts. But returning to the essence, we can understand DDD as a “super-evolved enhanced version” of MVC. Building on MVC, it solves the pain point of system “bloat” as business complexity grows through clearer separation of responsibilities and logical decoupling.

1. Core Mindset: From “Looking at the Manual” to “Asking the Person Directly”

In traditional MVC (Anemic Domain Model), entity classes (Entity/PO) are merely data carriers, like a blank sheet of paper. All business logic is piled up in the Service layer.

  • Pain Point: The Service layer grows larger and larger, logic becomes scattered, and maintaining it feels like trying to find the end of a tangled thread.

In DDD (Rich Domain Model), data and business logic are written together.

  • The Shift: Entity classes become living, principled “business experts.”

  • Example: Consider the “order cancellation” logic.

    • MVC: OrderService fetches Order data, checks the status, modifies the status, saves to disk.
    • DDD: The Order entity has an internal cancel() method — it decides for itself whether it can be cancelled.

Key Point: The benefit of DDD is high logical cohesion. When business logic changes, you only need to modify the corresponding domain model object, rather than digging through thousands of lines of Service code.

2. Architectural Mapping: How DDD Maps to MVC

We can simply understand the DDD workflow as:

Controller $\rightarrow$ Application Service $\rightarrow$ Domain Model $\rightarrow$ Repository (Impl $\rightarrow$ Mapper)

For easier understanding, here is a comparison table:

Layer DDD Naming MVC Counterpart Enhanced Responsibility
Interface Layer Interfaces Controller Only handles protocol conversion (REST/JSON), does no business logic.
Application Layer Application Service (light) Commander: No if-else logic — only orchestrates domain objects.
Domain Layer Domain Entity (heavy) Core: Contains business rules — data and logic coexist.
Infrastructure Layer Infrastructure DAO / Mapper Plug-in style: Hides database details. Repository is the interface, Mapper is the implementation.

3. Why Does DDD Have More Packages? (The Truth About Decoupling)

You will notice DDD introduces ApplicationService, Domain Model, Repository, etc. This may seem cumbersome, but it actually achieves two levels of core decoupling:

1. Business Logic Decoupled from Process Orchestration (Application vs Domain)

  • The Application layer only cares about “what to do first, what to do next.”
  • The Domain layer only cares about “what is the business rule.”
  • Benefit: Business logic can be unit tested in isolation, without needing a running database — extremely fast.

2. Business Logic Decoupled from Storage Technology (Domain vs Infrastructure)

  • Domain models only recognize the Repository interface and don’t care whether the underlying technology is MyBatis, JPA, or Redis.
  • Benefit: Even if you switch your database from MySQL to MongoDB, your core business logic (the Domain layer) does not need a single character changed.

4. The Three Members of the Model (Tactical Modeling)

Within the DDD domain layer, not all classes are the same. To organize business logic more scientifically, we typically divide models into the following three types:

1. Entity (Entity) — Has a Unique Identity

The core characteristic of an entity is its identity. Even if all its attributes change, it remains the same object.

  • Definition: An object with a unique identifier (ID). Even if two orders have the exact same products and prices, as long as their IDs are different, they are two different things.
  • Characteristics: Has a lifecycle (creation, modification, state transitions, archival).
  • Examples: Order, User.

Scenario: When an order is created, its status is “pending payment” and the shipping address is “Shanghai”; after payment, the status becomes “paid” and the address changes to “Beijing.”

Core Idea: Although the status and address have changed, since its OrderNo (or ID) hasn’t changed, we still consider it the same order.

Code Characteristic: Internally it must have a private Long id; or private String orderNo;, and logical comparisons use this ID for equals().

2. Value Object (VO) — Attributes Only, No ID

A value object is like “descriptive text.” If all attributes of two value objects are the same, they are the same thing.

  • Definition: No ID, defined purely by its attributes. If two objects have exactly the same attribute values, they are interchangeable.
  • Characteristics: Immutability. If you want to change an address, you don’t modify the original address object’s properties — you directly replace it with a new address object.
  • Examples: Address (province/city/district/street combination), Money (currency + amount).

Scenario: An order has a shipping address: {Province: "Guangdong", City: "Shenzhen", Street: "Nanshan District"}.

Core Idea: We don’t care about this address object’s “identity card” — we only care about where it’s addressed to. If two orders are both shipped to this place, then these two address objects are logically equivalent.

Code Characteristics:

  1. No ID.
  2. Immutability: If you want to change the address, you don’t call address.setStreet("Futian District") — instead, you directly give the Order a new Address object: order.changeAddress(new Address("Guangdong", "Shenzhen", "Futian District")).

3. Aggregate Root (AR) — The Organizational Manager

  • Definition: The “big boss” of a group of associated objects. External code can only access its internal members through the aggregate root.
  • Responsibility: Maintains business integrity (invariants).
  • Example: In order business, Order is the aggregate root, and OrderItem is one of its internal members.

Scenario: An order contains 3 products (order items).

Core Idea:

  1. External Service code cannot bypass Order to directly modify the price of an OrderItem.
  2. It must call order.adjustItemPrice(itemId, newPrice). It is the Order — the “big boss” — that decides whether this operation is valid (e.g., if the order has already shipped, the boss will refuse to modify the price).

Lifecycle: The aggregate root is responsible for the lifecycle of its internal members. If the Order is deleted from the database, its internal OrderItem objects must disappear along with it.

Prohibition: You absolutely must not directly call OrderItemMapper in the Controller to modify a product’s price — you must go through Order.updateItemPrice().

4. Summary and Comparison

Model Type Has Unique ID When All Attributes Match Modification Method Examples
Entity Yes Still two independent objects Modify attributes via methods User, Product
Value Object (VO) No Considered the same object Whole-object replacement (immutable) Money, Address
Aggregate Root (AR) Yes (Same as Entity) Coordinates all internal members Order, Forum Topic

5. Model Transformation: Each Layer Has Its Own “Face”

To achieve “decoupling,” each layer actually uses different models. Although this adds verbosity, it effectively prevents database logic from polluting business logic:

  1. DTO (Data Transfer Object): Used in the interface layer. Shaped like a form; fields may be sparse.
  2. Domain Entity: Used in the domain layer. This is the “living object” you write, carrying business logic.
  3. PO (Persistent Object): Used in the infrastructure layer. Looks exactly like the database table.

// Entity class: Order.java
public class Order {// <--- This is an [Aggregate Root]
    private Long orderId;// <--- Aggregate root is also an Entity, has unique ID
    private List<OrderItem> items;// <--- Order items are [Entities], but managed by the aggregate root
    private OrderStatus status; // CREATED, PAID, CANCELLED, SHIPPED
    private Address address; // <--- Shipping address is a [Value Object], no ID, whole-object replacement
    private BigDecimal totalPrice;

	// Aggregate root method: ensures business integrity
    public void changeAddress(Address newAddress) {
        if (this.status == OrderStatus.SHIPPED) {
            throw new BusinessException("Cannot change address after shipment");
        }
        this.address = newAddress; 
    }

    // --- Business logic: construction constraints for creating an order ---
    public Order(List<OrderItem> items) {
        if (items == null || items.isEmpty()) {
            throw new BusinessException("Order must contain at least one product");
        }
        this.items = items;
        this.status = OrderStatus.CREATED;
        this.totalPrice = calculateTotal(); // Internal logic, auto-calculates total
    }

    // --- Business logic: cancel an order ---
    public void cancel() {
        if (this.status == OrderStatus.SHIPPED) {
            throw new BusinessException("A shipped order cannot be cancelled");
        }
        this.status = OrderStatus.CANCELLED;
    }

    private BigDecimal calculateTotal() {
        return items.stream().map(OrderItem::getPrice).reduce(BigDecimal.ZERO, BigDecimal::add);
    }
  
    // Getters omitted...
}

// Repository interface: OrderRepository.java (only defines business behaviors)
public interface OrderRepository {
    void save(Order order);
    Order findById(Long id);
}

@Service
public class OrderApplicationService {
    @Autowired
    private OrderRepository orderRepository;

    // Order creation flow
    @Transactional
    public void createOrder(OrderCreateDTO dto) {
        // Call domain model for creation
        Order order = new Order(dto.getItems());
        // Call repository for persistence
        orderRepository.save(order);
    }

    // Order cancellation flow
    @Transactional
    public void cancelOrder(Long id) {
        // 1. Find the "living" object through the repository
        Order order = orderRepository.findById(id);
        // 2. Issue the command to the object: cancel yourself
        order.cancel(); 
        // 3. Save the modified state
        orderRepository.save(order);
    }
}

@Repository
public class OrderRepositoryImpl implements OrderRepository {
    @Autowired
    private OrderMapper orderMapper; // MyBatis Mapper

    @Override
    public void save(Order order) {
        // 1. Conversion: transform domain object Order into database table object OrderPO
        OrderPO po = convertToPO(order);
        // 2. Persist: call the Mapper to execute SQL
        if (po.getId() == null) {
            orderMapper.insert(po);
        } else {
            orderMapper.updateStatus(po);
        }
    }

    @Override
    public Order findById(Long id) {
        OrderPO po = orderMapper.selectById(id);
        // 3. Restoration: convert database record back into a domain object with business capabilities
        return convertToEntity(po);
    }
}

@RestController
@RequestMapping("/api/orders")
public class OrderController {
    @Autowired
    private OrderApplicationService orderAppService;

    @PostMapping("/create")
    public Response create(@RequestBody OrderCreateDTO dto) {
        orderAppService.createOrder(dto);
        return Response.ok();
    }

    @PostMapping("/{id}/cancel")
    public Response cancel(@PathVariable Long id) {
        orderAppService.cancelOrder(id);
        return Response.ok();
    }
}
  1. Where is the logic?
  • The logic for “can it be cancelled?” is in the Order class (domain layer).
  • The steps of “fetch first, then modify, then save” are in OrderApplicationService (application layer).
  1. Where is the decoupling?
  • ApplicationService has no idea whether the database is MySQL or a text file, because it only calls orderRepository.save().
  • The actual SQL statements are completely physically isolated in the Mapper within the Infrastructure layer.
  1. Why write it this way?
  • If the “order cancellation” rule changes in the future (e.g., orders that have been unpaid for more than 30 minutes cannot be cancelled), you only need to modify the Order entity class in one place — the other three layers’ code doesn’t need to be touched at all. This is the power of DDD in handling complex business scenarios.

7. Summary: What Exactly Does DDD Enhance?

  1. High Cohesion: Whoever owns the data is responsible for it — business logic no longer “miscarries” across various Service classes.
  2. Maintainability: The code structure mirrors the business blueprint — a glance at the domain objects reveals the business rules.
  3. Plug-in Architecture: Databases and external services become “plugins,” making the system more robust.

8. Conclusion

DDD is not about overthrowing MVC. Rather, when business complexity reaches a certain threshold, it provides developers with a “scalpel” that allows us to elegantly dissect intertwined logic.

In one sentence: MVC helps us put code in the right places, while DDD brings the objects to life.
