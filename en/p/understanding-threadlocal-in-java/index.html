Introduction to ThreadLocal

From the description in the official Java documentation: The ThreadLocal class is used to provide thread-local variables. Such variables, when accessed in a multi-threaded environment (via get and set methods), ensure that each thread’s variables remain relatively independent from variables in other threads. ThreadLocal instances are typically private static fields, used to associate threads with their thread context.

We can deduce that the purpose of ThreadLocal is: to provide local variables within a thread, ensuring different threads do not interfere with each other. These variables are effective throughout the thread’s lifecycle, reducing the complexity of passing common variables between multiple functions or components within the same thread.

  • Thread concurrency: In multi-threaded concurrent scenarios
  • Passing data: We can use ThreadLocal to pass common variables between different components within the same thread (somewhat similar to Session?)
  • Thread isolation: Each thread’s variables are independent and do not affect each other

Differences Between ThreadLocal and Synchronized

Although both the ThreadLocal pattern and the Synchronized keyword are used to handle the problem of multi-threaded concurrent access to variables, their approaches and perspectives differ.

Synchronized ThreadLocal
Principle The synchronization mechanism uses a time-for-space tradeoff, providing only one copy of the variable and having different threads queue for access ThreadLocal uses a space-for-time tradeoff, providing each thread with its own copy of the variable, enabling simultaneous access without interference
Focus Synchronization of resource access among multiple threads Data isolation between threads in a multi-threaded environment

Summary: In the example above, although both ThreadLocal and Synchronized can solve the problem, using ThreadLocal is more appropriate because it allows the program to have higher concurrency.

Internal Structure of ThreadLocal

Through the above learning, we have gained some understanding of ThreadLocal’s functionality. Now let us look at ThreadLocal’s internal structure together and explore the principles behind its ability to achieve thread data isolation.

Common Misconception

If we do not read the source code, we might guess that ThreadLocal is designed like this: each ThreadLocal creates a Map, then uses Thread as the Map’s key and the local variable to be stored as the Map’s value. This way, the effect of isolating local variables for each thread is achieved. This is the simplest design, and indeed, the earliest versions of ThreadLocal in the JDK were designed this way — but not anymore.

The Current Design

However, the JDK later optimized the design. In JDK 8, ThreadLocal’s design is: each Thread maintains a ThreadLocalMap, where the Map’s key is the ThreadLocal instance itself, and the value is the actual Object to be stored. The specific process is as follows:

  • Each Thread has a Map (ThreadLocalMap) internally
  • The Map stores ThreadLocal objects (as keys) and the thread’s variable copies (as values)
  • The Map inside Thread is maintained by ThreadLocal, which is responsible for getting and setting the thread’s variable values from/to the Map
  • For different threads, each time a copy value is retrieved, other threads cannot access the current thread’s copy value, thus forming copy isolation with no mutual interference

Comparison

What are the benefits of the JDK 8 design change?

  • The number of Entries stored in each Map is reduced, because originally the number of Entries was determined by the number of Threads, whereas now it is determined by the number of ThreadLocals.
    • In real development, the number of Threads far exceeds the number of ThreadLocals.
  • When a Thread is destroyed, its ThreadLocalMap is also destroyed along with it, because ThreadLocalMap is stored within Thread and disappears as Thread is destroyed, reducing overhead.

Source Code Analysis of ThreadLocal Core Methods

Based on ThreadLocal’s internal structure, let us continue to analyze the source code of its core methods for a deeper understanding of its operating principles. Apart from the constructor, ThreadLocal exposes the following 4 methods:

Method Declaration Description
protected T initialValue() Returns the initial value of the current thread’s local variable
public void set(T value) Sets the local variable bound to the current thread
public T get() Gets the local variable bound to the current thread
public void remove() Removes the local variable bound to the current thread

Below is a detailed source code analysis of these 4 methods. (To keep the thought process clear, the ThreadLocalMap part will not be expanded for now — it will be detailed in the next section.)

The set Method

Code flow:

  • First, obtain the current thread, and based on the current thread, obtain a Map
  • If the obtained Map is not empty, set the parameter into the Map (using the current ThreadLocal’s reference as the key)
  • If the Map is empty, create a Map for this thread and set the initial value

The get Method

Code execution flow:

  • First, obtain the current thread, and based on the current thread, obtain a Map
  • If the obtained Map is not empty, use the ThreadLocal’s reference as the key to get the corresponding Entry from the Map. Otherwise, go to step 4
  • If the Entry is not null, return e.value. Otherwise, go to step 4
  • If the Map is empty or the Entry is null, obtain the initial value through the initialValue function, then use the ThreadLocal’s reference and the value as firstKey and firstValue to create a new Map

Summary: First, get the ThreadLocal variable of the current thread. If it exists, return the value; if not, create it and return the initial value.

The remove Method

Code execution flow:

  • First, obtain the current thread, and based on the current thread, obtain a Map
  • If the obtained Map is not empty, remove the Entry corresponding to the current ThreadLocal object

The initialValue Method

The purpose of this method is to return the initial value of this thread’s local variable.

  • This method is a lazily invoked method. From the code above, we know it is executed only when set has not yet been called but get is called first, and it executes only once.
  • The default implementation directly returns null.
  • If you want an initial value other than null, you can override this method. (Note: This method is protected, clearly designed to be overridden by subclasses.)

Weak References and Memory Leaks

Some developers encounter memory leaks while using ThreadLocal and conjecture that the leak is related to the use of weak references for the key in Entry. This understanding is actually incorrect.

Let us first review several conceptual terms involved in this problem, then analyze the issue.

Memory Leak Related Concepts

Memory overflow: There is not enough memory available for the requester to use.

Memory leak: Refers to heap memory that has been dynamically allocated by a program but, for some reason, is not released or cannot be released, resulting in wasted system memory, leading to slowed program execution speed or even system crashes. The accumulation of memory leaks will eventually lead to memory overflow.

Weak Reference Related Concepts

There are 4 types of references in Java: strong, soft, weak, and phantom. The current issue primarily involves strong and weak references:

Strong Reference (“Strong” Reference) is the most common ordinary object reference we encounter. As long as a strong reference points to an object, it indicates that the object is still “alive”, and the garbage collector will not reclaim such an object.

Weak Reference (WeakReference): Once the garbage collector discovers an object that only has weak references, it will reclaim its memory regardless of whether the current memory space is sufficient.

Would a memory leak occur if the key used strong references?

Suppose the key in ThreadLocalMap used strong references — would a memory leak occur?

At this point, the memory diagram for ThreadLocal (solid lines indicate strong references) is as follows:

  • Suppose after using ThreadLocal in business code, the threadLocal Ref is reclaimed.
  • But because the ThreadLocalMap’s Entry holds a strong reference to threadLocal, threadLocal cannot be reclaimed.
  • Without manually deleting this Entry and with the CurrentThread still running, there is always a strong reference chain threadRef -> currentThread -> threadLocalMap -> entry, and the Entry will not be reclaimed (the Entry includes the ThreadLocal instance and value), causing an Entry memory leak.

In other words, if the key in ThreadLocalMap uses strong references, memory leaks cannot be completely avoided.

Would a memory leak occur if the key uses weak references?

  • Similarly, suppose after using ThreadLocal in business code, the threadLocal Ref is reclaimed.
  • Since ThreadLocalMap only holds a weak reference to ThreadLocal, with no strong references pointing to the threadlocal instance, threadlocal can be smoothly reclaimed by the GC. At this point, the key in the Entry = null.
  • However, without manually deleting this Entry and with the CurrentThread still running, there also exists a strong reference chain threadRef -> currentThread -> threadLocalMap -> entry -> value, so value will not be reclaimed, and this piece of value will never be accessible again, causing a value memory leak.

In other words, even if the key in ThreadLocalMap uses weak references, memory leaks are still possible.

The Real Cause of Memory Leaks

Comparing the two cases above, we find that the occurrence of memory leaks has nothing to do with whether the key in ThreadLocalMap uses weak references. So what is the real cause of memory leaks?

Careful readers will notice that in both memory leak scenarios above, there are two prerequisites:

  • The Entry was not manually deleted
  • The CurrentThread is still running

The first point is easy to understand: as long as you call the remove method to delete the corresponding Entry after using ThreadLocal, memory leaks can be avoided.

The second point is slightly more complex. Since ThreadLocalMap is an attribute of Thread and is referenced by the current thread, its lifecycle is as long as the Thread’s. So after using ThreadLocal, if the current Thread also finishes execution, ThreadLocalMap will naturally be reclaimed by the GC, avoiding memory leaks at the root.

In summary, the root cause of ThreadLocal memory leaks is: because the lifecycle of ThreadLocalMap is as long as the Thread’s, failure to manually delete the corresponding key will lead to memory leaks.

Why Use Weak References?

Based on the analysis just now, we know: regardless of which type of reference is used for the key in ThreadLocalMap, memory leaks cannot be completely avoided. It has nothing to do with using weak references.

There are two ways to avoid memory leaks:

  • After using ThreadLocal, call its remove method to delete the corresponding Entry
  • After using ThreadLocal, the current Thread also finishes execution

Compared to the first approach, the second is clearly harder to control, especially when using thread pools — threads that finish executing are not destroyed but instead returned to the thread pool.

That is to say, as long as you remember to call remove promptly after using ThreadLocal, there will be no problem regardless of whether the key is a strong or weak reference. So why use weak references for the key?

In fact, in the set/getEntry methods of ThreadLocalMap, a check is performed for keys that are null (i.e., ThreadLocal being null). If null, the value is set to null.

This means that after using ThreadLocal, even if the CurrentThread is still running and you forget to call the remove method, weak references provide one extra layer of protection compared to strong references: the weakly referenced ThreadLocal will be reclaimed, and the corresponding value will be cleared the next time any of ThreadLocalMap’s set, get, or remove methods is called, thereby avoiding memory leaks.

public void set(T value) {

ThreadLocal.ThreadLocalMap getMap(Thread t) {
    return t.threadLocals;
}

void createMap(Thread t, T firstValue) {
    // Calls ThreadLocalMap's constructor
    t.threadLocals = new ThreadLocal.ThreadLocalMap(this, firstValue);
}

We analyzed this method earlier. Its purpose is to set the local variable bound to the current thread:

  • First, obtain the current thread, and based on the current thread, obtain a Map
  • If the obtained Map is not empty, set the parameter into the Map (using the current ThreadLocal’s reference as the key) (this calls ThreadLocalMap’s set method)
  • If the Map is empty, create a Map for this thread and set the initial value (this calls ThreadLocalMap’s constructor)

This code touches on two methods of ThreadLocalMap in two places. Let us analyze these two methods next.

Constructor

ThreadLocalMap(ThreadLocal<?> firstKey, Object firstValue)

The constructor first creates an Entry array of length 16, then calculates the index corresponding to firstKey, stores it in the table, and sets the size and threshold.

Key analysis: int i = firstKey.threadLocalHashCode & (INITIAL_CAPACITY - 1)

About: threadLocalHashCode

An AtomicInteger type is defined here. Each time the current value is obtained and HASH_INCREMENT is added. HASH_INCREMENT = 0x61c88647, a value related to the Fibonacci sequence (golden ratio). Its main purpose is to allow hash codes to be evenly distributed across an array whose length is a power of 2 — that is, in the Entry[] table. Doing so minimizes hash conflicts.

About: & (INITIAL_CAPACITY - 1)

When computing the hash, the algorithm hashCode & (size - 1) is used internally. This is a more efficient implementation equivalent to the modulo operation hashCode % size. It is precisely because of this algorithm that we require size to be a power of 2, which also ensures that the number of hash conflicts is reduced while the index does not go out of bounds.

The set Method (of ThreadLocalMap)

Code execution flow:

  • First, calculate index i based on the key, then look up the Entry at that position
  • If the Entry already exists and the key equals the passed-in key, then directly assign the new value to this Entry
  • If the Entry exists but the key is null, call replaceStaleEntry to replace this Entry whose key is null
  • Continuously loop until a null position is encountered. If no return occurs during the loop, create a new Entry at this null position, insert it, and increment size by 1

Finally, call cleanSomeSlots to clean up Entries with null keys. Then check whether sz >= threshold, meaning the rehash condition is met. If so, call the rehash function to perform a full-table scan cleanup.

Linear Probing for Hash Conflict Resolution

This method probes subsequent addresses one by one until an empty address is found for insertion. If no empty address is found in the entire space, an overflow occurs.

For example, suppose the current table length is 16. If the hash value calculated for the key is 14 and table[14] already has a value whose key does not match the current key, then a hash conflict has occurred. At this point, add 1 to 14 to get 15 and check table[15]. If still a conflict, wrap around back to 0 and check table[0], and so on, until an insertion point is found.

Following the description above, the Entry table can be viewed as a circular array.

User Scenario 1

Beyond source code scenarios, do you have your own use cases for ThreadLocal?

Previously, after going live, we discovered that dates for some users were incorrect. After investigation, it turned out to be a SimpleDateFormat issue. At the time, we used SimpleDateFormat’s parse() method, which internally has a Calendar object. Calling SimpleDateFormat’s parse() method first calls Calendar.clear() and then Calendar.add(). If one thread calls add() first and then another thread calls clear(), the time parsed by parse() will be incorrect.

In fact, solving this problem is very simple — let each thread create its own SimpleDateFormat. But would 1000 threads need to create 1000 SimpleDateFormat instances?

So at the time, we used a thread pool combined with ThreadLocal to wrap SimpleDateFormat, then overrode initialValue so each thread had its own copy of SimpleDateFormat. This solved the thread safety issue while also improving performance.

User Scenario 2

In my project, there was a thread frequently encountering the need to pass objects across several method calls — the context. It is a state, often representing user identity, task information, etc., leading to the problem of excessive parameter passing.

Using something like the Chain of Responsibility pattern, adding a context parameter to each method is very cumbersome. Moreover, sometimes when the call chain involves third-party libraries whose source code cannot be modified, the object parameter cannot be passed in. So I used ThreadLocal to refactor this. Now, you only need to set the parameter in ThreadLocal before the call, and elsewhere just get it.

      // Inside these methods:  User u = threadLocalUser.get(); is all that's needed
    getInfo();
    checkInfo();
    setSomeThing();
    log();
    } finally {
     threadLocalUser.remove();
    }
}
