Troubleshooting Git Clone Failures for Large Repos: The SSH Solution

2026-04-29
May 08, 2026 01:07 +0800
819字

HTTP/2 stream interruption and SSL connection resets when cloning large repos? This post walks through the troubleshooting process, protocol analysis, and the ultimate fix: switching from HTTPS to SSH for reliable Git data transfer.

1. Problem Background

While attempting to clone the large open-source project taichi-project/anyagent, the terminal repeatedly reported network-layer disconnection errors that caused the clone to fail.

Initial error: A basic git clone would pull data halfway before abruptly failing:

error: RPC failed; curl 92 HTTP/2 stream 7 was not closed cleanly: CANCEL (err 8) fatal: early EOF

Root cause: This is a classic Git network transport interruption scenario. Due to the repository’s large size (or extensive commit history), the HTTP/2 data stream was forcibly terminated midway through the proxy environment (v2rayN).

2. Solutions Attempted

2.1 Shallow Clone (Failed)

Running git clone --depth 1 https://... to reduce download volume.

While the object count decreased, the connection still broke midway, with the error evolving to:

curl 56 OpenSSL SSL_read: SSL_ERROR_SYSCALL, errno 0

Analysis: This proves it’s not just a file-size issue — the underlying HTTPS connection is being physically severed mid-transfer by the firewall or the proxy software’s SSL mechanism.

2.2 Proxy Configuration Tuning (Partially effective)

Inspected the local v2rayN proxy configuration and found the mixed port was 10808. Attempted injecting temporary environment variables via $env:HTTP_PROXY in PowerShell, and considered enabling Tun mode to take over system-wide traffic.

While this approach addresses the root connectivity issue, HTTP proxies remain unreliable for sustained high-volume data streams, and proxy rules frequently conflict with system-level network configurations.

3. Protocol Deep Dive: HTTP(S) vs. SSH

HTTP/HTTPS Protocol

  • Mechanism: Relies on standard web ports (80/443); data transfer is governed by local proxy rules (PAC, system proxy, or CLI environment variables).
  • Upside: Extremely low barrier to entry — anyone with a URL can clone a public repository.
  • Downside: Highly sensitive to network conditions. When routed through complex proxy nodes, it is vulnerable to MITM certificate substitution (triggering SSL parsing errors) or buffer overflow on high-volume streams, causing connection resets.

SSH Protocol

  • Mechanism: Operates on an independent TCP port 22 using asymmetric encryption (public/private key pairs). Once the local private key is paired with the public key on GitHub’s servers, an end-to-end encrypted tunnel is established.
  • Upside: Extremely stable and secure. It bypasses most HTTP-oriented application-layer proxies and censorship, making it immune to curl-related network interruptions.
  • Downside: Higher setup cost — requires generating a key pair and registering it with the platform; tightly bound to the physical machine.

4. Why HTTP Fails and SSH Succeeds

The root cause boils down to how proxy software handles different protocol data streams:

  1. HTTPS gets “clipped” by the proxy: When cloning over HTTPS, traffic is forcibly routed to the proxy software’s port 10808. When processing sustained, large Git object streams, the proxy node may trigger a timeout-based drop, or a momentary certificate verification gap between local OpenSSL and the proxy server may cause a forced SYSCALL interrupt.
  2. SSH’s “fast-pass” lane: After switching to SSH, the terminal bypasses the system HTTP proxy routes entirely and handshakes directly with the remote via port 22. Backed by cryptographic key authentication, this low-level encrypted tunnel is robust enough to slip past the web-layer proxy rules, guaranteeing complete delivery of large data volumes.

5. The Final Solution: Full SSH Setup Guide

Steps for Windows PowerShell.

5.1 Generate an SSH Key Pair 

1

ssh-keygen -t ed25519 -C "your-email@example.com"
  • Press Enter to accept the default save path (~/.ssh/id_ed25519)
  • When prompted for a passphrase, press Enter twice to leave it blank — this avoids extra password prompts when pulling code later.

5.2 Copy the Public Key 

1

Get-Content ~/.ssh/id_ed25519.pub | Set-Clipboard

If you used the default RSA encryption instead of ed25519, the file is ~/.ssh/id_rsa.pub.

5.3 Add the Public Key to GitHub

  1. Log in to GitHub, click your avatar → Settings
  2. Select SSH and GPG keys from the left sidebar
  3. Click New SSH key
  4. Title: anything descriptive, e.g. “My Windows PC”
  5. Key type: keep the default “Authentication Key”
  6. Key: paste the public key content (starts with ssh-ed25519 or ssh-rsa)
  7. Click Add SSH key

5.4 Test the Connection 

1

ssh -T git@github.com

On first connection, you’ll see Are you sure you want to continue connecting? — type yes manually. Upon success, you’ll see something like Hi your_username! You've successfully authenticated....

5.5 Re-clone

Now clone using the SSH address:

1

git clone git@github.com:taichi-project/anyagent.git

5.6 Pros, Cons, and Best Practices

Pros: A one-time investment for long-term stability and security. Once configured, you have a fully encrypted, password-free direct channel to GitHub, completely immune to proxy port conflicts, SSL certificate hijacking, and the frequent connection-reset errors that plague large file transfers over HTTP/HTTPS.

Cons: Higher setup barrier. For newcomers, understanding public-key cryptography and navigating the generate-copy-register workflow in the terminal is error-prone (e.g., missing characters when copying, forgetting to type yes). It’s also machine-bound — you’ll need to reconfigure after replacing a computer or reinstalling the OS.

Best practice: Make SSH your default protocol for daily Git interactions. Use SSH for all long-lived repositories or those you frequently push/pull. Reserve HTTPS (with browser or terminal proxy) for one-off, temporary clones where stability is not critical.
