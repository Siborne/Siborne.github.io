User Login Authentication Flow (Based on JWT)

  1. The user enters their username and password and sends them to the server via an HTTPS request.

  2. The server verifies the credentials:

    • If verification succeeds, it generates a signed JWT (JSON Web Token) and returns it to the client;
    • If verification fails, it returns an error message.

  3. After the client (e.g., a browser) receives the JWT, it stores it (typically in localStorage or cookie; for Vue.js frameworks, Vuex or Pinia can be used).

  4. For every subsequent request, the client includes the JWT in the HTTP request header (e.g., Authorization: Bearer <token>) and sends it to the server.

  5. Upon receiving the request, the server:

    • Uses its locally stored secret key to verify the JWT signature;
    • If the signature is valid and the token has not expired (determined by the exp field), the user is considered authenticated and the requested data is returned;
    • Otherwise, the request is rejected.

  6. When the user logs out, the client simply destroys the locally stored token — the server does not need to take any action.

Introduction to JWT

JWT (JSON Web Token) is an open standard (RFC 7519) for securely transmitting information between parties as a JSON object. It encrypts/encodes user information (such as user ID, roles, etc.) into the token’s payload, and the server does not store any user information. The server verifies the correctness of the token using the stored secret key — if it is correct, authentication passes.

Its advantages include solving single sign-on problems well in distributed systems and easily resolving session sharing issues. JWT is relatively short in length and can be transmitted via URL (URL-safe).

Core Characteristics:

  • Stateless: The server does not store session information; all authentication data is contained within the token.
  • Self-contained: The token itself carries the necessary data, reducing database queries.
  • Cross-domain and Distributed System Support: Naturally suited for microservice architectures and Single Sign-On (SSO) scenarios.
  • URL-safe: Base64Url encoding allows it to be safely transmitted via URL, POST parameters, or HTTP Headers.

/** Generate token */
public static String generateToken(Map<String, Object> claimMaps) {

    if (null != claimMaps) {
        claimMaps.forEach((key, val) -> {
            claimMaps.put(key, val.toString());
        });
    }

    return Jwts.builder()
            // JWT_ID, can be used for unique identification of each signature
            .setId(UUID.randomUUID().toString())
            // Data compression method
            .compressWith(CompressionCodecs.GZIP)
            // Issuer information
            .setIssuer(ISSUER)
            // Subject
            .setSubject("system")
            // Audience
            .setAudience(AUDIENCE)
            // Issued-at timestamp
            .setIssuedAt(new Date(System.currentTimeMillis()))
            // Expiration timestamp
            .setExpiration(new Date(System.currentTimeMillis() + EXPIRES_IN * 1000))
            // Claim information, custom payload
            .addClaims(claimMaps)
            // Signature algorithm + secret key
            .signWith(SIGNATURE_ALGORITHM, secretKey)
            .compact();
}

The process of verifying a token is essentially the same as generating a new token.

Based on the received header, payload, and the secret key stored on the server, a new token is regenerated and compared:

  • If the tokens match, the token is valid and has not been tampered with.
  • If the token has not been tampered with, the payload can be further decrypted via Base64, and the exp expiration field in the payload can be used to determine whether the token has expired.

Note: JWT itself contains authentication information, so once the information is leaked, anyone can obtain all the permissions of the token. Therefore, when doing front-end development, it is best not to store JWT in Cookie, which is a storage unit prone to leaking personal privacy information.

Advantages

  • Stateless & Scalable: Very suitable for distributed systems and microservice architectures;
  • Solves Session Sharing Issues: No need to share session storage;
  • Natively supports cross-domain and mobile;
  • Reduces database pressure: Authentication information is built into the token, eliminating the need for frequent database queries.

Disadvantages and Risks

  1. Cannot actively revoke tokens Once issued, a token remains valid until it expires. If a user logs out or their permissions change, the server cannot immediately invalidate the old token (unless a blacklist mechanism is introduced, but this goes against the stateless design principle).
  2. Risk of sensitive information leakage Although the Payload is Base64-encoded, it is not encrypted (unless JWE is used). Never store sensitive data such as passwords in the token.
  3. HTTPS is mandatory JWT is transmitted over the network. If HTTP is used, it is highly susceptible to man-in-the-middle attacks. Always use HTTPS throughout.
  4. Large token size Compared to traditional session IDs, JWT is longer because it contains data, which may affect performance (especially in high-frequency request scenarios).

Additional Notes

  • Single Sign-On (SSO): JWT natively supports SSO because the token can be verified by multiple services.

  • Homepage Access Control: If you need to “open the homepage” (i.e., allow anonymous access), you should configure a whitelist path in the gateway or interceptor to skip JWT verification.

  • Cross-domain Support: JWT itself is not related to CORS, but when used with the Authorization Header, cross-domain authentication can be easily achieved.

  • Comparison with Spring Session:

    • Spring Session relies on server-side storage (e.g., Redis) and supports active invalidation;
    • JWT is stateless but sacrifices real-time control capability;
    • Both are suitable for different scenarios and can be used in combination (e.g., using JWT for authentication and Redis for managing blacklists).

Recommended Approaches for Enhancing JWT Security and Controllability

Although JWT has advantages such as being stateless and scalable, its characteristic of “inability to actively revoke” does pose challenges in certain business scenarios (such as user logout, password changes, permission changes). To address this, the following two complementary strategies are recommended to enhance the system’s security control capabilities:

Approach 1: Short-lived Access Token + Refresh Token Mechanism

  • Core Idea:

    • Access Token: Has a short validity period (e.g., 15–30 minutes), used for everyday API authentication;
    • Refresh Token: Has a longer validity period (e.g., 7 days), stored in a secure HttpOnly Cookie or secure storage, used only to obtain a new Access Token.

  • Workflow:

    1. After the user successfully logs in, the server returns a pair of tokens: access_token and refresh_token;
    2. The client uses the access_token to call protected APIs;
    3. When the access_token expires, the client uses the refresh_token to request a new access_token from the authentication service;
    4. If the user logs out or changes their password, the server immediately revokes the corresponding refresh_token (e.g., deletes it from the database or Redis);
    5. Even if the old access_token has not yet expired, since it cannot be renewed, the effective window is greatly shortened.

  • Advantages:

    • Balances security and user experience;
    • After logout, the token becomes fully invalid at most after one Access Token lifecycle (e.g., 30 minutes);
    • Conforms to OAuth 2.0 standard practices.

Approach 2: Lightweight Token Blacklist / Whitelist Mechanism Based on Redis

  • Implementation A: JTI Blacklist

    • Embed a unique identifier in the JWT’s jti (JWT ID) field;
    • When a user logs out, changes password, or has permission changes, store the jti and its expiration time in Redis (TTL = remaining validity period of the original JWT);
    • Each time a JWT is verified, additionally check whether the jti exists in the blacklist;
    • If it exists, reject the request.

  • Implementation B: User Session Whitelist (Stricter)

    • After each successful login generates a JWT, store the full token string (or its hash value) in Redis keyed by user_id:session_id;
    • All protected APIs, after verifying the JWT signature and expiration, additionally verify whether the token exists in Redis;
    • When a user logs out, changes password, or an administrator forces an offline, delete the corresponding Redis key;
    • At this point, even if the token has not expired and the signature is valid, it will be rejected because it is “not in the whitelist.”

  • Advantages:

    • Achieves true instant logout;
    • Supports fine-grained control (e.g., multi-device management, forced logout);
    • Redis offers high performance with minimal impact on system throughput.

  • Notes:

    • Properly set the TTL of Redis keys to avoid unlimited memory growth;
    • While the whitelist approach is more secure, it slightly sacrifices JWT’s “fully stateless” nature, belonging to a stateful enhancement pattern.

Comprehensive Recommendations

Scenario Recommended Approach
General Web applications, mobile Apps Access Token + Refresh Token (balances security and performance)
High-security systems (e.g., finance, admin panels) Refresh Token + Redis Blacklist/Whitelist
Need to support “multi-device login management” Use Redis Whitelist + session_id to identify devices

💡 Best Practice: Even when using a blacklist mechanism, keep the Access Token’s validity period short (e.g., ≤30 minutes) to limit Redis storage pressure and potential attack windows.
