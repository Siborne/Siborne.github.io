ThreadLocal Introduction

From the official Java documentation: The ThreadLocal class is used to provide thread-local variables. These variables, when accessed in a multithreaded environment (via get and set methods), ensure that each thread’s variables are relatively independent from variables in other threads. ThreadLocal instances are typically private static types, used to associate threads with their context.

We can understand ThreadLocal’s purpose as: providing thread-local variables that don’t interfere with each other between different threads. These variables are effective within a thread’s lifecycle, reducing the complexity of passing common variables between multiple functions or components within the same thread.

  • Thread concurrency: In multithreaded concurrent scenarios
  • Data passing: We can use ThreadLocal to pass common variables between different components within the same thread (somewhat similar to Session?)
  • Thread isolation: Each thread’s variables are independent and don’t affect each other

ThreadLocal vs Synchronized Differences

Although both ThreadLocal pattern and Synchronized keyword handle multithreaded concurrent variable access, their problem-solving approaches and perspectives differ.

Synchronized ThreadLocal
Principle Synchronization mechanism trades time for space, providing only one variable copy, forcing threads to queue for access ThreadLocal trades space for time, providing each thread with its own variable copy, enabling simultaneous access without interference
Focus Synchronization of resource access between multiple threads Isolating data between threads in multithreaded environments

Summary: In the earlier example, both ThreadLocal and Synchronized solve the problem, but ThreadLocal is more appropriate as it enables higher program concurrency.

ThreadLocal Internal Structure

Through the above learning, we’ve understood ThreadLocal’s functionality. Now let’s examine ThreadLocal’s internal structure to explore the principle behind its thread data isolation.

Common Misconceptions

Without examining the source code, one might guess ThreadLocal is designed like this: each ThreadLocal creates a Map, using the thread as Map’s key and the local variable to store as Map’s value, achieving local variable isolation for each thread. This is the simplest design method, and JDK’s earliest ThreadLocal was indeed designed this way, but it’s no longer the case.

Current Design

However, JDK later optimized the design. In JDK 8, ThreadLocal’s design is: each Thread maintains a ThreadLocalMap, where this Map’s key is the ThreadLocal instance itself, and value is the actual object to store. The specific process is:

  • Each Thread has an internal Map (ThreadLocalMap)
  • Map stores ThreadLocal objects (key) and thread variable copies (value)
  • Thread’s internal Map is maintained by ThreadLocal, which is responsible for getting and setting thread variable values from the map
  • For different threads, when retrieving copy values, other threads cannot access the current thread’s copy value, forming copy isolation without interference

Comparison

What are the benefits of JDK8’s design?

  • Each Map stores fewer Entry数量, as original Entry count was determined by Thread, now determined by ThreadLocal
    • In real development, Thread count far exceeds ThreadLocal count
  • When Thread is destroyed, ThreadLocalMap is also destroyed, as ThreadLocal is stored within Thread, disappearing with Thread destruction, reducing overhead.

ThreadLocal Core Method Source Code

Based on ThreadLocal’s internal structure, we continue analyzing its core method source code for deeper understanding of its operational principles. Besides constructors, ThreadLocal exposes the following 4 methods

Method Declaration Description
protected T initialValue() Return initial value of current thread’s local variable
public void set(T value) Return current thread’s bound local variable
public T get() Get current thread’s bound local variable
public void remove() Remove current thread’s bound local variable

Below is detailed source code analysis of these 4 methods (ThreadLocalMap section temporarily omitted for clarity, to be detailed in next knowledge point)

set Method

Code flow

  • First get current thread, and based on current thread get a Map
  • If retrieved Map is not empty, set parameter to Map (using current ThreadLocal reference as key)
  • If Map is empty, create Map for that thread and set initial value

get Method

Code execution flow

  • First get current thread, based on current thread get a Map
  • If retrieved Map is not empty, use ThreadLocal reference as key to get corresponding Entry from Map, otherwise go to step 4
  • If e is not null, return e.value, otherwise go to step 4
  • Map is empty or e is empty, get initial value via initialValue function, then create new Map using ThreadLocal reference and value as firstKey and firstValue

Summary: First get current thread’s ThreadLocal variable, if exists return value, if not exists create and return initial value

remove Method

Code execution flow

  • First get current thread, based on current thread get a Map
  • If retrieved Map is not empty, remove Entry corresponding to current ThreadLocal object

initialValue Method

This method returns the initial value of the thread-local variable.

  • This method is a lazy invocation method. From the above code, we see it executes when set hasn’t been called but get is called first, and only executes once.
  • This method’s default implementation directly returns null.
  • To get an initial value other than null, override this method. (Note: this is a protected method, obviously designed for subclass overriding)

Weak References and Memory Leaks

Some developers discover memory leaks when using ThreadLocal, guessing this relates to weak reference keys in Entry. This understanding is actually incorrect.

Let’s review the concepts involved in this problem before analyzing.

Memory Leak Related Concepts

Memory overflow: Insufficient memory for applicants.

Memory leak: Dynamically allocated heap memory in programs not released or unable to be released due to some reason, causing system memory waste, leading to slower program execution or even system crashes. Accumulated memory leaks will eventually cause memory overflow.

Weak Reference Related Concepts

Java has 4 reference types: strong, soft, weak, and phantom. This problem mainly involves strong and weak references:

Strong Reference (“Strong” Reference): The most common object reference. As long as a strong reference points to an object, the object is considered “alive” and garbage collector won’t collect it.

Weak Reference (WeakReference): Once garbage collector discovers objects with only weak references, regardless of current memory space availability, it will reclaim their memory.

If key uses strong reference, will memory leak occur?

Assuming ThreadLocalMap’s key uses strong reference, will memory leak occur?

ThreadLocal memory diagram at this point (solid lines represent strong references):

  • Assuming business code finishes using ThreadLocal, threadLocal Ref is collected
  • But because threadLocalMap’s Entry has strong reference to threadLocal, threadLocal cannot be collected.
  • Without manually deleting this Entry and CurrentThread still running, there’s always a strong reference chain threadRef->currentThread->threadLocalMap->entry, Entry won’t be collected (Entry includes ThreadLocal instance and value), causing Entry memory leak.

This means ThreadLocalMap’s key using strong reference cannot completely avoid memory leaks.

If key uses weak reference, will memory leak occur?

  • Similarly assuming business code finishes using ThreadLocal, threadLocal Ref is collected.
  • Since ThreadLocalMap only holds ThreadLocal’s weak reference, no strong reference points to threadlocal instance, so threadlocal can be smoothly GC collected, at this point Entry’s key=null.
  • But without manually deleting this Entry and CurrentThread still running, there’s also a strong reference chain threadRef->currentThread->threadLocalMap->entry->value, value won’t be collected, and this value will never be accessed, causing value memory leak.

This means ThreadLocalMap’s key using weak reference can also cause memory leaks.

Real Cause of Memory Leaks

Comparing these two situations, we find memory leak occurrence is unrelated to whether ThreadLocalMap’s key uses weak reference. So what’s the real cause of memory leaks?

Careful observers will notice both memory leak situations have two prerequisites:

  • Not manually deleting this Entry
  • CurrentThread still running

The first point is easy to understand - using ThreadLocal’s remove method to delete corresponding Entry after use avoids memory leaks.

The second point is more complex - since ThreadLocalMap is a Thread attribute referenced by current thread, its lifecycle matches Thread’s. After using ThreadLocal, if current Thread also finishes execution, ThreadLocalMap will naturally be GC collected, fundamentally avoiding memory leaks.

In summary, ThreadLocal memory leak root cause is: because ThreadLocalMap’s lifecycle matches Thread’s, not manually deleting corresponding key will cause memory leaks.

Why Use Weak References?

Based on the analysis, we know: regardless of which reference type ThreadLocalMap’s key uses, memory leaks cannot be completely avoided, unrelated to weak reference usage.

Two ways to avoid memory leaks:

  • Using ThreadLocal’s remove method to delete corresponding Entry after use
  • Current Thread also finishes running after using ThreadLocal

Compared to the first method, the second is obviously harder to control, especially with thread pools where threads don’t destroy but return to the pool.

This means as long as you remember to call remove after using ThreadLocal, regardless of whether key is strong or weak reference, there won’t be problems.

So why use weak references for keys?

Actually, in ThreadLocalMap’s set/getEntry methods, when key is null (ThreadLocal is null), it will set value to null.

This means after using ThreadLocal, with CurrentThread still running, even if you forget to call remove, weak references provide an extra guarantee over strong references: weakly referenced ThreadLocal will be collected, corresponding value will be cleared on next ThreadLocalMap set, get, or remove method call, thus avoiding memory leaks.

public void set(T value) {
    Thread t = Thread.currentThread();
    ThreadLocal.ThreadLocalMap map = getMap(t);
    if (map != null)
        // Called ThreadLocalMap's set method
        map.set(this, value);

        createMap(t, value);

ThreadLocal.ThreadLocalMap getMap(Thread t) {
    return t.threadLocals;
}

void createMap(Thread t, T firstValue) {
    // Called ThreadLocalMap's constructor
    t.threadLocals = new ThreadLocal.ThreadLocalMap(this, firstValue);

This method we analyzed earlier - sets current thread’s bound local variable

  • First get current thread, based on current thread get a Map
  • If retrieved Map is not empty, set parameter to Map (using current ThreadLocal reference as key) (here calls ThreadLocalMap’s set method)
  • If Map is empty, create Map for that thread and set initial value (here calls ThreadLocalMap’s constructor)

This code involves two ThreadLocalMap methods, let’s analyze these two methods

Constructor

ThreadLocalMap(ThreadLocal firstKey, Object firstValue)

Constructor first creates Entry array of length 16, then calculates firstKey’s corresponding index, stores to table, sets size and threshold.

Key analysis: int i = firstKey.threadLocalHashCode & (INITIAL_CAPACITY - 1)

About: threadLocalHashCode

Here an AtomicInteger type is defined, each time getting current value plus HASH_INCREMENT, HASH_INCREMENT = 0x61c88647, related to Fibonacci sequence (golden ratio), mainly to ensure hash codes are evenly distributed in 2^n power arrays, i.e., Entry[] table, minimizing hash conflicts.

About & (INITIAL_CAPACITY - 1)

Hash calculation uses hashCode & (size-1) algorithm, equivalent to more efficient hashCode % size modulo operation. Because of this algorithm, size must be power of 2, ensuring minimal hash conflicts while preventing index overflow.

Get Method

Code execution flow

  • First calculate index i based on key, then find Entry at that position,
  • If Entry exists and key equals passed key, directly assign new value to this Entry,
  • If Entry exists but key is null, call replaceStaleEntry to replace this null-keyed Entry,
  • Continuously loop detection until encountering null position, if still no return during loop, create new Entry at this null position, insert, increment size by 1.

Finally call cleanSomeSlots to clean null-keyed Entries, return whether Entries were cleaned, then check if sz >= threshold for rehash conditions, if met call rehash function for full table scan cleanup.

Linear Probing Hash Conflict Resolution

This method probes next address sequentially, inserts when empty address found, overflows if entire space has no empty addresses.

Example: assuming current table length 16, if calculated key hash is 14, if table[14] already has value and its key differs from current key, hash conflict occurs. Then 14+1=15, check table[15], if still conflicts return to 0, check table[0], and so on until insertion possible.

Following the above description, Entry table can be considered a circular array.

User Usage Scenario 1

Besides source code ThreadLocal usage scenarios, do you have your own usage scenarios?

Previously after launch, we found some users’ dates were incorrect. Investigation revealed SimpleDataFormat was the culprit. When using SimpleDataFormat’s parse() method, internal Calendar object called Calendar.clear() then Calendar.add(). If one thread called add() then another called clear(), the parse() method would parse incorrect time.

Actually solving this is simple - let each thread new its own SimpleDataFormat. But with 1000 threads, should we new 1000 SimpleDataFormats?

So we used thread pool plus ThreadLocal wrapping SimpleDataFormat, calling initialValue to give each thread a SimpleDataFormat copy, solving thread safety issues and improving performance.
