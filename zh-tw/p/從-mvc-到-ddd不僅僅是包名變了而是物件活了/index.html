從 MVC 到 DDD：不僅僅是包名變了，而是「物件」活了

引言

在學習 DDD（領域驅動設計）時，很多人會被複雜的概念勸退。但回歸本質，我們可以將 DDD 理解為 MVC 的「超進化增強版」。它在 MVC 的基礎上，透過更清晰的職責劃分和邏輯解耦，解決了系統在業務複雜後的「臃腫」痛點。

一、 核心心法：從「找說明書」到「問當事人」

在傳統的 MVC（貧血模型） 中，實體類別（Entity/PO）往往只是資料的載體，像是一張白紙。所有的業務邏輯都堆積在 Service 層。

  • 痛點： Service 越來越大，邏輯散亂，維護起來像是在一坨亂麻中找線頭。

在 DDD（充血模型） 中，資料和業務邏輯是寫在一起的。

  • 轉變： 實體類別變成了有生命、有原則的「業務專家」。

  • 例子： 比如「訂單取消」邏輯。

    • MVC： OrderService 取得 Order 資料，判斷狀態，修改狀態，存盤。
    • DDD： Order 實體內部有一個 cancel() 方法，它自己判斷能不能取消。

要點： DDD 的好處是邏輯高度內聚。一旦業務邏輯有變化，你只需要修改對應的領域模型物件，而不是去翻幾千行的 Service。

二、 架構連連看：DDD 與 MVC 的映射關係

我們可以把 DDD 的流程簡單理解為：

Controller $\rightarrow$ Application Service $\rightarrow$ Domain Model $\rightarrow$ Repository (Impl $\rightarrow$ Mapper)

為了方便理解，我們可以看這張對比表：

層次 DDD 命名 MVC 對應 職責增強點
介面層 Interfaces Controller 僅負責協議轉換（REST/JSON），不做任何業務。
應用層 Application Service (輕) 指揮官： 不寫 if-else，只負責編排領域物件幹活。
領域層 Domain Entity (重) 核心： 包含業務規則，資料與邏輯共存。
基礎層 Infrastructure DAO / Mapper 外掛化： 蔽蓋資料庫細節。Repository 是介面，Mapper 是實現。

三、 為什麼 DDD 的包變多了？（關於解耦的真相）

你會發現 DDD 引入了 ApplicationService、Domain Model、Repository 等。這看似繁瑣，實則是為了實現兩級核心解耦：

1. 業務邏輯與流程編排解耦 (Application vs Domain)

  • Application 層只關心「第一步做什麼，第二步做什麼」。
  • Domain 層只關心「這個業務規則是什麼」。
  • 收益： 業務邏輯可以脫離環境進行單元測試，不需要啟動資料庫，速度極快。

2. 業務邏輯與儲存技術解耦 (Domain vs Infrastructure)

  • 領域模型只認 Repository 介面，不關心底層是 MyBatis、JPA 還是 Redis。
  • 收益： 就算資料庫從 MySQL 換成 MongoDB，你的核心業務邏輯（Domain 層）一個字都不用改。

四、 模型的三大成員（戰術建模）

在 DDD 的領域層中，並不是所有的類別都是一樣的。為了讓業務邏輯組織得更科學，我們通常將模型分為以下三類：

1. 實體 (Entity) —— 有唯一標識

實體最核心的特徵是身分（Identity）。即使它的所有屬性都變了，它依然是那個物件。

  • 定義： 具有唯一標識（ID）的物件。即使兩個訂單的商品、價格完全一樣，只要 ID 不同，它們就是兩個不同的東西。
  • 特點： 有生命週期（建立、修改、狀態流轉、存檔）。
  • 例子： Order（訂單）、User（使用者）。

情境： 訂單建立時，狀態是「待支付」，收貨地址是「上海」；支付後，狀態變成了「已支付」，地址改成了「北京」。

核心： 雖然狀態和地址都變了，但由於它的 OrderNo (或 ID) 沒變，我們依然認為它是同一個訂單。

程式碼特徵： 內部一定有一個 private Long id; 或 private String orderNo;，且邏輯判斷時使用這個 ID 進行 equals()。

2. 值物件 (Value Object) —— 只有屬性，沒有 ID

值物件就像是「描述性的文字」。如果兩個值物件的所有屬性都一樣，那它們就是同一個東西。

  • 定義： 沒有 ID，透過屬性來定義。如果兩個物件的屬性值完全相同，它們就可以互相替換。
  • 特點： 不可變性 (Immutable)。如果你要改一個地址，不是改原地址物件的屬性，而是直接換一個新的地址物件。
  • 例子： Address（省市區街道組合）、Money（幣種+金額）。

情境： 訂單裡有一個收貨地址：{省: "廣東", 市: "深圳", 街道: "南山區"}。

核心： 我們並不關心這個地址物件的「身份證」，我們只關心它填的是哪。如果兩個訂單都發往這個地方，那這兩個地址物件在邏輯上是等價的。

程式碼特徵：

  1. 沒有 ID。
  2. 不可變性 (Immutable)：如果你想改地址，不是呼叫 address.setStreet("福田區")，而是直接給 Order 換一個新的 Address 物件：order.changeAddress(new Address("廣東", "深圳", "福田區"))。
  • 程式碼小技巧：

3. 聚合根 (Aggregate Root) —— 組織管理者

  • 定義： 一組關聯物件的「大老闆」。外部只能透過聚合根來訪問它內部的成員。
  • 職責： 維護業務完整性（不變量）。
  • 例子： 在訂單業務中，Order 是聚合根，OrderItem（訂單項）是它內部的成員。

情境： 一個訂單裡有 3 個商品（訂單項）。

核心：

  1. 外面的 Service 不能直接繞過 Order 去修改某個 OrderItem 的價格。
  2. 必須呼叫 order.adjustItemPrice(itemId, newPrice)。由 Order 這個「大老闆」來決定這個操作合不合法（比如：訂單如果已發貨，老闆就會拒絕修改價格）。

生命週期： 聚合根負責其內部成員的生死。如果 Order 從資料庫裡被刪除了，它內部的 OrderItem 必須跟著一起消失。

禁令： 你絕對不能在 Controller 裡直接呼叫 OrderItemMapper 去改某一行商品的價格，必須透過 Order.updateItemPrice()。

4. 總結對比

模型類型 是否有唯一 ID 屬性完全相同時 修改方式 舉例
實體 (Entity) 是 依然是兩個獨立的物件 透過方法修改屬性 使用者(User)、商品(Product)
值物件 (VO) 否 視為同一個物件 整體替換（不可變） 貨幣(Money)、地址(Address)
聚合根 (AR) 是 (同實體) 負責協調內部所有成員 訂單(Order)、論壇主題(Topic)

五、 模型轉換：每一層都有自己的「臉」

為了實現「解耦」，每一層使用的模型其實是不一樣的。雖然寫起來麻煩，但能有效防止資料庫邏輯污染業務邏輯：

  1. DTO (Data Transfer Object): 介面層使用。長得像表單，欄位可能很少。
  2. Domain Entity: 領域層使用。這是你寫的那個「活的物件」，帶業務邏輯。
  3. PO (Persistent Object): 基礎設施層使用。長得和資料庫表一模一樣。

// 實體類別：Order.java
public class Order {// <--- 這是一個【聚合根】
    private Long orderId;// <--- 聚合根也是實體，有唯一 ID
    private List<OrderItem> items;// <--- 訂單項是【實體】，但受聚合根管理
    private OrderStatus status; // CREATED, PAID, CANCELLED, SHIPPED
    private Address address; // <--- 收貨地址是【值物件】，沒有 ID，整體替換
    private BigDecimal totalPrice;

	// 聚合根的方法：確保業務完整性
    public void changeAddress(Address newAddress) {
        if (this.status == OrderStatus.SHIPPED) {
            throw new BusinessException("發貨後不能改地址");
        }
        this.address = newAddress; 
    }

    // --- 業務邏輯：新增訂單的構造約束 ---
    public Order(List<OrderItem> items) {
        if (items == null || items.isEmpty()) {
            throw new BusinessException("訂單至少需要一個商品");
        }
        this.items = items;
        this.status = OrderStatus.CREATED;
        this.totalPrice = calculateTotal(); // 內部邏輯，自動計算總價
    }

    // --- 業務邏輯：取消訂單 ---
    public void cancel() {
        if (this.status == OrderStatus.SHIPPED) {
            throw new BusinessException("已發貨訂單無法取消");
        }
        this.status = OrderStatus.CANCELLED;
    }

    private BigDecimal calculateTotal() {
        return items.stream().map(OrderItem::getPrice).reduce(BigDecimal.ZERO, BigDecimal::add);
    }
  
    // 省略 Getter...
}

// 倉庫介面：OrderRepository.java (只定義業務行為)
public interface OrderRepository {
    void save(Order order);
    Order findById(Long id);
}

@Service
public class OrderApplicationService {
    @Autowired
    private OrderRepository orderRepository;

    // 新增訂單流程
    @Transactional
    public void createOrder(OrderCreateDTO dto) {
        // 呼叫領域模型進行建立
        Order order = new Order(dto.getItems());
        // 呼叫倉庫進行持久化
        orderRepository.save(order);
    }

    // 取消訂單流程
    @Transactional
    public void cancelOrder(Long id) {
        // 1. 透過倉庫找到那個「活的」物件
        Order order = orderRepository.findById(id);
        // 2. 發送指令給物件：你自己取消吧
        order.cancel(); 
        // 3. 儲存修改後的狀態
        orderRepository.save(order);
    }
}

@Repository
public class OrderRepositoryImpl implements OrderRepository {
    @Autowired
    private OrderMapper orderMapper; // MyBatis 的 Mapper

    @Override
    public void save(Order order) {
        // 1. 轉換：把領域物件 Order 轉成 資料庫表物件 OrderPO
        OrderPO po = convertToPO(order);
        // 2. 落地：呼叫 Mapper 執行 SQL
        if (po.getId() == null) {
            orderMapper.insert(po);
        } else {
            orderMapper.updateStatus(po);
        }
    }

    @Override
    public Order findById(Long id) {
        OrderPO po = orderMapper.selectById(id);
        // 3. 還原：把資料庫記錄轉回成帶有業務能力的領域物件
        return convertToEntity(po);
    }
}

@RestController
@RequestMapping("/api/orders")
public class OrderController {
    @Autowired
    private OrderApplicationService orderAppService;

    @PostMapping("/create")
    public Response create(@RequestBody OrderCreateDTO dto) {
        orderAppService.createOrder(dto);
        return Response.ok();
    }

    @PostMapping("/{id}/cancel")
    public Response cancel(@PathVariable Long id) {
        orderAppService.cancelOrder(id);
        return Response.ok();
    }
}
  1. 邏輯在哪裡？
  • 判斷「能否取消」 的邏輯在 Order 類別裡（領域層）。
  • 「先查出來、再改、再存」 的步驟在 OrderApplicationService 裡（應用層）。
  1. 解耦在哪裡？
  • ApplicationService 根本不知道資料庫是 MySQL 還是文字檔，因為它只呼叫了 orderRepository.save()。
  • 真正的 SQL 語句全被物理隔離在 Infrastructure 層的 Mapper 中。
  1. 為什麼這麼寫？
  • 如果未來「取消訂單」的規則變了（比如支付超過30分鐘不能取消），你只需要改 Order 實體類別一個地方，其他三層程式碼動都不用動。這就是 DDD 應對複雜業務的威力。

七、總結：DDD 到底增強了什麼？

  1. 高內聚： 誰的資料誰負責，業務邏輯不再「流產」在各個 Service 裡。
  2. 易維護： 程式碼結構即業務藍圖，看一眼領域物件就知道業務規則。
  3. 外掛化： 資料庫和外部服務都變成了「外掛」，系統更健壯。

八、結語

DDD 並不是要推翻 MVC，而是在業務複雜到一定程度時，給開發者的一把「手術刀」，讓我們能把糾纏在一起的邏輯優雅地拆解開。

一句話總結： MVC 讓我們把程式碼放對位置，而 DDD 讓我們讓物件「活」了過來。
