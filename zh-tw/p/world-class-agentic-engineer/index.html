引言

你是個開發者。你每天都在用 Claude 和 Codex CLI，每天在想自己到底有沒有把這些 Agent 的真正潛力榨出來。偶爾你看到它做一些蠢到不可思議的事，而你又完全不理解為什麼外面那些人看起來像是在造虛擬火箭，自己卻連兩塊石頭都疊不起來。

你覺得是自己用的 harness 不對、外掛不夠好、終端設定有問題。你試了 beads、opencode、zep，你的 CLAUDE.md 寫了 26000 行。但無論你做什麼，都到不了天堂的門口，只能乾看著別人在雲端嬉戲。

這篇文章，就是你要的飛升指南。

順便說一句，我沒站隊。當我說 CLAUDE.md，也包括 AGENT.md；說 Claude，也包括 Codex。我兩個都用得非常深入。

過去幾個月裡，我觀察到的最有趣的現象之一就是：幾乎沒有人真正知道如何把 Agent 的能力榨到極致。

一小撮人似乎能讓 Agent 成為世界構建者，而其他人都在掙扎，面對市場中五花八門的工具患上選擇分析困難症——心想只要找到正確的包、技能或 harness 組合，就能解鎖 AGI。

今天我想把這一切都打破，給你們一句簡單而誠實的話：你不需要最新的 agentic harness，不需要裝一百萬個套件，絕對不用覺得自己必須看一百萬個東西才能追上潮流。 實際上，你的熱情可能弊大於利。

我不是來旅遊的——我從 Agent 還幾乎寫不出程式碼的年代就開始用了。我試過了所有的套件、harness 和範式。我搭建過 agentic 工廠來生成訊號、構建基礎設施和資料流水線——不是"玩具專案"，是真正在生產中執行的真實用例。然後經歷了這一切之後……

今天，我執行的設定幾乎是你能想像的最簡潔版本，卻做出了我做過的最開創性的工作——只用最基礎的 CLI（Claude Code 和 Codex），加上對 agentic engineering 的幾個基本原則的理解。

理解"世界在狂奔"

首先，我想說基礎模型公司正在進行一代人級別的競速，如你所見，它們不會很快慢下來。每一次"Agent 智慧"的進化都會改變你與它們協作的方式，因為 Agent 被工程化得越來越願意服從指令。

就在幾個版本之前，如果你在 CLAUDE.md 裡寫讓它做任何事之前先讀 READ_THIS_BEFORE_DOING_ANYTHING.md，它 50% 的時間會直接甩你一臉然後我行我素。今天，它對大多數指令都服從了，甚至對複雜的巢狀指令也是如此——比如你可以大致說"讀 A，然後讀 B，如果是 C，則讀 D"，它基本上都會樂意照辦。

我想說的是：最重要的原則是認識到每一代新 Agent 都會迫使你重新思考什麼是最優的，這就是為什麼少即是多。

當你使用許多不同的函式庫和 harness 時，你把自己鎖進了一個可能在未來幾代 Agent 中根本不存在的"解決方案"。此外，你知道 Agent 最熱情、最大的用戶是誰嗎？沒錯——是前沿公司的內部員工，擁有無限的 Token 預算和真正的、最新的模型。你懂這意味著什麼嗎？

這意味著如果某個真實問題真的存在，並且有好的解決方案，前沿公司會是這個方案最大的用戶。那你知道他們接下來會做什麼嗎？他們會把那個方案融入自己的產品。你想，公司怎麼會讓別人的產品來解決真正的痛點並依賴外部呢？你知道我怎麼知道這是真的？看看 skills、memory harness、subagents 這些——它們都是從真實問題的"解決方案"開始，經過實際驗證後被認為真正有用，最終才出現的。

所以，如果某樣東西真的具有開創性，而且能以一種有意義的方式擴充套件 agentic 用例，它遲早會被基礎模型公司納入基礎產品。 相信我，前沿公司在狂飆。所以放鬆，你不需要裝任何東西或依賴任何外部工具來做出你最好的工作。

上下文是一切

不是開玩笑。上下文是一切。 這就是使用一大堆外掛和外部依賴的另一個問題——你會遭遇上下文膨脹（context bloat），說白了就是 Agent 被太多資訊淹沒了！

給我用 Python 寫個 Hangman 遊戲？簡單。等等，這個 26 個工作階段前關於"管理記憶體"的備註是什麼？啊，是之前生成了太多子程序，那個螢幕掛掉了的 71 個工作階段前的事情。總是要寫筆記？好，沒問題……但這些和 Hangman 有什麼關係？

你明白了吧。你想給 Agent 恰恰好完成它任務所需的資訊，不多不少！ 你越能控制好這一點，Agent 的表現就越好。一旦你開始引入各種奇怪的記憶體系統、外掛，或者太多命名混亂、被隨意呼叫的技能，你就是在給 Agent 同時發製造炸彈的說明書和烘焙蛋糕的食譜，但你實際只想要一首關於紅杉森林的小詩。

所以，我再次強調——卸掉所有依賴，然後……

做那些真正有效的事

精確描述實作目標

記得上下文是一切的道理嗎？

記得你想給 Agent 注入恰好完成它任務所需的資訊、不多不少？

確保這一點的第一條路徑就是：把研究（Research）和實作（Implementation）分開。 你對 Agent 的要求必須極其精確。

這是你不精確時發生的事：“去，構建一個認證系統。“Agent 必須去研究——什麼是認證系統？有哪些可選方案？各自的優缺點？於是它去網上扒拉自己其實不需要的資訊，上下文裡塞滿了大量不同方向的實作細節。等到真要實作的時候，它搞混或幻覺出不必要、不相關的實作細節的機率就大大增加了。

反過來，如果你說：“用 JWT + bcrypt-12 密碼雜湊實作認證，帶 7 天到期的 refresh token 輪換……“那麼它不必研究其他方案。它知道你到底想要什麼，因此可以將上下文塞滿實作細節。

當然你不會總是有實作細節。你經常不知道究竟哪種選擇最好——有時候你甚至想把選擇實作方案的工作也交給 Agent。這時候怎麼辦？簡單——建立一個研究任務來探索各種實作的可能性，然後要麼自己做決定，要麼讓一個 Agent 決定選哪個實作方案，最後再用一個全新上下文的 Agent 去實作。

一旦你開始按這個思路思考，你就會在流程中發現那些 Agent 被沒必要地汙染了上下文的地方。然後你可以在 agentic 工作流中建起圍牆，把不必要的資訊抽象掉，只讓 Agent 獲取出色完成其任務所需的具體上下文。記住，你擁有的是一個非常有才華和聰明的團隊成員，它知道宇宙中所有型別的球——但除非你告訴它你想讓它專注於設計一個人們可以跳舞和享受美好時光的空間，它會一直跟你講擁有球形物體的所有好處。

諂媚偏差的設計侷限

沒人想用一個不斷吐槽自己、總說自己錯了、或者乾脆無視自己指令的產品。因此，這些 Agent 的本質就是試圖同意你、做你想讓它做的事。

如果你給它一個指令——每三個詞後面加一個"開心”，它會盡力照做——大多數人都理解這一點。它願意聽話恰恰是讓它成為如此有趣產品的原因。但這帶來了非常有趣的特徵——這意味著如果你說"幫我在程式碼庫中找一個 Bug”，它一定會給你找一個 Bug——哪怕它得自己造一個。 因為什麼？因為它太想聽你的指令了！

大多數人都忙著抱怨 LLM 幻覺或編造不存在的東西，卻沒意識到問題出在自己身上。 如果你要求一個東西，它一定會給你——哪怕它得稍微歪曲事實！

那你該怎麼辦？我發現**“中性"提示詞很管用**，也就是不讓 Agent 偏向某個結果。比如，我不說"在資料庫裡找 Bug”，而是說"搜尋整個資料庫，嘗試緊跟每個元件的邏輯，報告所有發現。”

這種中性提示詞有時會發現 Bug，有時只會就事論事地陳述程式碼如何執行。但它不會讓 Agent 產生"一定有個 Bug"的偏見。

我另一種處理諂媚的方法是反過來利用它。 我知道 Agent 在想討好我、想遵循我的指令，也知道我可以讓它向某一方向偏移。這是我的方法：

  1. Bug 發現 Agent：我告訴它低影響的 Bug +1 分，有些影響的 +5 分，嚴重影響的 +10 分。這個 Agent 變得極度熱情，識別出各種型別的 Bug（甚至包括不是 Bug 的那些）。我把這看作所有可能 Bug 的超集。

  2. 對抗 Agent：對於每一個它能證明不是 Bug 的條目，它獲得該條目的分；但如果證明錯了，它將被扣掉該條目的 2 倍分。所以這個對抗 Agent 會拼命嘗試反駁 Bug（甚至包括真正的 Bug），但會帶有一點謹慎。我把這看作是實際真實 Bug 的子集。

  3. 裁判 Agent：我騙裁判 Agent 說我有正確的標準答案。評判正確 +1 分，評判錯誤 -1 分。裁判說什麼就是真相，然後我再自己查證。絕大多數情況下這種方法有著驚人的高準確率——偶爾確實還會出錯，但這整體上是一個近乎完美的流程。

也許你會發現只用 Bug 發現 Agent 就夠了，但這個方法對我有效，因為它利用了每個 Agent 被硬編碼要做的事——想要討好。

怎麼知道什麼真正有用？

這個問題看起來很難，需要你深入研究、站在 AI 更新的最前沿，但實際上非常簡單……如果 OpenAI 和 Claude 都實作或收購了實作了某個功能的東西……那它大機率是有用的。

  • 注意到 skills 現在到處都是，並且成為 Claude 和 Codex 官方文件的一部分了嗎？
  • 看到 OpenAI 收購 OpenClaw 了嗎？
  • 看到 Claude 立刻加入了記憶、語音和遠端工作了嗎？
  • 那 planning（計劃）呢？還記得一群人發現先做計劃再實作真的很有用，然後它變成了一個核心功能嗎？

是啊……那些都有用！

還記得無休止的 stop-hook 曾經多有用嗎，因為 Agent 那時有多不願做長時間工作……然後 Codex 5.2 釋出，那一夜之間就消失了？是啊……

這就是你需要知道的全部。如果某個東西真的重要且有用，Claude 和 Codex 就會實作它們！所以你不用太擔心使用"新東西"或熟悉"新東西”。你甚至不用"跟上潮流"。

就是每隔一段時間更新你的命令列工具，讀一讀新增了哪些功能。這已經遠遠足夠了。

壓縮、上下文與假設

一個讓你在使用 Agent 過程中會意識到的大坑：有時候它們看起來像地球上最聰明的存在，而另一些時候你簡直無法相信自己上當了。

主要區別在於：Agent 是否需要做出任何"假設"或"填補空白"。 到今天為止，它們在"連線點"、“填補空白"或做假設方面仍然非常糟糕。每當它們那麼做的時候，立刻就會看出它們顯然已經走偏了。

CLAUDE.md 中最重要的規則之一，就是關於如何處理獲取上下文的規則。無論何時，只要 Agent 讀取 CLAUDE.md（這總是在壓縮之後），就讓它第一個讀那條規則。在上下文獲取規則中，幾條簡單的指令可以產生大作用——重讀你的任務計劃，並在繼續之前重讀與任務相關的檔案。

讓 Agent 知道任務該何時結束

我們對"任務什麼時候算完成"有比較強的直覺。對 Agent 來說，當前智慧最大的問題是：它知道怎麼開始一個任務，但不知道怎麼結束。

這常常導致非常令人沮喪的結果——Agent 實作一大堆樁（stubs），然後就算交差了。

測試對 Agent 來說是一個非常非常好的里程碑，因為它們是確定性的，你可以設非常清晰的期望。“除非這 X 個測試全部通過，否則你的任務不算完成；而且不準你編輯這些測試。”

然後你只需稽核測試，一旦所有測試通過，就可以安心了。你當然可以自動化這一步，但要點是——記住"任務的終點"對人類來說非常自然，對 Agent 來說卻不然。

你知道還有什麼是最近變得可行的任務終點嗎？截圖 + 驗證。 你可以讓 Agent 一直實作到所有測試通過，然後讓它截圖，並在截圖結果上驗證"設計或行為”。這讓你可以讓 Agent 不斷迭代、向你想要的設計靠攏，而不用擔心它在第一次嘗試後就停了！

這自然延伸出來的做法是建立一個與 Agent 的任務合約，並嵌入到規則中。比如，{TASK}_CONTRACT.md 規定了在允許結束工作階段之前必須完成的事項。在合約中，你指定你的測試、截圖和其他在確認任務可以結束之前需要完成的驗證！

永遠執行的 Agent

我常被問到的一個問題是：那些人怎麼能讓 Agent 跑 24 小時還不跑偏？

這裡有個非常簡單的辦法。建立一個 stop-hook，阻止 Agent 在 {TASK}_CONTRACT.md 的所有部分完成之前結束工作階段。

如果你有 100 個設計良好的合約，包含了你想要構建的確切內容，那麼你的 stop-hook 會阻止 Agent 在這 100 個合約全部完成之前終止——包括所有需要執行的測試和驗證！

專業提示： 我不認為長時間執行的 24 小時工作階段是做事的"最佳方式"。部分原因是，這在架構上本身就強制了上下文膨脹，將來自不相關的合約引入同一工作階段！所以，我不推薦。

一個更好的 Agent 自動化方式——每個合約一個新工作階段。 當你需要做事時建立合約。搞一個編排層來處理：每當"有事要做"就建立新合約，並為那個合約建立新工作階段來工作。這會徹底改變你的 agentic 體驗。

迭代，迭代，再迭代

如果你僱了一個行政助理，你指望 TA 第一天就知道你的日程安排嗎？或者你怎麼喝咖啡？你吃晚飯是 6 點而不是 8 點？顯然不是。偏好是隨著時間逐步建立的。

你的 Agent 也一樣。從極簡開始。忘掉那些複雜的結構或 harness。給基礎 CLI 一個機會。 然後，逐步加上你的偏好。怎麼做？

Rules（規則）

如果你不想讓你的 Agent 做某件事，把它寫成一條規則。然後在 CLAUDE.md 中讓 Agent 知道這條規則。類似：“在你寫程式碼之前，讀一下 coding-rules.md。”

規則可以巢狀，規則可以帶條件！“如果你在寫程式碼，讀 coding-rules.md；如果你在寫測試，讀 coding-test-rules.md。如果測試在失敗，讀 coding-test-failing-rules.md。”

你可以建立任意邏輯分支的規則來遵循，Claude（和 Codex）會愉快地跟著走——只要在 CLAUDE.md 中做了清晰的說明。

這是我給的第一條實用建議： 把 CLAUDE.md 當作一個邏輯化的、巢狀的目錄，指明在給定的場景和預期結果下去哪裡找上下文。它應該盡量極簡，只包含 IF-ELSE——去哪裡尋找上下文的邏輯。

如果你看到 Agent 做了讓你不認可的事，把它加為規則，告訴 Agent 在做那件事之前先讀那條規則，那麼它幾乎肯定不會再做。

Skills（技能）

Skills 像 Rules，但區別在於 Rules 更適合編碼偏好，Skills 更適合編碼配方（recipes）。如果你有特定的做事方式——想要某件事以特定方式完成——那你應該把它嵌入一個 Skill 裡。

事實上，人們經常抱怨自己不知道 Agent 會怎麼解決某個問題，這很可怕。那好，如果你想要一種讓這件事變得確定性的方法，讓 Agent 研究一下它會怎麼解決那個問題，然後寫成一個 Skill。 你會看到 Agent 處理那個問題的方法，你可以在它真正遇到那個問題之前糾正或改進。

你怎麼讓 Agent 知道這個 Skill 存在？對！用 CLAUDE.md 說：“當你看到這種場景、需要處理這件事時，讀一下這個 SKILL.md。”

管理 Rules 和 Skills

你肯定想繼續新增 Rules 和 Skills 來給你的 Agent。這是賦予它個性和偏好的記憶。其他幾乎所有東西都是過度設計。

一旦你開始這樣做，Agent 對你來說就會像魔法一樣。它會按照"你想要的方式"做事。然後你終於會覺得自己"真正懂了"agentic engineering。

然後……你會發現效能又開始惡化了。 怎麼回事？！

簡單。隨著你新增越來越多的 Rules 和 Skills，它們開始互相矛盾，或者 Agent 開始有太多的上下文膨脹。如果你在 Agent 開始程式設計之前需要它讀 14 個 Markdown 檔案，它就有了同樣的問題——大量無用的資訊。

那麼，你怎麼辦？

你清理。 你告訴 Agent 去"做一次 spa"，整合 Rules 和 Skills，透過問你的更新偏好來消除矛盾。

然後魔法又回來了。

就是這樣。這真的是祕密。保持簡單，用 Rules 和 Skills 和 CLAUDE.md 作為目錄，同時宗教般虔誠地關注它們的上下文和設計侷限。

承擔你的結果

今天沒有一個 Agent 是完美的。你可以把大量的設計和實作委派給 Agent，但你得對結果負責。

所以小心行事……並享受樂趣！玩來自未來的玩具太快了（當然，用它們來做嚴肅的事）！
