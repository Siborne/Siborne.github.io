技術踩坑記錄：Git 大倉庫克隆網路中斷與 SSH 破局方案

克隆大型倉庫時遭遇 HTTP/2 流中斷、SSL 連線重置？本文從排查過程到原理剖析，最終透過 SSH 協定替代 HTTPS 一勞永逸解決 Git 大倉庫克隆的網路傳輸問題。

Computer Tools
简体中文 English 日本語

1. 問題背景

在嘗試克隆大型開源專案 taichi-project/anyagent 時，終端頻繁出現由於網路層斷開導致克隆失敗的報錯。

初始報錯跡象：執行基礎 git clone 時，資料拉取到一半突然中斷：

error: RPC failed; curl 92 HTTP/2 stream 7 was not closed cleanly: CANCEL (err 8) fatal: early EOF

問題實質：這是典型的 Git 網路傳輸中斷現象。目標倉庫體積較大（或包含較多歷史記錄），透過當前網路代理環境（v2rayN）拉取時，HTTP/2 資料流被意外強行掐斷。

2. 嘗試過的解決方案

2.1 淺克隆（失敗）

執行 git clone --depth 1 https://... 試圖減少下載體積。

結果：物件數確實減少了，但依然在中途斷開，報錯演變為：

curl 56 OpenSSL SSL_read: SSL_ERROR_SYSCALL, errno 0

分析：這說明不僅僅是檔案大小問題，底層 HTTPS 連線在資料傳輸中途被防火牆或代理軟體的 SSL 機制物理切斷了。

2.2 配置本機代理環境（部分有效）

查閱本地 v2rayN 代理配置，發現混合埠為 10808。嘗試在 PowerShell 中注入臨時環境變數 $env:HTTP_PROXY，或考慮開啟 Tun 模式接管全域流量。

此方案雖然觸及了網路連通性的根本，但 HTTP 代理在面對極大資料流的持續傳輸時依然不穩定，且代理規則容易與系統級網路配置發生衝突。

3. 原理剖析：HTTP(S) 與 SSH 的差異

HTTP/HTTPS 協定

  • 運作機制：依賴標準 Web 埠（80/443），資料傳輸受限於本機網路代理規則（PAC、系統代理或命令列環境變數）。
  • 優點：門檻極低，任何人拿到 URL 就能直接下載公開倉庫。
  • 缺點：對網路環境極為敏感。經過複雜代理節點時，極易受到中間人證書替換（引發 SSL 解析錯誤）或大流量快取溢位的影響，導致連線重置。

SSH 協定

  • 運作機制：執行在獨立的 TCP 22 埠，採用非對稱加密（公鑰+私鑰）機制。本機私鑰與 GitHub 伺服器上的公鑰配對成功後，建立端到端加密隧道。
  • 優點：極其穩定且安全，直接穿透或繞過絕大多數針對 HTTP 的應用層代理和審查機制，免疫 curl 相關的網路阻斷。
  • 缺點：配置門檻較高，需事先生成金鑰對並在平臺完成身份繫結，且與物理裝置強繫結。

4. 為什麼 HTTP 失敗，而 SSH 成功？

結合本次排錯過程，根本原因在於代理軟體對不同協定資料流的處理機制差異：

  1. HTTPS 被代理「夾斷」：使用 HTTPS 克隆時，流量被強制引導至代理軟體的 10808 埠。代理節點在處理持續不斷的大型 Git 物件流時，可能觸發了超時丟棄機制，或本地 OpenSSL 與代理伺服器之間的證書驗證出現瞬間斷層，導致系統強制 SYSCALL 中斷。
  2. SSH 的「免檢通行」：切換到 SSH 協定後，終端不再使用系統 HTTP 代理路由，而是直接透過 22 埠向遠端發起握手。金鑰的硬性背書使這條加密隧道足夠底層且堅固，不再受上層 Web 代理規則干擾，從而保障大資料量的完整傳輸。

5. 最終方案：SSH 完整配置步驟

適用於 Windows PowerShell。

5.1 生成本機 SSH 金鑰 

1

ssh-keygen -t ed25519 -C "你的郵箱@example.com"
  • 按回車接受預設儲存路徑（~/.ssh/id_ed25519）
  • 提示輸入密碼時，直接按兩次回車留空，後續拉取程式碼無需額外輸密碼。

5.2 複製公鑰內容 

1

Get-Content ~/.ssh/id_ed25519.pub | Set-Clipboard

如果使用預設 RSA 加密而非 ed25519，則檔案是 ~/.ssh/id_rsa.pub。

5.3 繫結公鑰到 GitHub

  1. 瀏覽器登入 GitHub，點選右上角頭像 → Settings
  2. 左側選單選擇 SSH and GPG keys
  3. 點選 New SSH key
  4. Title：隨便填寫，例如 “My Windows PC”
  5. Key type：保持預設 “Authentication Key”
  6. Key：貼上剛才複製的公鑰內容（以 ssh-ed25519 或 ssh-rsa 開頭）
  7. 點選 Add SSH key 儲存

5.4 測試連線 

1

ssh -T git@github.com

第一次連線時，會提示 Are you sure you want to continue connecting?，務必手動輸入 yes。成功後顯示類似 Hi your_username! You've successfully authenticated...。

5.5 重新克隆 

1

git clone git@github.com:taichi-project/anyagent.git

5.6 優缺點與最佳實踐

優點：一勞永逸的安全與穩定。配置完成後，你和 GitHub 之間建立了一條完全加密且免密的直連通道，徹底免疫 HTTP/HTTPS 協定下的代理埠衝突、SSL 證書劫持、以及大檔案傳輸時頻繁出現的連線重置錯誤。

缺點：前置門檻較高。對於新手而言，理解公私鑰非對稱加密並在命令列中完成生成、複製、繫結這套流程容易出錯（例如少複製字元、忘記輸入 yes）。並且與裝置強繫結，換電腦或重灌系統後需要重新配置。

最佳實踐：在日常開發中，強烈建議將 SSH 作為 Git 互動的預設協定。對自己長期維護或頻繁 push/pull 的倉庫，一律使用 SSH 直連；僅在需要臨時下載一次性程式碼、對穩定性要求不高時，才使用 HTTPS 配合瀏覽器或終端代理。
