SKILL.md 的格式規範已經成熟，真正的挑戰在於內容設計。本文梳理了從 Anthropic、Vercel 到 Google 內部實踐中沈澱的五種可複用 Agent Skill 設計模式——Tool Wrapper、Generator、Reviewer、Inversion、Pipeline，每種都附有可直接執行的 ADK 程式碼範例。

談到 SKILL.md，開發者往往糾結於格式——寫好 YAML、組織目錄結構、遵循規範。但在 30 多種 Agent 工具（如 Claude Code、Gemini CLI、Cursor）已經統一採用相同佈局的今天，格式問題已基本成為過去式。

真正的挑戰在於內容設計。規範告訴你如何打包 Skill，但完全沒有涉及如何組織內部邏輯。例如，一個封裝 FastAPI 約定的 Skill 與一個四步文件生成流水線，雖然外部的 SKILL.md 檔案看起來一樣，內部運作方式卻截然不同。

透過研究整個生態系統中 Skill 的構建方式——從 Anthropic 的倉庫到 Vercel 和 Google 的內部指南——有五種反覆出現的設計模式可以幫助開發者構建更可靠的 Agent。

本文逐一介紹每種模式，並附帶可執行的 ADK 程式碼：

  • Tool Wrapper：讓你的 Agent 立即成為任何函式庫的專家
  • Generator：基於可複用範本生成結構化文件
  • Reviewer：按清單對程式碼進行嚴重性評分
  • Inversion：Agent 先採訪你，再動手
  • Pipeline：透過檢查點強制執行嚴格的多步工作流

模式 1：Tool Wrapper

Tool Wrapper 為你的 Agent 提供特定函式庫的按需上下文。你不必將 API 約定硬編碼到系統提示詞中，而是將它們打包到 Skill 裡。Agent 只有在真正使用該技術時才會載入這些上下文。

這是最簡單的實作模式。SKILL.md 檔案監聽使用者提示詞中的特定函式庫關鍵字，動態載入 references/ 目錄中的內部文件，並將這些規則作為絕對真理來遵循。這正是你將團隊內部編碼規範或特定框架最佳實踐分發到開發者工作流中的機制。

# skills/api-expert/SKILL.md
---
name: api-expert
description: FastAPI development best practices and conventions. Use when building, reviewing,
  or debugging FastAPI applications, REST APIs, or Pydantic models.
metadata:
  pattern: tool-wrapper
  domain: fastapi
---

You are an expert in FastAPI development. Apply these conventions to the user's code or question.

## Core Conventions

Load 'references/conventions.md' for the complete list of FastAPI best practices.

## When Reviewing Code
1. Load the conventions reference
2. Check the user's code against each convention
3. For each violation, cite the specific rule and suggest the fix

## When Writing Code
1. Load the conventions reference
2. Follow every convention exactly
3. Add type annotations to all function signatures
4. Use Annotated style for dependency injection

模式 2：Generator

Tool Wrapper 負責注入知識，Generator 則保證輸出的一致性。如果你苦惱於 Agent 每次執行都生成不同的文件結構，Generator 透過編排"填空"流程來解決這個問題。

它利用兩個可選目錄：assets/ 存放輸出範本，references/ 存放風格指南。指令扮演專案經理的角色——告訴 Agent 載入範本、閱讀風格指南、向使用者詢問缺失變數，然後填充文件。這對生成可預測的 API 文件、標準化 commit message 或腳手架程式碼架構非常實用。

# skills/report-generator/SKILL.md
---
name: report-generator
description: Generates structured technical reports in Markdown. Use when the user asks to write,
  create, or draft a report, summary, or analysis document.
metadata:
  pattern: generator
  output-format: markdown
---

You are a technical report generator. Follow these steps exactly:

Step 1: Load 'references/style-guide.md' for tone and formatting rules.

Step 2: Load 'assets/report-template.md' for the required output structure.

Step 3: Ask the user for any missing information needed to fill the template:
- Topic or subject
- Key findings or data points
- Target audience (technical, executive, general)

Step 4: Fill the template following the style guide rules. Every section in the template must be
present in the output.

Step 5: Return the completed report as a single Markdown document.

模式 3：Reviewer

Reviewer 模式將"檢查什麼"與"如何檢查"分離開來。你不必寫一個長篇系統提示詞來羅列每種程式碼異味，而是將模組化的評分標準存放在 references/review-checklist.md 檔案中。

當使用者提交程式碼時，Agent 載入這個清單並有條理地對程式碼進行評分，按嚴重程度對發現進行分組。如果你將 Python 風格檢查清單換成 OWASP 安全檢查清單，就能用完全相同的 Skill 基礎設施得到完全不同的專項審計。這是自動化 PR Review 或在人工審核前捕獲漏洞的高效方法。

下面的程式碼審查 Skill 展示了這種分離。指令保持靜態，Agent 動態地從外部清單載入具體的審查標準，並強制輸出結構化的、按嚴重性分組的結果：

# skills/code-reviewer/SKILL.md
---
name: code-reviewer
description: Reviews Python code for quality, style, and common bugs. Use when the user submits
  code for review, asks for feedback on their code, or wants a code audit.
metadata:
  pattern: reviewer
  severity-levels: error,warning,info
---

You are a Python code reviewer. Follow this review protocol exactly:

Step 1: Load 'references/review-checklist.md' for the complete review criteria.

Step 2: Read the user's code carefully. Understand its purpose before critiquing.

Step 3: Apply each rule from the checklist to the code. For every violation found:
- Note the line number (or approximate location)
- Classify severity: error (must fix), warning (should fix), info (consider)
- Explain WHY it's a problem, not just WHAT is wrong
- Suggest a specific fix with corrected code

Step 4: Produce a structured review with these sections:
- **Summary**: What the code does, overall quality assessment
- **Findings**: Grouped by severity (errors first, then warnings, then info)
- **Score**: Rate 1-10 with brief justification
- **Top 3 Recommendations**: The most impactful improvements

模式 4：Inversion

Agent 天生傾向於直接猜測並立即生成。Inversion 模式翻轉了這個動態關係——不是使用者驅動提示詞、Agent 執行，而是 Agent 反向充當採訪者。

Inversion 依賴明確、不可協商的門控指令（如"在所有階段完成之前不要開始構建"）來強制 Agent 先收集上下文。它按順序提出結構化問題，等待你回答後再進入下一階段。Agent 在完整了解你的需求和部署約束之前，拒絕輸出最終結果。

# skills/project-planner/SKILL.md
---
name: project-planner
description: Plans a new software project by gathering requirements through structured questions
  before producing a plan. Use when the user says "I want to build", "help me plan", "design a system",
  or "start a new project".
metadata:
  pattern: inversion
  interaction: multi-turn
---

You are conducting a structured requirements interview. DO NOT start building or designing until
all phases are complete.

## Phase 1 — Problem Discovery (ask one question at a time, wait for each answer)

Ask these questions in order. Do not skip any.

- Q1: "What problem does this project solve for its users?"
- Q2: "Who are the primary users? What is their technical level?"
- Q3: "What is the expected scale? (users per day, data volume, request rate)"

## Phase 2 — Technical Constraints (only after Phase 1 is fully answered)

- Q4: "What deployment environment will you use?"
- Q5: "Do you have any technology stack requirements or preferences?"
- Q6: "What are the non-negotiable requirements? (latency, uptime, compliance, budget)"

## Phase 3 — Synthesis (only after all questions are answered)

1. Load 'assets/plan-template.md' for the output format
2. Fill in every section of the template using the gathered requirements
3. Present the completed plan to the user
4. Ask: "Does this plan accurately capture your requirements? What would you change?"
5. Iterate on feedback until the user confirms

模式 5：Pipeline

對於複雜任務，你無法承受跳過步驟或忽略指令的後果。Pipeline 模式透過硬檢查點強制執行嚴格的順序工作流。

指令本身就是工作流定義。透過實現明確的門控條件（例如，在從文件字串生成進入最終組裝之前要求使用者批准），Pipeline 確保 Agent 無法繞過複雜任務並呈現未經校驗的最終結果。

這個模式利用所有可選目錄，僅在需要的特定步驟時拉入不同的引用檔案和範本，保持上下文視窗的整潔。

# skills/doc-pipeline/SKILL.md
---
name: doc-pipeline
description: Generates API documentation from Python source code through a multi-step pipeline.
  Use when the user asks to document a module, generate API docs, or create documentation from code.
metadata:
  pattern: pipeline
  steps: "4"
---

You are running a documentation generation pipeline. Execute each step in order. Do NOT skip steps
or proceed if a step fails.

## Step 1 — Parse & Inventory
Analyze the user's Python code to extract all public classes, functions, and constants. Present
the inventory as a checklist. Ask: "Is this the complete public API you want documented?"

## Step 2 — Generate Docstrings
For each function lacking a docstring:
- Load 'references/docstring-style.md' for the required format
- Generate a docstring following the style guide exactly
- Present each generated docstring for user approval
Do NOT proceed to Step 3 until the user confirms.

## Step 3 — Assemble Documentation
Load 'assets/api-doc-template.md' for the output structure. Compile all classes, functions, and
docstrings into a single API reference document.

## Step 4 — Quality Check
Review against 'references/quality-checklist.md':
- Every public symbol documented
- Every parameter has a type and description
- At least one usage example per function
Report results. Fix issues before presenting the final document.

模式可以組合

這些模式不是互斥的——它們可以組合使用。

Pipeline 可以在最後加入 Reviewer 步驟來雙重檢查自己的工作。Generator 可以在最開始依賴 Inversion 來收集填充範本所需的變數。得益於 ADK 的 SkillToolset 和漸進式上下文載入，你的 Agent 只在執行時消耗確有所需的模式對應的 Context Token。

不要試圖把複雜而脆弱的指令塞進一個系統提示詞。將你的工作流拆解開來，應用正確的結構模式，打造可靠的 Agent。
