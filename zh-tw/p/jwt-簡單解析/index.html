使用者登入驗證流程（基於 JWT）

  1. 使用者輸入使用者名稱和密碼，並透過 HTTPS 請求傳送至伺服器。

  2. 伺服器驗證憑據：

    • 若驗證成功，則生成一個 簽名過的 JWT（JSON Web Token） 並返回給客戶端；
    • 若失敗，則返回錯誤資訊。

  3. 客戶端（如瀏覽器）收到 JWT 後，將其儲存（通常存於 localStorage 或 cookie 中，Vue.js 框架可使用 Vuex 或 Pinia）。

  4. 後續每次請求，客戶端將 JWT 放在 HTTP 請求頭（如 Authorization: Bearer <token>）中傳送給伺服器。

  5. 伺服器收到請求後：

    • 使用本地儲存的金鑰對 JWT 的簽名進行驗證；
    • 若簽名有效且未過期（透過 exp 欄位判斷），則認為使用者已認證，返回所需資料；
    • 否則拒絕請求。

  6. 使用者退出登入時，客戶端只需銷燬本地儲存的 token 即可，伺服器無需任何操作。

JWT 簡介

JWT（JSON Web Token）是一種開放標準（RFC 7519），用於在各方之間安全地傳輸資訊作為 JSON 物件。它將（使用者資訊如使用者 ID、角色等）加密編碼到 token 的 payload 中，伺服器不儲存任何使用者資訊。伺服器透過使用儲存的金鑰驗證 token 的正確性，只要正確即透過驗證。

優點是在分散式系統中，很好地解決了單點登入問題，很容易解決了 session 共享的問題。jwt 長度較小，且可以使用 URL 傳輸（URLsafe）。

核心特點：

  • 無狀態（Stateless） ：伺服器不儲存 session 資訊，所有認證資訊都包含在 token 中。
  • 自包含（Self-contained） ：token 本身攜帶必要資料，減少資料庫查詢。
  • 支援跨域與分散式系統：天然適用於微服務架構和單點登入（SSO）場景。
  • URL 安全：Base64Url 編碼使其可安全地透過 URL、POST 引數或 HTTP Header 傳輸。

/** 生產 token */
public static String generateToken(Map<String, Object> claimMaps) {

    if (null != claimMaps) {
        claimMaps.forEach((key, val) -> {
            claimMaps.put(key, val.toString());
        });
    }

    return Jwts.builder()
            // JWT_ID，可用於每次簽名唯一識別
            .setId(UUID.randomUUID().toString())
            // 資料壓縮方式
            .compressWith(CompressionCodecs.GZIP)
            // 簽發者資訊
            .setIssuer(ISSUER)
            // 說明
            .setSubject("system")
            // 接收使用者
            .setAudience(AUDIENCE)
            // 簽發時間
            .setIssuedAt(new Date(System.currentTimeMillis()))
            // 過期時間戳
            .setExpiration(new Date(System.currentTimeMillis() + EXPIRES_IN * 1000))
            // claim 資訊，自定義載荷
            .addClaims(claimMaps)
            // 簽名演算法 + 金鑰
            .signWith(SIGNATURE_ALGORITHM, secretKey)
            .compact();
}

驗證 token 的過程其實跟重新生成一個 token 的過程是一樣的

根據傳遞過來的 header、payload 以及服務端儲存的金鑰，重新生成一個 token 對比：

  • 如果 token 相同，那麼標誌 token 有效，沒被修改。

    • 同時如果 token 沒被修改，還可以進一步同 base64 解密 payload，然後根據 payload 中的 exp 有效期資訊，判斷 token 是否已經過期

注意： JWT 本身包含認證資訊，因此一旦資訊洩露，任何人都可以獲得令牌的所有許可權。因此做前端開發時，最好不要把 JWT 存放在 Cookie 這種容易洩露個人隱私資訊的儲存單元。

優點

  • 無狀態 & 易擴充套件：非常適合分散式系統和微服務架構；
  • 解決 Session 共享問題：無需共享 session 儲存；
  • 天然支援跨域和移動端；
  • 減少資料庫壓力：認證資訊內建於 token，無需頻繁查庫。

缺點與風險

  1. 無法主動作廢令牌
    一旦簽發，在過期前始終有效。若使用者登出或許可權變更，伺服器無法立即使舊 token 失效（除非引入黑名單機制，但這違背了無狀態初衷）。
  2. 敏感資訊洩露風險
    Payload 雖經 Base64 編碼，但未加密（除非使用 JWE）。切勿在 token 中存放密碼等敏感資料。
  3. 必須使用 HTTPS
    JWT 透過網路傳輸，若使用 HTTP，極易被中間人竊取。務必全程使用 HTTPS。
  4. 令牌體積較大
    相比傳統 session ID，JWT 因包含資料而更長，可能影響效能（尤其在高頻請求場景）。

補充說明

  • 單點登入（SSO） ：JWT 天然支援，因 token 可被多個服務驗證。

  • 首頁訪問控制：若需「放開首頁」（即匿名訪問），應在閘道器或攔截器中配置白名單路徑，跳過 JWT 驗證。

  • 跨域支援：JWT 本身與 CORS 無關，但配合 Authorization Header 可輕鬆實現跨域認證。

  • 對比 Spring Session：

    • Spring Session 依賴伺服器端儲存（如 Redis），支援主動失效；
    • JWT 無狀態，但犧牲了實時控制能力；
    • 兩者適用於不同場景，可結合使用（如用 JWT 認證，用 Redis 管理黑名單）。

增強 JWT 安全性與可控性的建議方案

儘管 JWT 具備無狀態、可擴充套件等優勢，但其「無法主動失效」的特性在某些業務場景（如使用者登出、密碼修改、許可權變更）中確實構成挑戰。為此，推薦採用以下兩種互補策略來增強系統的安全控制能力：

方案一：短期訪問令牌 + 重新整理令牌機制（Access Token + Refresh Token）

  • 核心思想：

    • Access Token：有效期較短（如 15~30 分鐘），用於日常 API 認證；
    • Refresh Token：有效期較長（如 7 天），儲存於安全的 HttpOnly Cookie 或安全儲存中，僅用於換取新的 Access Token。

  • 工作流程：

    1. 使用者登入成功後，伺服器返回一對令牌：access_token 和 refresh_token；
    2. 客戶端使用 access_token 呼叫受保護介面；
    3. 當 access_token 過期時，客戶端用 refresh_token 向認證服務申請新的 access_token；
    4. 若使用者登出或修改密碼，伺服器立即作廢對應的 refresh_token（如從資料庫或 Redis 中刪除）；
    5. 即使舊的 access_token 尚未過期，因其無法續期，實際有效視窗被大幅縮短。

  • 優點：

    • 平衡安全性與使用者體驗；
    • 登出後最多等待一個 Access Token 的生命週期（如 30 分鐘）即可完全失效；
    • 符合 OAuth 2.0 標準實踐。

方案二：基於 Redis 的輕量級 Token 黑名單 / 白名單機制

  • 實現方式 A：JTI 黑名單

    • 在 JWT 的 jti（JWT ID）欄位中嵌入唯一標識；
    • 使用者登出、改密或許可權變更時，將該 jti 及其過期時間存入 Redis（TTL = 原 JWT 剩餘有效期）；
    • 每次驗證 JWT 時，額外檢查 jti 是否存在於黑名單中；
    • 若存在，則拒絕請求。

  • 實現方式 B：使用者會話白名單（更嚴格）

    • 每次成功登入生成 JWT 後，將其完整字串（或雜湊值）以 user_id:session_id 為鍵存入 Redis；
    • 所有受保護介面在驗證 JWT 簽名和有效期後，額外校驗該 token 是否存在於 Redis 中；
    • 當使用者登出、改密或管理員強制下線時，刪除對應 Redis 鍵；
    • 此時即使 token 未過期、簽名有效，也會因「不在白名單」而被拒絕。

  • 優點：

    • 實現真正的即時登出；
    • 支援細粒度控制（如多裝置管理、強制踢下線）；
    • Redis 高效能，對系統吞吐影響極小。

  • 注意事項：

    • 需合理設定 Redis 鍵的 TTL，避免記憶體無限增長；
    • 白名單方案雖更安全，但略微犧牲了 JWT 的「完全無狀態」特性，屬於有狀態增強模式。

綜合建議

場景 推薦方案
普通 Web 應用、移動端 App Access Token + Refresh Token（平衡安全與效能）
高安全要求系統（如金融、後臺管理） Refresh Token + Redis 黑名單/白名單
需支援「多裝置登入管理」 使用 Redis 白名單 + session_id 標識裝置

💡 最佳實踐：即使採用黑名單機制，也應保持 Access Token 的短期有效期（如 ≤30 分鐘），以限制 Redis 儲存壓力和潛在攻擊視窗。
