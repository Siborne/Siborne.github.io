核心要點

  • 橫軸 vs 縱軸：升級基礎模型是 OpenAI 和 Anthropic 的事；普通開發者應在縱軸上發力——用工程技術增強現有 LLM 的能力，即 Augmenting LLM。
  • 強化單模型的三板斧：Prompt Engineering（零成本，優先使用）→ RAG（補知識短板）→ Fine-Tuning（不得已才做）。
  • 從模型到系統：Agentic Workflow 將 LLM 從「會回答問題的模型」升級為「一套真正運作、產出價值的系統」。
  • 心態轉變：從確定性工程思維切換到模糊工程思維——你是管理者，AI 是執行者。
  • 評估是命脈：沒有完善的 Evaluation 系統，Agent 上線的風險不可控。
  • Multi-Agent 的本質：把 Agent 當作 Tool 來呼叫，就像呼叫 API 一樣。

一、開篇：AI Builder 的困境與縱軸思維

如果你關注 AI 領域，最近兩年最炙手可熱的角色一定是 AI Engineer 和 AI Builder。大型語言模型越強，這群人越吃香——他們能幫公司打造內部工具、優化營運流程，很多人甚至已經把想法做成產品、成立了自己的公司。

但想學 AI 的人很多，大多數人卻不知從何下手。市面上的資源不是太碎片化，就是過於艱澀，看完仍然不知道自己學到了什麼，或者下一步該往哪走。

Stanford 有一門課叫 Beyond LLM，我認為這是目前最接近答案的東西。它從大型語言模型的本質講起，一路延伸到 Prompt Engineering、RAG、Fine-Tuning、Agentic Workflow，以及 Multi-Agent 框架。本文將用一篇文章的篇幅把核心整理給你——看完之後，你將對 AI 在商業領域的應用建立一套完整的認知框架。

什麼是 LLM？它的限制是什麼？

LLM（Large Language Model，大型語言模型） 是一種基於 Transformer 架構的大規模神經網路，透過對海量文本資料的訓練，學會了預測下一個 Token 的機率分佈。本質上，它是一個極其複雜的自迴歸機率預測機。

LLM 要變強有兩條路：

  • 橫軸：換更強的 Base Model（基礎模型），比如從 GPT-4 升級到 GPT-5。但這條路是 OpenAI 和 Anthropic 在走的，普通人沒有能力也沒有資金去訓練自己的大模型。
  • 縱軸：在現有 LLM 上疊加各種工程技巧，即 Augmenting LLM（增強型語言模型）——想辦法在已有的基礎模型上提升能力。

這條縱軸，也正是整篇文章關注的核心。

學習提示：如果你是初學者，建議先把精力 100% 投入縱軸。橫軸的事情——今天 GPT-5 發布、明天 Claude 4 出來——你當成新聞看看就好。真正讓你在職場有差異化競爭力的是：別人只會用 ChatGPT 聊天，而你能用 RAG + Agentic Workflow 搭一套自動處理客服工單的系統。

如果你只會用 Base Model，在商業場景上一定會撞牆。ChatGPT 剛出來的時候，沒有聯網功能，沒有辦法呼叫工具，充其量就是一個聰明的問答機器人，不能實際完成一件事。

Stanford 教授整理了 Base Model 的幾個常見限制：

限制 說明
缺乏領域知識 你的公司資料、內部文件、產品規格，Base Model 一概不知
資訊滯後 模型不可能每幾個月重訓一次，新詞、新事件、新公司它都不認識
輸出不可控 LLM 是機率性輸出，同樣的 Prompt 跑兩次結果可能不同。在聊天場景 OK，但在生產環境可能造成嚴重後果
長上下文退化 Context 太長時模型表現顯著下降，存在「Lost in the Middle」現象——即使資訊就在上下文中，模型也可能找不到

關鍵洞察：這四個限制不是獨立存在的——它們會相互放大。比如「資訊滯後」遇上「輸出不可控」，意味著模型可能用自信的語氣說出過時錯誤資訊，而你很難一眼識別。理解這四個限制，是後面學 RAG、Agentic Workflow 的底層動機——每項技術本質上都在解決其中一個或多個限制。

做 AI 產品，光換更強的 Base Model 是不夠的——你需要在縱軸上發力。

接下來，文章前半部分會介紹強化單一個 LLM 的三大工具：Prompt Engineering、Fine-Tuning 和 RAG；後半部分進入系統設計，介紹 Agentic Workflow、Evaluation 評估方法，以及 Multi-Agent。

二、強化單一 LLM 的三大工具

Prompt Engineering：每個工程師的基本功

Prompt Engineering（提示詞工程） 是設計和優化輸入給 LLM 的文本指令，以引導模型產生更高品質、更符合預期的輸出。

Stanford 教授直言，他不認為「Prompt Engineer」會成為一個獨立職業——因為這是每個工程師都該掌握的基本技能，就像九九乘法表一樣。

鋸齒邊界、打瞌睡與半人馬的隱喻

頂級管理顧問公司 BCG 做過一個經典實驗：將一群顧問分成三組——無 AI 組、ChatGPT 組、ChatGPT + 提示詞訓練組。研究發現了三個重要現象：

  1. The Jagged Frontier（鋸齒邊界）：AI 不是在所有任務上都表現得好。有些任務搭配 AI 顯著加分，但有些 AI 反而會拖後腿。你需要清楚地知道這個邊界在哪裡。

  2. Falling Asleep at the Wheel（在方向盤前打瞌睡）：當你不知道某個任務恰好是 AI 不擅長的領域，卻過度信任它、把輸出直接交付——結果比不用 AI 還慘。

  3. Centaurs vs Cyborgs（半人馬 vs 生化人）：

    • Centaur（半人馬）模式：分工委派型——丟一個長 Prompt 給 AI 完成整份簡報，自己做其他事。適合重複性高、流程清楚的任務。
    • Cyborg（生化人）模式：高頻率來回協作型——和模型一句一句對話。適合需要判斷、需要創意、需要來回校正的任務。

關鍵不在於哪種更好，而在於有意識地切換。企業自動化工作流常用 Centaur 模式，個人深度協作常用 Cyborg 模式。

概念串聯：Centaur 模式本質上就是後面會講的 Agentic Workflow 的雛形——你把整個任務丟給系統，系統內部自行拆解執行。而 Cyborg 模式更接近你日常使用 ChatGPT/Claude 的方式。當你搭建 Agent 系統時，你的角色就從 Cyborg（親自來回對話）變成了 Centaur（設計流程，讓系統自動跑）。

Prompt Chaining：最重要卻最被低估的技巧

很多人以為 Prompt Engineering 就是寫好格式——給誰看、什麼格式、重點在哪。這些當然重要，但教授指出，最常用、最重要的技巧是 Prompt Chaining（提示詞鏈式呼叫）。

注意區分：Chain of Thought（CoT，思維鏈） 是讓模型 “step by step” 思考；Chaining 是把一個複雜 Prompt 拆成多個獨立 Prompt，前一個的輸出餵給下一個。

舉個例子——寫客戶投訴回信：

方式 做法 問題
單 Prompt 「讀這封投訴信，寫一封專業回信」 黑盒子，輸出有問題也不知道調整哪裡
Chaining（3 步） ① 抽取客戶抱怨點 → ② 用抽取的問題起草大綱 → ③ 用大綱寫完整回信 每一步可獨立測試、獨立 Debug

Chaining 不僅讓模型表現更好，也賦予你 Observability（可觀測性）——你能知道 LLM 在做什麼、哪個環節出了問題。

實戰建議：在實際專案中，建議你從 Chaining 開始而不是從單 Prompt 開始。即使是最簡單的需求，也先拆成 2-3 步——你會發現 Debug 效率提升至少 3 倍。工具上可以用 LangChain 的 LCEL 或直接手寫 Python 串聯，核心邏輯不到 50 行程式碼。

Fine-Tuning：能不做就不做

Fine-Tuning（微調） 是指在預訓練模型的基礎上，用特定領域的標註資料對模型參數進行進一步訓練，使其在特定任務上表現更好。

Stanford 教授的立場很明確：能不做就不做。原因有四：

  1. 需要大量優質標註資料：成本對普通人太高。
  2. 容易 Overfit（過擬合）：在你那個特定任務上變很強，但通用問題反而答不出來，失去 Base Model 原本的廣度。
  3. 時效性差：你花兩個月 Fine-Tune 完上線，下個月新一代替換 Base Model 直接打翻你的版本。
  4. Prompt Engineering 通常能达到同样效果：成本低得多，而且 Prompt 是 Portable（可移植的）——換新 Base Model 後 Prompt 大多還能用，Fine-Tuning 的模型不行。

當然，少數場景下 Fine-Tune 仍然值得做，比如法律、科學等需要高精度重複輸出的領域，或者 Base Model 在某個 Domain 上表現確實吃力。

常見誤區：很多人以為「我的行業很專業，所以需要 Fine-Tune」。但實際上，醫療、金融、法律等領域的絕大多數應用場景，用 RAG + 精心設計的 Prompt 就能达到生產級效果。判斷標準很簡單：只有當你的任務需要模型學會一種「新能力」（而不僅僅是「新知識」），Fine-Tune 才真正有必要。

那如果 Prompt Engineering 塞不下特定領域知識，Fine-Tuning 又成本效益不對等——怎麼辦？答案就是 RAG。

RAG：連接 LLM 與私有知識的標準解法

RAG（Retrieval-Augmented Generation，檢索增強生成） 是 AI 工程師面試中最常考的題目之一。它的核心思路是：不把知識塞進模型參數，而是在推理時動態檢索相關內容，拼到 Prompt 裡讓模型參考。

RAG 解決的痛點：

  • Context Window 太小 / 長 Context 檢索不準
  • 資訊有時效性
  • 模型容易產生幻覺——Hallucination（指 LLM 憑空編造不存在的事實）

關鍵洞察：Hallucination 是 RAG 要解決的核心問題，但要注意——RAG 只是「降低」幻覺機率，不是「消除」。即使把資料鎖在 Prompt 裡，模型仍然可能在概括或推理時產生偏差。這就是為什麼後面的 Evaluation 系統至關重要：你需要持續監控幻覺率，而不是上線後就以為萬事大吉。

RAG 工作流程

假設一個需要高度準確的醫療場景——查詢藥物副作用：

  1. 向量化入庫：用 Embedding 模型（嵌入模型） 把所有資料轉成向量，存入 Vector Database（向量資料庫）。語義相近的文字在數學空間中距離也更近。

  2. 查詢向量化：使用者問題「藥物 A 的副作用」也用同一個 Embedding 模型轉成向量。

  3. 語義檢索：用距離度量從向量資料庫中找出最相關的文件片段。注意：這不是關鍵字匹配——就算文件寫的是「不良反應」而不是「副作用」，一樣能找到。

  4. 組裝 Prompt：將檢索到的文件 + System Prompt + 使用者問題組合成最終 Prompt，模板大致如下：

根據以下 Documents 回答使用者的問題。如果 Documents 裡沒有答案，就說「我不知道」。

這樣設計是為了把模型鎖在你提供的資料範圍內，避免它自由發揮。你還可以要求模型附上答案來源（第幾頁、第幾章），讓使用者驗證。

Chunking 與多層級檢索

一份藥物說明書可能長達 50 頁，直接整個轉成向量會讓細節遺失。所以通常需要 Chunking（文件切分）——將文件切為固定大小的片段，每段各自轉成向量。

更進階的做法是多層級儲存：同時保留整篇、每章、每段的向量。檢索時先找到相關章節，再往下鑽到精確段落。

實戰建議：Chunking 是 RAG 系統裡最容易被低估的環節。一個經驗法則——Chunk Size 控制在 256~1024 Token，相鄰 Chunk 之間保留 10%~20% 的重疊（Overlap）。太小則語義不完整，太大則檢索精度下降。多層級檢索（先搜章節再搜段落）對超過 50 頁的文件效果顯著，但複雜度也相應增加——建議先用單層 Chunking 跑通全流程，再優化。

RAG 會被超長 Context Window 淘汰嗎？

有人說，等模型支援超長 Context Window 且算力足夠便宜，Base Model 直接讀取整個資料庫，RAG 就沒用了。Stanford 教授的回答是：

理論上對，實際上錯。

原因很實際——Latency（延遲）。每次問問題模型都要把整個 Google Drive 重讀一遍，沒人等得了。就像搜尋引擎靠預建索引快速定位，不可能每次查詢都把整個網路重爬一遍。

RAG 除了準確度外，還有檢索效率、即時更新等優勢，在可預見的未來仍將存在價值。

三、Agentic Workflow：從模型到系統

講完強化單模型的三個工具，接下來進入第二大部分——從模型到系統。單個 LLM 再強也有做不到的事，Agentic Workflow 把 AI 從「會回答問題的模型」變成「一套真正運作、產出價值的系統」。

什麼是 Agentic Workflow？

Agentic Workflow（智能體工作流） 這個詞來自 Andrew Ng（吳恩達）——Coursera 聯合創始人、Google Brain 創始負責人、前百度首席科學家。他刻意不用已被濫用的 “AI Agent” 一詞，而是用 Agentic Workflow 精確描述：

把一組 Prompt、外部工具（Tools）、記憶（Memory）和各種元件組合進一個有結構的工作流程中，形成一套系統。

RAG 主要做一件事：給 LLM 外部資料當參考。而 Agent 把 RAG 當作眾多工具之一，還能呼叫外部 API、維護記憶、執行多步驟決策。

舉個退訂單的例子：

場景 RAG 能做的 Agent 能做的
「我想退這筆訂單」 丟給你退費政策文件 用 RAG 檢索政策 → 主動問訂單編號 → 用 Tool 查訂單 → 確認退費 → 告知 3-5 個工作天到帳

RAG 是工具，Agent 是使用 RAG 這個工具的系統。

學習提示：這句話是整個課程最重要的心智模型之一。你可以建立這樣一個思維習慣：每次看到一門新技術（比如新的向量資料庫、新的 Agent 框架），先問自己——這是「工具」還是「系統」？工具是拼圖的一塊，系統是把拼圖拼起來的方式。大多數人卡住的原因不是不會用工具，而是不知道怎麼把它們拼起來。

工程心態的四重轉變

要打造 Agentic Workflow，你的工程心態需要先在四個維度上翻轉：

維度 傳統軟體 Agentic AI 軟體
資料 結構化資料（JSON、資料庫、表單） 自由文本、圖片、音訊——無固定格式
邏輯 Deterministic（確定性的）：同樣的輸入永遠給同樣的輸出 Fuzzy（模糊性的）：同樣輸入可能產生不同輸出
架構心態 精確控制每一步執行路徑，像寫 Microservices Think like a manager：給 AI 目標和限制，讓它自己決定怎麼做
測試 確定性測試，跑一百次結果一樣 迭代探索式測試，模型對 Context 敏感，無法窮舉

第一條落地原則隨之而來：

能 Deterministic 解的問題，就 Deterministic 解；剩下 Fuzzy 的部分，加上護欄（Guardrails）。

關鍵洞察：這條原則可以翻譯成一句更具體的話——你的程式碼裡應該永遠是 if-else 包裹著 LLM 呼叫，而不是 LLM 呼叫包裹著 if-else。 把 LLM 當成你系統裡的一個「模糊推理模組」，外圍用確定性邏輯（校驗、重試、降級）把它保護起來。這樣即使 LLM 犯錯了，系統也不會崩潰。

教授舉了自己的例子：技能評估系統中，選擇題和配對題用確定性方式計分（有標準答案）；但語音+程式設計混合題型沒有標準答案，只能用 LLM 模糊評分。而 Fuzzy 評分一定會有誤判——所以他們在系統裡設計了一個 Appeal Feature（申訴機制），受測者可以提出申訴，由真人介入審查。

這就是護欄的具體形式：不是試圖讓 AI 零錯誤，而是在它出錯時有人接得住。

實戰建議：護欄設計有三個層次——① 輸入護欄：校驗使用者輸入是否合法；② 過程護欄：監控 Agent 每一步的輸出是否符合預期格式；③ 輸出護欄：最終結果是否在安全範圍內。至少實現①和③，②是進階優化。另外，永遠要有一個 Human-in-the-loop（人工介入） 的逃生通道。

打造 Agent 的三個核心要素

以「幫我訂一張去巴黎的機票」為例：

① Prompts（提示詞）

你如何告訴 AI：它的角色是什麼、它能做什麼、不能做什麼。

② Context Management（上下文管理）

本質就一件事：把對的資訊，在對的時間，提供給 Agent。包含：

  • Working Memory（工作記憶）：高頻、要快的資訊，如使用者名字、本次目的地。
  • Archival Memory（歸檔記憶）：低頻、可以慢一點的資訊，如過去五年的訂房記錄，需要時再查。

③ Tools（工具）

Agent 能呼叫的外部能力，通常分兩種：

  • 做事的：Flight Search、Hotel Booking、Payment
  • 查資料的：去 CRM 查客戶資料、查訂單記錄

Agent 自主性的三層分級

層級 描述 特點
Level 1: Hardcoded Steps 步驟全部寫死，按順序走 安全可預測，但僵硬
Level 2: Hardcoded Tools + 自主步驟 給 Agent 一組工具，讓它自己決定執行順序 目前最常見的 Production Setup，教授推薦的起點
Level 3: Fully Autonomous 自己決定步驟，甚至自己建立工具 能力最強，風險最高——誤判可能導致嚴重損失

學習提示：如果你是第一次搭建 Agent，務必從 Level 2 開始。Level 1 太僵硬，遇到預期外的情況就會卡住；Level 3 太危險，生產環境不可控。Level 2 的甜點在於——你控制「工具範圍」，Agent 控制「執行順序」。等你對 Level 2 完全熟練、Eval 系統也建立好之後，再考慮往 Level 3 探索。

MCP：工業級工具整合標準

MCP（Model Context Protocol，模型上下文協議） 是 Anthropic 推出的標準化客戶端-伺服器架構，用於解決 AI 工具生態碎片化的問題。

傳統做法是：你要為每一個 API 單獨寫串接邏輯，手動教 LLM 每個 API 怎麼用、傳什麼參數。

MCP 的做法是：在中間放一個協議層——Agent 不需要認識每個 API，它只需要跟 MCP Server 溝通，MCP Server 負責跟後面的服務打交道。

你可以把 MCP 想像成一個通用 USB-C 插頭：以前每個國家的插座規格不同，你要帶一堆轉接頭；有了 MCP，插一個就全通了。

關鍵洞察：MCP 在 2024 年底發布後迅速成為業界標準。到今天（2026 年中），主流 AI 工具（Claude Desktop、Cursor、Continue 等）都已原生支援 MCP。這意味著你只需寫一次 MCP Server（比如連接公司 Jira 的 Server），所有支援 MCP 的 AI 應用都能直接呼叫。此外，MCP 還天然支援 Agent-to-Agent Communication——後面 Multi-Agent 章節會展開講。

四、Evaluation：生產級系統的命脈

不管單 Agent 還是 Multi-Agent，上線之前都要回答同一個問題：怎麼知道它真的有用？

答案就是 Evaluation（評估系統）——它是 Production 級別 Agentic 系統的命脈。

三維度評估框架

Stanford 教授給出了一個完整的評估框架，三個維度交叉使用：

維度一：End-to-End（端到端）vs Component-based（元件級）

  • End-to-End 看整體：使用者用完後給幾分？滿不滿意？
  • Component-based 拆開看：這個 Tool 是不是忘了更新 email？發送那一步格式對不對？
  • 光看整體知道哪裡壞但不知道為什麼壞；光看元件可能修了細節但整體體驗仍然差。實務上兩個都要做。

維度二：Objective（客觀）vs Subjective（主觀）

  • Objective 可自動驗證：使用者說 Order ID 是 X，LLM 寫進資料庫變成 Y——寫個 Python 腳本自動對比。
  • Subjective 沒有標準答案：語氣好不好？回答有沒有同理心？這類需要人工評分或用另一個 LLM 當評審。

維度三：Quantitative（定量）vs Qualitative（定性）

  • Quantitative 是數字：改地址成功率百分之幾？各環節延遲多少？
  • Qualitative 是感覺：在哪裡產生了幻覺？語氣哪裡不對？使用者在哪一步卡住了？這個需要人工逐條看，沒有捷徑。

實戰建議：初建 Eval 系統時，最容易犯的錯誤是一上來就想覆蓋全部 8 個交叉格。建議的優先級是：① Component × Objective（自動驗證每步正確性）→ ② End-to-End × Quantitative（追蹤核心指標）→ ③ End-to-End × Subjective（定期人工抽檢）。前兩個可以在 CI/CD 中自動跑，第三個每週抽 20 條看一次。LLM-as-Judge 等更進階的手段，等你對系統有足夠信心再引入。

LLM-as-Judge：用 AI 評審 AI

對於 Subjective Evaluation，常用做法是 LLM-as-Judge（以 LLM 為評審）——用一個額外的 LLM 來評分。有四種主流設計：

  1. Pairwise Comparison（成對比較）：給 Judge 兩個答案，問哪個更好
  2. Single-answer Grading（單答案打分）：直接打 1-5 分
  3. Reference-guided Pairwise（參考引導成對比較）：多給一個標準答案做參照
  4. Rubric-based（基於評分標準）：自己定義評分標準，如「5分=100字以內，含3個重點，首句是概述；0分=答非所問、冗長失焦」

這四種可以混用。例如 Rubric-based + Few-shot Examples，讓評審更清楚你要什麼。

常見誤區：LLM-as-Judge 最大的陷阱是「用同一個模型評判自己」——比如用 GPT-4 評審 GPT-4 的輸出，容易產生 Self-bias（自我偏好），評分虛高。最佳實踐是用不同家族的模型做 Judge（比如用 Claude 評審 GPT 的輸出），或者至少用同家族的不同版本。另外，Judge 的 Rubric 要寫得非常具體，模糊的 Rubric 產出的分數沒有參考價值。

實操：用 Travel Agent 的「禮貌度」舉個例子

教授用 Travel Agent 的禮貌度評估完整演示了四步流程：

步驟 內容 為什麼不能省
Step 1: Error Analysis 從 1000 個使用者對話中抽 20 個，人工逐條讀 你必須先知道問題長什麼樣，才能設計對的評估
Step 2: Design Eval 用 LLM-as-Judge + 禮貌度 Rubric 把 Step 1 發現的問題翻譯成評分標準
Step 3: A/B Test (模型) 固定 Prompt，換底層模型，跑同一批對話，Judge 評分 看哪個模型禮貌度更高
Step 4: A/B Test (Prompt) 固定模型，改 Prompt 措辭，看一個詞的差距影響多大 微小的 Prompt 變化可能帶來顯著差異

核心原則：先人工掃出問題，再設計自動化評估；且模型和 Prompt 這兩個變數一次只動一個。

學習提示：這條「A/B Test 一次只動一個變數」的原則聽起來簡單，但實際執行時很容易違反。一個常見的錯誤是：「換成 Claude 模型 + 同時優化了 Prompt」——結果效果好，但你不知道是模型的功勞還是 Prompt 的功勞。建議你養成一個習慣：每次實驗只改一件事，記錄在實驗日誌裡。

五、Case Study：搭建一個客服 AI Agent

教授給了一個完整的實戰案例——搭建處理「改訂單地址」請求的客服 Agent。用例如下：

使用者說：「我要改 A127 訂單的地址，因為我搬家到建國南路了。」

Step 1: Task Decomposition（任務拆解）

做 Agentic Workflow 的第一步，不是寫程式碼，而是先去客服旁邊坐一兩天，看他們怎麼實際處理這類請求。理解人的工作流之後，再做 Task Decomposition——把大任務拆解成小任務。

觀察後發現，客服實際走了五步：

1
2
3
4
5

① 抽出關鍵資訊（Intent、Order ID、新地址）
  → ② 查資料庫客戶記錄
    → ③ 查公司政策（能改嗎？已出貨了嗎？）
      → ④ 根據收集的資訊起草回信
        → ⑤ 發送 Email

Step 2: 為每一步選擇工具

步驟 工具選擇 原因
① 資訊抽取 LLM 單次 API 呼叫 純文本理解，無需外部工具
② 查/改資料庫 Custom Tool 或 MCP Server 需要與外部系統互動
③ 政策檢查 RAG 政策文件會更新，需要高效檢索
④ 起草回信 LLM 綜合前幾步資訊產生自然語言
⑤ 發送郵件 Email Tool 呼叫外部郵件服務

判斷方法很簡單：先問自己每步是 Fuzzy 還是 Deterministic，再決定用什麼工具。

這就是 AI Builder 真實在做的工作——知道每個工具和技術的邊界，然後組合出你需要的方案。

概念串聯：回顧前面的三層分級——這裡搭建的客服 Agent 正是典型的 Level 2：工具範圍是固定的（5 個步驟各有明確工具），但執行順序由 Agent 根據輸入動態決定。

Step 3: Build Evals

將前面三維度框架全部用上：

  • End-to-End：最終回覆正確性、語氣、使用者滿意度
  • Component-based：資訊抽取精度、API 錯誤率、政策遵守率
  • Objective：自動驗證 Order ID 是否正確、有沒有違反退費政策
  • Subjective：人工 + LLM-as-Judge 評估回信禮貌度、同理心
  • Quantitative：改地址成功率、延遲、退費正確率
  • Qualitative：哪裡產生了幻覺？語氣哪裡不一致？使用者在哪一步困惑？

從零到上線的工程流程總結就是三步：

1

拆解大任務 → 設計工作流 → 建立評估系統

學習提示：如果你是第一次動手做 AI 專案，建議從一個極簡版開始——選一個只有 3-5 步的小任務，不做 RAG、不做 Multi-Agent，只用 Prompt Chaining 搭一個 Level 1 Agent，然後加一套只有 Objective Eval 的評估系統。跑通後再迭代加 RAG、加 Tool、升級到 Level 2。先跑通再優化，先簡單再複雜——這是 AI Builder 最重要的工程紀律。

六、Multi-Agent：把 Agent 當作 Tool

為什麼需要 Multi-Agent？

單個 Agent 已經能拆步驟、呼叫工具、做 RAG、寫郵件——似乎夠用了。Multi-Agent 的存在理由主要有兩個：

理由 說明
平行處理（Parallel Processing） 訂機票時，找航班、找飯店、查天氣——三件事完全可以同時進行。單 Agent 只能序列化，Multi-Agent 可以三個 Specialized Agent 同時跑
可復用性（Reusability） 公司裡的 Design Agent 可以給行銷團隊用，也可以給產品團隊用

但設計原則是：如果一個 Agent 就能解決的問題，硬上 Multi-Agent 只會徒增複雜度。能簡單就簡單，不要過度設計。

常見誤區：很多團隊一上來就說「我們要做 Multi-Agent 系統」，覺得單 Agent 不夠「高級」。但實際上，Multi-Agent 引入了三個額外成本——① Agent 間的通訊開銷和延遲，② 多套 System Prompt 的維護負擔，③ Debug 時需要在多個 Agent 日誌中回溯。只有當你的業務確實滿足以下兩個條件之一時，才值得上 Multi-Agent：a) 任務可以明顯切分為 2+ 個獨立平行子任務；b) 不同子任務需要的核心能力差異巨大，單 Agent Prompt 會過於臃腫。

智慧家庭 Multi-Agent 範例

教授用智慧家庭做 Brainstorm 範例。一個完整的智慧家庭 Multi-Agent 系統可能包含：

  • 溫度控制 Agent
  • 燈光 Agent
  • 保全 Agent
  • 娛樂 Agent
  • 通知 Agent
  • 能源管理 Agent
  • 外加一個 Orchestrator（編排器） 統籌

兩種互動模式：

模式 運作方式 適用場景
Hierarchical（層級式） 使用者只跟 Orchestrator 講話，由它派工給下層 Agent 使用者側——「我要出門了」，Orchestrator 自己去協調燈光、保全、溫控
Flat（扁平式） Agent 之間直接互通，沒有中間人 後台——溫控 Agent 和能源管理 Agent 直接溝通，省掉每次過 Orchestrator 的成本

當 Agent 之間互相通訊時——本質上就是 MCP Protocol。你把 Agent 當作 Tool，就像把 API 當作 Tool 一樣。 每個 Agent 對外暴露一組 Tool-like 介面，其他 Agent 像呼叫工具一樣呼叫它。

這個心態一旦想通，Multi-Agent 就不再神秘——它只是把你已經懂的東西，多疊一層。

七、總結：你的 AI 學習全景路線圖

這篇文章從基礎模型的限制出發，逐層展開了增強 LLM 能力的完整技術棧：

層級 技術 核心要點
L1 Prompt Engineering 成本最低，優先使用。重點在 Chaining 和 Testing，是每個工程師的基本功
L2 Fine-Tuning 除非處理法律、科學等高精度領域，或者興趣使然，否則別輕易碰。成本高、時效性差、Prompt Engineering 通常就夠了
L3 RAG 幫模型補知識的標準解法。做 AI 產品基本一定會碰到——Embedding → Vector DB → Retrieval → Generation
L4 Agentic Workflow 從強化單模型到系統設計。核心是心態轉變：從 Deterministic Engineering 到 Fuzzy Engineering，做 Task Decomposition，建 Evaluation 系統
L5 Multi-Agent 把 Agent 當 Tool，彼此協作。提升速度（平行）和復用性。但記住：能簡單就不要複雜

有了這套認知框架，你就不會盲目跟風——看到別人做 Multi-Agent 就跟著做，看到別人聊 Fine-Tuning 就覺得酷。從實作出發：看看你生活或工作中有什麼痛點，從痛點出發去思考解決方案。在這個過程中，你自然會發現需要學會哪些技術，從而高效地規劃自己的學習路線。

下一步行動建議：如果你想今天就開始動手，這裡有一個「最小可行路徑」——① 找一個你工作中的重複性文字任務（如整理週報、回覆 FAQ）；② 用 Prompt Chaining 把它拆成 2-3 步並串起來跑通；③ 寫幾個 Objective Test Case 自動驗證輸出格式；④ 跑一週看看效果，記下哪裡好哪裡不好。完成這四步，你就已經是一個在實踐中成長的 AI Builder 了。
